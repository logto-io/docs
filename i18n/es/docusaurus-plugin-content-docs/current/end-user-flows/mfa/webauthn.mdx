# Passkeys (WebAuthn)

[Passkey](https://auth.wiki/passkey) proporciona una alternativa más segura y fácil de usar que las contraseñas tradicionales. Al utilizar criptografía de clave pública, passkey mejora la seguridad al vincular el dispositivo del usuario, el dominio del servicio y el ID de usuario, contrarrestando eficazmente los ataques de phishing y contraseñas. Es compatible con varios dispositivos o navegadores, y permite a los usuarios emplear biometría y funciones de seguridad de hardware para una autenticación conveniente. [WebAuthn](https://auth.wiki/webauthn) proporciona la API para que los sitios web implementen passkey.

Logto admite passkeys (WebAuthn) tanto para [Autenticación multifactor (MFA)](/end-user-flows/mfa/configure-mfa) como para [inicio de sesión con passkey](/end-user-flows/sign-up-and-sign-in/passkey-sign-in). La misma credencial WebAuthn subyacente puede reutilizarse en ambos casos, dependiendo de la configuración de tu tenant.

## Conceptos \{#concepts}

Los clientes siempre conocen Passkeys más que WebAuthn, entonces ¿cuál es la relación entre ellos y cómo se usan? Exploremos estos conceptos:

- **Passkeys**: Un passkey es una credencial basada en FIDO, resistente al phishing, que reemplaza las contraseñas. Utiliza criptografía asimétrica de clave pública para una mayor seguridad. Puede ser un token de hardware o una llave de seguridad, como dispositivos USB o Bluetooth. Dado que "Passkeys" es el método de autenticación mostrado a los usuarios, debe usarse dentro del cliente de tu producto.
- **WebAuthn**: Es una API de JavaScript desarrollada por el W3C y la FIDO Alliance, que permite la autenticación de aplicaciones web con los estándares FIDO2. Passkeys es uno de los métodos de autenticación que admite WebAuthn. En la Consola de Logto, nos referimos profesionalmente a esta integración como "WebAuthn".

WebAuthn proporciona diversos autenticadores para que los usuarios elijan, disponibles en dos tipos para uso local y en la nube:

- **Autenticador de plataforma (Platform authenticator, autenticador interno)**: Está vinculado a un único sistema operativo de dispositivo específico, como una computadora, portátil, teléfono o tableta, con el que el usuario inicia sesión. Funciona exclusivamente en el dispositivo para la autorización usando métodos como biometría o un código de acceso del dispositivo, por lo que es una forma rápida de autenticar. Ejemplo: iCloud Keychain verificado por Touch ID, Face ID o código de acceso en macOS o iOS; Windows Hello verificado por reconocimiento facial, huella digital o PIN.
- **Autenticador itinerante (Roaming authenticator, autenticador externo, autenticador multiplataforma)**: Es un dispositivo portátil separado o una aplicación de software, como una llave de seguridad de hardware o un smartphone. Debe conectar el dispositivo usando USB o mantener activado NFC o Bluetooth. El autenticador itinerante no está limitado a un solo dispositivo o navegador, proporcionando mayor flexibilidad.

Para profundizar en los principios y procesos de WebAuthn, puedes consultar nuestras publicaciones de blog: [WebAuthn y Passkeys 101](https://blog.logto.io/web-authn-and-passkey-101/) y [Cosas que debes saber antes de integrar WebAuthn](https://blog.logto.io/webauthn-base-knowledge/).

## Configurar la verificación de passkeys para MFA \{#configure-passkeys-verification-for-mfa}

1. Ve a <CloudLink to="/mfa">Consola > Autenticación multifactor</CloudLink>
2. Habilita el factor "Passkeys (WebAuthn)". Se recomienda usar Passkeys en combinación con otros factores MFA (TOTP, SMS, códigos de respaldo) para reducir la dependencia de un solo factor.
3. Configura tu política MFA preferida (obligatoria vs. opcional)
4. Guarda los cambios de configuración

:::tip
Si el mismo usuario inicia sesión con [inicio de sesión con passkey](/end-user-flows/sign-up-and-sign-in/passkey-sign-in), Logto omitirá el paso de verificación MFA por separado. Un inicio de sesión con passkey ya satisface el requisito de verificación basado en WebAuthn.
:::

:::note Presta atención a las limitaciones

Es esencial tener en cuenta algunas limitaciones al implementar WebAuthn:

1. **Limitación de plataforma y navegador**: Es importante señalar que Logto actualmente no ofrece soporte WebAuthn para aplicaciones nativas. Además, la disponibilidad de autenticadores WebAuthn depende de las capacidades del navegador y del dispositivo ([Consulta la lista](https://caniuse.com/?search=webauthn)). Por lo tanto, WebAuthn no es siempre la única opción para implementar Autenticación multifactor (MFA); de lo contrario, puedes controlar qué navegadores y dispositivos pueden acceder a tu producto.
2. **Limitación de dominio**: Cambiar el dominio puede dificultar la verificación del usuario a través de sus cuentas WebAuthn existentes. Los passkeys están vinculados al dominio específico de la página web actual y no pueden usarse entre diferentes dominios.
3. **Limitación de dispositivo**: Perder el dispositivo puede resultar en la pérdida de acceso a sus cuentas, especialmente para quienes dependen de autenticadores de plataforma "Este dispositivo". Para mejorar el acceso a la autenticación, es recomendable proporcionar a los usuarios más de un factor de autenticación.

:::

## Configurar la gestión de passkeys \{#configure-passkeys-management}

Puedes usar la Account API para construir interfaces personalizadas de gestión de cuentas donde los usuarios puedan agregar, ver, renombrar y eliminar sus passkeys. Esto es útil para crear centros de cuentas personalizados y habilitar escenarios de respaldo entre dispositivos.

Para pasos de implementación detallados y endpoints de la API, consulta [Configuración de cuenta por Account API](/end-user-flows/account-settings/by-account-api#link-a-new-webauthn-passkey).

## Exportar passkeys \{#export-passkeys}

Puedes exportar las credenciales WebAuthn que Logto almacena para un usuario con la [Management API](/integrate-logto/interact-with-management-api). Usa la exportación para mover passkeys a otro sistema que sirva WebAuthn en el mismo dominio, para que los usuarios puedan seguir iniciando sesión con sus passkeys existentes.

Llama a [`GET /api/users/{userId}/mfa-verifications`](https://openapi.logto.io/operation/operation-listusermfaverifications) con el parámetro de consulta `includeWebAuthnCredentials` establecido en `true`:

```bash
curl "https://[tenant-id].logto.app/api/users/{userId}/mfa-verifications?includeWebAuthnCredentials=true" \
  -H 'authorization: Bearer <management-api-access-token>'
```

Cada entrada WebAuthn en la respuesta incluye la credencial almacenada:

```json
[
  {
    "id": "wv9m3k2x7p1q",
    "createdAt": "2026-10-12T08:31:24.000Z",
    "lastUsedAt": "2026-11-02T06:15:09.000Z",
    "type": "WebAuthn",
    "agent": "Mozilla/5.0 (Macintosh) ...",
    "name": "MacBook",
    "rpId": "auth.example.com",
    "credentialId": "Ab3dY0n9Kq2LwX8mR4sT1uV6zE",
    "publicKey": "pQECAyYgASFYIOrE5x...",
    "counter": 0,
    "transports": ["internal", "hybrid"]
  }
]
```

| Campo          | Descripción                                                                                                       |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| `credentialId` | El ID de la credencial WebAuthn, codificado en base64url.                                                         |
| `publicKey`    | La clave pública de la credencial en formato COSE, codificada en base64url.                                       |
| `counter`      | El último contador de firma (`signCount`) que Logto vio para la credencial. Muchos passkeys siempre reportan `0`. |
| `transports`   | Los transportes que el autenticador reportó al registrarse, como `internal`, `hybrid` o `usb`.                    |
| `rpId`         | El ID de la relying party (dominio) para el que se registró la credencial.                                        |
| `createdAt`    | Cuándo se registró la credencial.                                                                                 |
| `lastUsedAt`   | Cuándo se usó por última vez la credencial para verificar al usuario.                                             |

Sin `includeWebAuthnCredentials`, la respuesta omite `credentialId`, `publicKey`, `counter`, `transports` y `rpId`. Otros factores MFA se devuelven sin cambios. El parámetro también funciona con acceso de solo lectura a la Management API, porque un ID de credencial y una clave pública no pueden usarse para iniciar sesión.

Cuando importes las credenciales a otro sistema:

- **Mantén el mismo dominio.** Un passkey solo funciona en el ID de relying party para el que fue registrado. El otro sistema debe usar el `rpId` exportado como su ID de relying party WebAuthn, lo que significa servir el inicio de sesión en ese dominio, como tu [dominio personalizado](/logto-cloud/custom-domain).
- **Gestiona credenciales sin `rpId`.** Las credenciales registradas antes de que Logto comenzara a registrar el ID de relying party, y que no se han usado desde entonces, no tienen `rpId`. Están vinculadas al dominio que sirvió la página de inicio de sesión cuando se registraron, que puede no ser tu dominio personalizado actual.
- **Mapea el identificador de usuario.** Logto registra los bytes UTF-8 del ID de usuario de Logto como el `userHandle` de WebAuthn. Para el inicio de sesión con passkey, el autenticador devuelve este valor, por lo que el otro sistema debe mapearlo al usuario migrado.
- **Mantén el contador.** Almacena `counter` como el contador de firmas actual de la credencial, para que el otro sistema pueda seguir detectando autenticadores clonados.

## Flujos de configuración de passkey \{#passkey-setup-flows}

La especificación de Passkeys requiere que los usuarios hagan clic activamente en el botón de la página actual para iniciar el componente de autenticación. Esto significa que tanto en los flujos de configuración como de verificación, los usuarios deben ser redirigidos a la página de inicio para iniciar WebAuthn.

## Flujos de verificación de passkey \{#passkey-verification-flows}

Cuando los usuarios han configurado varios métodos MFA, incluidos passkeys, passkey se presentará como el método de verificación MFA recomendado en la primera pantalla debido a su mayor seguridad y conveniencia. Los usuarios pueden cambiar a otros métodos de verificación haciendo clic en "Probar otro método para verificar" abajo. Lee [Configurar MFA](/end-user-flows/mfa/configure-mfa#mfa-verification-flow) para saber más.

Si el usuario completa el inicio de sesión con [inicio de sesión con passkey](/end-user-flows/sign-up-and-sign-in/passkey-sign-in) en lugar de ingresar otro primer factor, Logto no pedirá un paso MFA adicional después. Esto se debe a que el propio passkey se trata como un factor MFA WebAuthn.

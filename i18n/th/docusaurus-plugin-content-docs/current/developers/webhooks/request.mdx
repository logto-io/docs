# คำขอ Webhooks (Webhooks request)

เมื่อเกิดเหตุการณ์ webhook ขึ้น Logto จะส่งคำขอ `POST` ไปยังทุก endpoint ที่สมัครรับเหตุการณ์นั้นไว้ แคตตาล็อกเหตุการณ์ทั้งหมดดูได้ที่ [เหตุการณ์ Webhooks](/developers/webhooks/webhooks-events); หน้านี้อธิบาย **รูปแบบของคำขอ** ที่ Logto ส่งให้

## ส่วนหัวของคำขอ (Request headers) \{#request-headers}

| Key                     | ปรับแต่งได้ | หมายเหตุ                                                                                                    |
| ----------------------- | ----------- | ----------------------------------------------------------------------------------------------------------- |
| user-agent              | ✅          | ค่าเริ่มต้นคือ `Logto (https://logto.io/)`.                                                                 |
| content-type            | ✅          | ค่าเริ่มต้นคือ `application/json`.                                                                          |
| logto-signature-sha-256 |             | ลายเซ็นของเนื้อหาใน request body ดู [การรักษาความปลอดภัยของ webhook](/developers/webhooks/secure-webhooks). |

ส่วนหัวที่สามารถปรับแต่งได้ สามารถ override ได้ผ่าน [secure webhook](/developers/webhooks/configure-webhooks/#secure-webhook)

## ภาพรวมของ request body (Request body overview) \{#request-body-overview}

body จะเป็นวัตถุ JSON รูปแบบที่แน่นอนขึ้นอยู่กับกลุ่มของเหตุการณ์ที่เกิดขึ้น:

| กลุ่ม (Family)    | เหตุการณ์ (Events)                                                                           | เมื่อเกิดเหตุการณ์                                                                                                                                               |
| ----------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **User flow**     | `PostRegister`, `PostSignIn`, `PostSignInAdaptiveMfaTriggered`, `PostResetPassword`          | ผู้ใช้ทำ flow สมัครสมาชิก, ลงชื่อเข้าใช้ หรือรีเซ็ตรหัสผ่านเสร็จสิ้น หรือเกิด [Adaptive MFA](/end-user-flows/mfa/adaptive-mfa) ระหว่าง sign-in บน Experience API |
| **Data mutation** | `User.*`, `Role.*`, `Scope.*`, `Organization.*`, `OrganizationRole.*`, `OrganizationScope.*` | โมเดลข้อมูลถูกเปลี่ยนแปลงโดย Management API หรือ user flow บน Experience API                                                                                     |
| **Exception**     | `Identifier.Lockout`, `Message.RateLimited`, `Grant.LimitExceeded`                           | เหตุการณ์ด้านความปลอดภัย เช่น บัญชีถูกล็อกหลังจากพยายามยืนยันตัวตนผิดหลายครั้ง                                                                                   |

ทุกกลุ่มจะมี [ฟิลด์ร่วม](#common-fields) อยู่เสมอ จากนั้นแต่ละกลุ่มจะมีฟิลด์ context เฉพาะของตัวเองและ payload เฉพาะเหตุการณ์

### ฟิลด์ร่วม (Common fields) \{#common-fields}

มีในทุกการส่ง ไม่ว่ากลุ่มใด:

| Field      | Type     | Optional | หมายเหตุ                                                                                                                                                                                                                                |
| ---------- | -------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| hookId     | `string` |          | รหัสการตั้งค่า webhook ใน Logto                                                                                                                                                                                                         |
| deliveryId | `string` |          | รหัสของการส่งนี้ เฉพาะแต่ละ webhook และ event และคงอยู่ระหว่าง [การ retry อัตโนมัติ](/developers/webhooks/configure-webhooks#monitor-webhook-health-status) ของ request เดียวกัน ดู [การ deduplicate การส่ง](#deduplicating-deliveries) |
| event      | `string` |          | เหตุการณ์ที่ทำให้เกิดการส่งนี้                                                                                                                                                                                                          |
| createdAt  | `string` |          | เวลาสร้าง payload ในรูปแบบ ISO 8601                                                                                                                                                                                                     |
| userAgent  | `string` | ✅       | user-agent ของ request ที่เป็นตัวกระตุ้นเหตุการณ์นี้                                                                                                                                                                                    |

แต่ละกลุ่มยังมี IP address ของ request ที่เป็นตัวกระตุ้นเหตุการณ์ โดยใช้ชื่อฟิลด์ `userIp` สำหรับ user-flow events และ `ip` สำหรับ data-mutation และ exception events ความหมายเหมือนกัน ต่างกันเพื่อความเข้ากันได้กับเวอร์ชันเก่า

### การ deduplicate การส่ง (Deduplicating deliveries) \{#deduplicating-deliveries}

การส่งหนึ่งครั้งอาจถึง endpoint ของคุณมากกว่าหนึ่งครั้ง: Logto จะ [retry](/developers/webhooks/configure-webhooks#monitor-webhook-health-status) คำขอที่ตอบกลับด้วยสถานะ 500 ขึ้นไป ดังนั้น request ที่ endpoint ของคุณประมวลผลแล้วแต่ยังตอบกลับด้วย 5xx (เช่น gateway ข้างหน้าตอบ 504 เพราะ handler ช้า) จะถูกส่งซ้ำ ทุกครั้งที่ส่งของ delivery เดียวกันจะมี `deliveryId` เดิม ในขณะที่ event ใหม่ หรือ event เดียวกันที่ส่งไป webhook อื่น จะได้ id ใหม่ ให้บันทึก `deliveryId` ของ payload ที่คุณประมวลผลแล้ว และข้าม payload ที่ id ซ้ำ

`deliveryId` ยังเป็น id ของ log entry ที่บันทึกการส่งนี้ด้วย ดังนั้นค่าที่รายงานโดย service ของคุณสามารถเปิดดูจาก recent requests ของ webhook ใน Console หรือดึงด้วย `GET /api/logs/:id`

[test payload](/developers/webhooks/configure-webhooks#test-webhook) ก็มี `deliveryId` เช่นกัน ดังนั้น handler เดียวกันสามารถประมวลผลได้ แม้ว่า test request จะไม่ถูก log

## Payload ของเหตุการณ์ user flow (User flow event payloads) \{#user-flow-event-payloads}

**เหตุการณ์:** `PostRegister`, `PostSignIn`, `PostSignInAdaptiveMfaTriggered`, `PostResetPassword`

เกิดขึ้นเมื่อผู้ใช้ทำ flow สมัครสมาชิก, ลงชื่อเข้าใช้ หรือรีเซ็ตรหัสผ่านที่จัดการโดย Experience API เสร็จสิ้น หรือเมื่อ [Adaptive MFA](/end-user-flows/mfa/adaptive-mfa) กระตุ้น MFA challenge ระหว่าง sign-in (`PostSignInAdaptiveMfaTriggered`) นอกจาก [ฟิลด์ร่วม](#common-fields) แล้ว body จะมี:

| Field             | Type                                         | Optional | หมายเหตุ                                                                                                                                                                           |
| ----------------- | -------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| interactionEvent  | `'SignIn' \| 'Register' \| 'ForgotPassword'` |          | ประเภทเหตุการณ์ user-flow (`'SignIn'` สำหรับ `PostSignIn` และ `PostSignInAdaptiveMfaTriggered`; `'Register'` สำหรับ `PostRegister`; `'ForgotPassword'` สำหรับ `PostResetPassword`) |
| sessionId         | `string`                                     | ✅       | Session ID (ไม่ใช่ Interaction ID) สำหรับ event นี้ ถ้ามี                                                                                                                          |
| userIp            | `string`                                     | ✅       | IP address ของ request ที่เป็นตัวกระตุ้นเหตุการณ์                                                                                                                                  |
| userId            | `string`                                     | ✅       | User ID ที่เกี่ยวข้องกับ event นี้ ถ้ามี                                                                                                                                           |
| user              | `UserEntity`                                 | ✅       | user entity ที่เกี่ยวข้องกับ event นี้ ถ้ามี                                                                                                                                       |
| applicationId     | `string`                                     | ✅       | Application ID ที่เกี่ยวข้องกับ event นี้ ถ้ามี                                                                                                                                    |
| application       | `ApplicationEntity`                          | ✅       | application entity ที่เกี่ยวข้องกับ event นี้ ถ้ามี                                                                                                                                |
| adaptiveMfaResult | `AdaptiveMfaResult`                          | ✅       | มีเฉพาะใน delivery `PostSignInAdaptiveMfaTriggered` จริง (ไม่มีใน test payload ของ Console) ดู [PostSignInAdaptiveMfaTriggered payload](#postsigninadaptivemfatriggered-payload)   |

#### PostSignInAdaptiveMfaTriggered payload \{#postsigninadaptivemfatriggered-payload}

เมื่อ [Adaptive MFA](/end-user-flows/mfa/adaptive-mfa) กระตุ้น MFA challenge ระหว่าง sign-in Logto จะส่ง `PostSignInAdaptiveMfaTriggered` หนึ่งครั้งต่อ flow sign-in — แม้ก่อนที่ผู้ใช้จะยืนยัน MFA เสร็จ (`PostSignIn` จะถูกส่งหลัง sign-in เสร็จเท่านั้น) body จะมี `adaptiveMfaResult`:

```tsx
type AdaptiveMfaResult = {
  requiresMfa: boolean;
  triggeredRules: Array<{
    rule: 'new_country' | 'geo_velocity' | 'long_inactivity' | 'untrusted_ip';
    details: Record<string, unknown>;
  }>;
};
```

## Payload ของเหตุการณ์ data mutation (Data mutation event payloads) \{#data-mutation-event-payloads}

**เหตุการณ์:** ทุก event ภายใต้ `User.*`, `Role.*`, `Scope.*`, `Organization.*`, `OrganizationRole.*`, `OrganizationScope.*` ดู [เหตุการณ์ Webhooks → Data mutation webhook events](/developers/webhooks/webhooks-events#data-mutation-hook-events) สำหรับแคตตาล็อกเต็ม

body จะมีเสมอ:

- [ฟิลด์ร่วม](#common-fields)
- ฟิลด์ `ip` คือ IP address ของ request ที่เป็นตัวกระตุ้น (optional, มีเมื่อทราบ)
- **API context** อธิบายว่าเปลี่ยนแปลงนี้เกิดจากอะไร context มี 2 แบบขึ้นกับแหล่งที่มา:
  - [Experience API context](#experience-api-context-fields) เมื่อเปลี่ยนแปลงมาจาก user-facing flow
  - [Management API context](#management-api-context-fields) เมื่อเปลี่ยนแปลงมาจาก Management API โดยตรง
- **payload เฉพาะ event**: entity ที่ได้รับผลกระทบใน `data` และ (สำหรับบาง event) ฟิลด์ระดับบนเพิ่มเติม ดู [event-specific data payloads](#event-specific-data-payloads)

### ฟิลด์ context ของ Experience API (Experience API context fields) \{#experience-api-context-fields}

มีเมื่อเปลี่ยนแปลงเกิดจาก user-facing flow บน Experience API เช่น `User.Created` ระหว่างสมัครสมาชิก หรือ `User.Data.Updated` ระหว่างอัปเดตโปรไฟล์

| Field            | Type                                         | Optional | หมายเหตุ                                                                                     |
| ---------------- | -------------------------------------------- | -------- | -------------------------------------------------------------------------------------------- |
| interactionEvent | `'SignIn' \| 'Register' \| 'ForgotPassword'` | ✅       | ประเภทเหตุการณ์ user-flow ที่ทำให้เกิดการเปลี่ยนแปลง ชื่อฟิลด์ยังคงใช้ "interaction" ตามเดิม |
| sessionId        | `string`                                     | ✅       | Session ID (ไม่ใช่ Interaction ID) สำหรับ event นี้ ถ้ามี                                    |
| applicationId    | `string`                                     | ✅       | Application ID ถ้ามี                                                                         |
| application      | `ApplicationEntity`                          | ✅       | application entity ถ้ามี                                                                     |

| matchedRoute | `string` | ✅       | koa matched route Logto ใช้ฟิลด์นี้จับคู่กับ webhook event filter ที่เปิดใช้งาน |

### payload ข้อมูลเฉพาะ event (Event-specific data payloads) \{#event-specific-data-payloads}

ทุก data-mutation event จะมีฟิลด์ระดับบน `data` ที่บรรจุ entity ที่ได้รับผลกระทบ หรือ `null` เมื่อเปลี่ยนแปลงไม่สามารถสรุปเป็น entity เดียวได้ (เช่น delete และ membership events) บาง event จะมีฟิลด์ระดับบนเพิ่มเติมนอกเหนือจาก `data` เช่น `Organization.Membership.Updated` ซึ่งอธิบายไว้ด้านล่าง

#### เหตุการณ์ผู้ใช้ (User events) \{#user-events}

| User.Data.Updated | data  | `UserEntity` |          | user entity ที่ถูกอัปเดต |

##### Organization.Membership.Updated payload \{#organizationmembershipupdated-payload}

นอกจาก [ฟิลด์ร่วม](#common-fields) และฟิลด์ context API ที่เกี่ยวข้องกับแหล่งที่มาการกระตุ้น ([Management API context](#management-api-context-fields) สำหรับ Management API, [Experience API context](#experience-api-context-fields) สำหรับ just-in-time provisioning) เหตุการณ์ `Organization.Membership.Updated` จะมี `organizationId` และ delta array (optional) ระดับบน (อยู่ข้างๆ `event`, `createdAt` ฯลฯ **ไม่ใช่** ใน `data` ซึ่งจะเป็น `null` เสมอสำหรับ event นี้)

| Field                 | Type       | Optional | หมายเหตุ                                                                                                        |
| --------------------- | ---------- | -------- | --------------------------------------------------------------------------------------------------------------- |
| organizationId        | `string`   |          | องค์กรที่ membership เปลี่ยนแปลง                                                                                |
| addedUserIds          | `string[]` | ✅       | User ID ที่ถูกเพิ่มใหม่โดย trigger นี้ ไม่มีเมื่อไม่มีการเพิ่ม user หรือ trigger ไม่กระทบ membership user       |
| removedUserIds        | `string[]` | ✅       | User ID ที่ถูกลบโดย trigger นี้ ไม่มีเมื่อไม่มีการลบ user                                                       |
| addedApplicationIds   | `string[]` | ✅       | Application ID ที่ถูกเพิ่มใหม่ ไม่มีเมื่อไม่มีการเพิ่ม application หรือ trigger ไม่กระทบ membership application |
| removedApplicationIds | `string[]` | ✅       | Application ID ที่ถูกลบ ไม่มีเมื่อไม่มีการลบ application                                                        |

delta array ทั้งสี่นี้ **optional และ additive**: ไม่เปลี่ยนรูปแบบ payload เดิมสำหรับ consumer ที่ไม่ได้คาดหวัง และฟิลด์ `data: null` แบบเดิมยังคงส่งเหมือนเดิม

###### trigger และ delta field ที่อาจเกิดขึ้น \{#membership-triggers}

| Trigger                                                     | delta field ที่อาจมี                           |
| ----------------------------------------------------------- | ---------------------------------------------- |
| `POST /organizations/:id/users`                             | `addedUserIds`                                 |
| `PUT /organizations/:id/users`                              | `addedUserIds`, `removedUserIds`               |
| `DELETE /organizations/:id/users/:userId`                   | `removedUserIds`                               |
| `POST /organizations/:id/applications`                      | `addedApplicationIds`                          |
| `PUT /organizations/:id/applications`                       | `addedApplicationIds`, `removedApplicationIds` |
| `DELETE /organizations/:id/applications/:applicationId`     | `removedApplicationIds`                        |
| `PUT /organization-invitations/:id/status` (`Accepted`)     | `addedUserIds`                                 |
| Just-in-time provisioning เมื่อเพิ่ม user เข้าสู่องค์กรใหม่ | `addedUserIds`                                 |

###### delta ว่างจะถูกละเว้น (Empty deltas are omitted) \{#empty-deltas-are-omitted}

delta array ที่ว่างจะ **ถูกละเว้นทั้งหมด** จาก payload เช่น `PUT /organizations/:id/users` ที่แทนที่ชุดสมาชิกด้วยชุดเดิมจะไม่เปลี่ยนแปลงจริง และ payload จะเหลือแค่ `{ organizationId }` โดยไม่มี delta field ทั้งสี่ เช่นเดียวกับการเพิ่มสมาชิกเดิมซ้ำ หรือการรับคำเชิญซ้ำโดย user ที่เป็นสมาชิกอยู่แล้ว

**consumer ต้องถือว่าฟิลด์ที่ขาดหายคือ "ไม่มีการเปลี่ยนแปลงฝั่งนั้น" ไม่ใช่ "เปลี่ยนแปลงว่าง"**

###### จำกัดจำนวนต่อ array (Per-array cap; silent truncation) \{#membership-delta-cap}

แต่ละ delta array จำกัดที่ **5000 รายการ** เมื่อ Management API call เดียวเพิ่มหรือลบ user (หรือ application) เกิน 5000 รายการ array ที่เกี่ยวข้องจะถูกตัดเหลือ 5000 รายการแรก **ไม่มี marker ใน payload** ว่าถูกตัด

หากแอปของคุณมี bulk operation ที่อาจกระทบสมาชิกเกิน 5000 รายการ ให้ถือว่า array ที่มี 5000 รายการคือสัญญาณให้ sync membership ผ่าน Management API:

- `GET /organizations/:id/users`: สมาชิก user ทั้งหมด
- `GET /organizations/:id/applications`: สมาชิก application ทั้งหมด

รูปแบบนี้เหมือนกับ event `push` ของ GitHub ที่จำกัด `commits` ไว้ 20 รายการและแนะนำให้ consumer ไปดู compare API สำหรับรายการเต็ม

###### ข้าม event ที่ไม่มีการเปลี่ยนแปลง (Skipping no-op events) \{#skipping-no-op-events}

เพื่อข้าม delivery ที่ไม่มีการเปลี่ยนแปลง (event ที่ไม่มี delta field) ฝั่ง consumer ให้ filter ด้วยการมี delta array:

```ts
if (
  payload.addedUserIds?.length ||
  payload.removedUserIds?.length ||
  payload.addedApplicationIds?.length ||
  payload.removedApplicationIds?.length
) {
  // มีการเปลี่ยนแปลง membership จริง ให้ handle
}
```

`?.length` จะเป็น falsy ทั้งกรณี `undefined` และ `[]` ดังนั้น predicate นี้ robust ไม่ว่าฟิลด์จะขาดหายหรือ (ในอนาคต) ถูกส่งเป็น array ว่าง

**เพิ่ม application (`POST /organizations/:id/applications`):**

```json
  "event": "Organization.Membership.Updated",

```

**เพิ่มสมาชิกเดิมซ้ำ, no-op `PUT` หรือรับคำเชิญซ้ำโดยสมาชิกเดิม (ไม่มีการเปลี่ยนแปลงจริง):**

```json
{
```

## Payload ของเหตุการณ์ exception (Exception event payloads) \{#exception-event-payloads}

**เหตุการณ์:** `Identifier.Lockout`, `Message.RateLimited`, `Grant.LimitExceeded`

เกิดขึ้นเมื่อมีเหตุการณ์ด้านความปลอดภัย เช่น บัญชีถูกล็อกหลังจากพยายามยืนยันตัวตนผิดหลายครั้ง หรือ grant ถูกยกเลิกเพราะเกินขีดจำกัด concurrent-device ของแอป

ทุก exception event จะมี [ฟิลด์ร่วม](#common-fields) และฟิลด์ `ip` (รูปแบบเดียวกับ data-mutation events) ฟิลด์ที่เหลือขึ้นกับ event

### Identifier.Lockout \{#identifierlockout-payload}

มาจาก user-facing flow ดังนั้น body จะมี [Experience API context fields](#experience-api-context-fields) ด้วย และ:

```tsx
enum SignInIdentifier {
  Email = 'email',
  Phone = 'phone',
  Username = 'username',
}
```

| Field | Type               | Optional | หมายเหตุ                                                    |
| ----- | ------------------ | -------- | ----------------------------------------------------------- |
| type  | `SignInIdentifier` |          | ประเภท identifier ของผู้ใช้ เช่น email, phone หรือ username |
| value | `string`           |          | ค่า identifier ของผู้ใช้ที่ทำให้เกิด lockout                |

### Message.RateLimited \{#messageratelimited-payload}

มาจาก user-facing flow ดังนั้น body จะมี [Experience API context fields](#experience-api-context-fields) ด้วย และ:

| Field     | Type     | Optional | หมายเหตุ                                                                  |
| --------- | -------- | -------- | ------------------------------------------------------------------------- |
| action    | `string` |          | action ที่ถูก rate-limit เช่น `VerificationCodeSend`                      |
| recipient | `string` |          | email หรือเบอร์โทรศัพท์ที่ชน [send rate limit](/security/send-rate-limit) |

### Grant.LimitExceeded \{#grantlimitexceeded-payload}

เกิดขึ้นเมื่อการอนุญาต (authorization) สำเร็จทำให้ผู้ใช้เกิน [จำนวนอุปกรณ์ที่ยืนยันตัวตนพร้อมกันสูงสุดต่อแอป](/sessions/session-configs#max-concurrent-authenticated-devices-per-app) (`maxAllowedGrants`) และ Logto เพิกถอน grant ที่เก่าที่สุดของแอปนั้น

event นี้ถูกส่งจาก OIDC authorization endpoint ไม่ใช่ Experience API ดังนั้นจะ **ไม่มี** `interactionEvent` หรือ `sessionId` นอกจากฟิลด์ร่วมและ `ip` body จะมี:

| Field                         | Type                | Optional | หมายเหตุ                                                    |
| ----------------------------- | ------------------- | -------- | ----------------------------------------------------------- |
| userId                        | `string`            |          | ผู้ใช้ที่ grant ถูกเพิกถอน                                  |
| applicationId                 | `string`            |          | แอปที่เกินขีดจำกัด `maxAllowedGrants`                       |
| application                   | `ApplicationEntity` | ✅       | application entity ไม่มีถ้าไม่สามารถ resolve แอปได้ขณะส่ง   |
| maxAllowedGrants              | `number`            |          | ขีดจำกัดที่ตั้งไว้บนแอปขณะเกิด event                        |
| preRevocationActiveGrantCount | `number`            |          | จำนวน grant ที่ผู้ใช้ถืออยู่ก่อนเพิกถอน (รวมอันที่เพิ่งออก) |
| revokedGrantIds               | `string[]`          |          | ID ของ grant ที่ถูกเพิกถอนจริง (เรียงจากเก่าสุด)            |

ตัวอย่าง payload:

```json
{
  "hookId": "hook_abc",
  "deliveryId": "3nfp8xk1q2z7",
  "event": "Grant.LimitExceeded",
  "createdAt": "2024-01-01T00:00:00.000Z",
  "ip": "192.168.0.1",
  "userAgent": "Mozilla/5.0",
  "userId": "u_001",
  "applicationId": "app_xyz",
  "application": {
    "id": "app_xyz",
    "type": "SPA",
    "name": "My app",
    "description": "My app description"
  },
  "maxAllowedGrants": 2,
  "preRevocationActiveGrantCount": 3,
  "revokedGrantIds": ["grant_001"]
}
```

หมายเหตุการส่ง:

- บันทึก grant ที่ถูกเพิกถอนจะถูกลบเป็นส่วนหนึ่งของการเพิกถอน ดังนั้น ID ใน `revokedGrantIds` จะไม่สามารถค้นหาได้ผ่าน endpoint รายการ grant หรือ Console — endpoint เหล่านั้นแสดงเฉพาะ grant **ที่ยัง active** เท่านั้น ให้ถือ payload นี้เป็นบันทึก และเก็บ ID ฝั่งคุณหากต้องใช้ในอนาคต
- event จะถูกส่งเฉพาะเมื่อมี grant **ถูกเพิกถอนจริง** การอนุญาตที่ยังไม่เกินขีดจำกัดจะไม่เกิด event
- จะถูกส่งทุกครั้งที่การอนุญาตเกินขีดจำกัด ดังนั้นผู้ใช้ที่ sign-in จากอุปกรณ์เกินจำนวนที่อนุญาตจะเกิด event หนึ่งต่อการเพิกถอนแต่ละครั้ง
- การ dispatch เป็นแบบ fire-and-forget: endpoint ที่ช้าหรือ error จะไม่บล็อกหรือทำให้การอนุญาตของผู้ใช้ล้มเหลว การส่งที่ล้มเหลวจะถูกบันทึกใน audit log เช่นเดียวกับ webhook อื่นๆ

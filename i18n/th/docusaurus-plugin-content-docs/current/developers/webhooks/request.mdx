# คำขอ Webhooks (Webhooks request)

เมื่อเกิดเหตุการณ์ webhook ขึ้น Logto จะส่งคำขอ `POST` ไปยังทุก endpoint ที่สมัครรับเหตุการณ์นั้นไว้ แคตตาล็อกเหตุการณ์ทั้งหมดดูได้ที่ [เหตุการณ์ Webhooks](/developers/webhooks/webhooks-events); หน้านี้จะอธิบาย **รูปแบบของคำขอ** ที่ Logto ส่งให้

## ส่วนหัวของคำขอ (Request headers) \{#request-headers}

| Key                     | ปรับแต่งได้ | หมายเหตุ                                                                                                        |
| ----------------------- | ----------- | --------------------------------------------------------------------------------------------------------------- |
| user-agent              | ✅          | ค่าเริ่มต้นคือ `Logto (https://logto.io/)`.                                                                     |
| content-type            | ✅          | ค่าเริ่มต้นคือ `application/json`.                                                                              |
| logto-signature-sha-256 |             | ลายเซ็นของเนื้อหาใน request body ดู [การรักษาความปลอดภัย webhook ของคุณ](/developers/webhooks/secure-webhooks). |

ส่วนหัวที่สามารถปรับแต่งได้ สามารถ override ได้ผ่านการตั้งค่า [secure webhook](/developers/webhooks/configure-webhooks/#secure-webhook)

## ภาพรวมของเนื้อหาในคำขอ (Request body overview) \{#request-body-overview}

เนื้อหา (body) เป็นอ็อบเจกต์ JSON รูปแบบที่แน่นอนขึ้นอยู่กับกลุ่มของเหตุการณ์ที่เกิดขึ้น:

| กลุ่ม (Family)    | เหตุการณ์ (Events)                                                                           | เมื่อเกิดเหตุการณ์ (When it fires)                                                   |
| ----------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **User flow**     | `PostRegister`, `PostSignIn`, `PostResetPassword`                                            | ผู้ใช้ดำเนินการลงทะเบียน, ลงชื่อเข้าใช้, หรือรีเซ็ตรหัสผ่านสำเร็จผ่าน Experience API |
| **Data mutation** | `User.*`, `Role.*`, `Scope.*`, `Organization.*`, `OrganizationRole.*`, `OrganizationScope.*` | โมเดลข้อมูลถูกเปลี่ยนแปลงโดย Management API หรือ user flow บน Experience API         |
| **Exception**     | `Identifier.Lockout`                                                                         | เหตุการณ์ด้านความปลอดภัย เช่น บัญชีถูกล็อกหลังจากพยายามยืนยันตัวตนล้มเหลวหลายครั้ง   |

ทุกกลุ่มจะมี [ฟิลด์ร่วม (common fields)](#common-fields) ชุดเล็ก ๆ จากนั้นแต่ละกลุ่มจะเพิ่มฟิลด์ context ของคำขอและ payload เฉพาะเหตุการณ์ของตัวเอง

### ฟิลด์ร่วม (Common fields) \{#common-fields}

มีอยู่ในทุกการส่ง ไม่ว่ากลุ่มใด:

| ฟิลด์     | ชนิด     | Optional | หมายเหตุ                                |
| --------- | -------- | -------- | --------------------------------------- |
| hookId    | `string` |          | ตัวระบุการตั้งค่า webhook ใน Logto      |
| event     | `string` |          | เหตุการณ์ที่ทริกเกอร์การส่งนี้          |
| createdAt | `string` |          | เวลาสร้าง payload ในรูปแบบ ISO 8601     |
| userAgent | `string` | ✅       | user-agent ของคำขอที่ทริกเกอร์เหตุการณ์ |

แต่ละกลุ่มยังมี IP address ของคำขอที่ทริกเกอร์เหตุการณ์ โดยใช้ชื่อฟิลด์ `userIp` สำหรับ user-flow events และ `ip` สำหรับ data-mutation และ exception events ความหมายเหมือนกัน ชื่อที่ต่างกันเพื่อความเข้ากันได้ย้อนหลัง

## Payload ของเหตุการณ์ User flow \{#user-flow-event-payloads}

**เหตุการณ์:** `PostRegister`, `PostSignIn`, `PostResetPassword`

ทริกเกอร์เมื่อผู้ใช้ดำเนินการลงทะเบียน, ลงชื่อเข้าใช้, หรือรีเซ็ตรหัสผ่านสำเร็จผ่าน Experience API นอกจาก [ฟิลด์ร่วม (common fields)](#common-fields) แล้ว body จะมี:

| ฟิลด์            | ชนิด                                         | Optional | หมายเหตุ                                                                                                                      |
| ---------------- | -------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| interactionEvent | `'SignIn' \| 'Register' \| 'ForgotPassword'` |          | ประเภทเหตุการณ์ user-flow แมปกับ `PostSignIn` / `PostRegister` / `PostResetPassword` ตามลำดับ ชื่อฟิลด์ยังคงใช้ "interaction" |
| sessionId        | `string`                                     | ✅       | Session ID (ไม่ใช่ Interaction ID) ของเหตุการณ์นี้ ถ้ามี                                                                      |
| userIp           | `string`                                     | ✅       | IP address ของคำขอที่ทริกเกอร์เหตุการณ์                                                                                       |
| userId           | `string`                                     | ✅       | User ID ที่เกี่ยวข้องกับเหตุการณ์นี้ ถ้ามี                                                                                    |
| user             | `UserEntity`                                 | ✅       | user entity ที่เกี่ยวข้องกับเหตุการณ์นี้ ถ้ามี                                                                                |
| applicationId    | `string`                                     | ✅       | Application ID ที่เกี่ยวข้องกับเหตุการณ์นี้ ถ้ามี                                                                             |
| application      | `ApplicationEntity`                          | ✅       | application entity ที่เกี่ยวข้องกับเหตุการณ์นี้ ถ้ามี                                                                         |

## Payload ของเหตุการณ์ Data mutation \{#data-mutation-event-payloads}

**เหตุการณ์:** ทุกเหตุการณ์ภายใต้ `User.*`, `Role.*`, `Scope.*`, `Organization.*`, `OrganizationRole.*`, `OrganizationScope.*` ดู [เหตุการณ์ Webhooks → Data mutation webhook events](/developers/webhooks/webhooks-events#data-mutation-hook-events) สำหรับแคตตาล็อกเต็ม

body จะมีเสมอ:

- [ฟิลด์ร่วม (common fields)](#common-fields)
- ฟิลด์ `ip` คือ IP address ของคำขอที่ทริกเกอร์เหตุการณ์ (optional, มีเมื่อทราบ)
- **API context** อธิบายว่าการเปลี่ยนแปลงถูกทริกเกอร์อย่างไร context มี 2 แบบขึ้นกับแหล่งที่มา:
  - [Experience API context](#experience-api-context-fields) เมื่อเปลี่ยนแปลงมาจาก user-facing flow
  - [Management API context](#management-api-context-fields) เมื่อเปลี่ยนแปลงมาจากการเรียก Management API โดยตรง
- **payload เฉพาะเหตุการณ์**: entity ที่ได้รับผลกระทบใน `data` และ (สำหรับบางเหตุการณ์) ฟิลด์ระดับบนเพิ่มเติม ดู [payload ข้อมูลเฉพาะเหตุการณ์](#event-specific-data-payloads)

### ฟิลด์ Experience API context \{#experience-api-context-fields}

มีเมื่อการเปลี่ยนแปลงถูกทริกเกอร์โดย user-facing flow บน Experience API เช่น `User.Created` ระหว่างลงทะเบียน หรือ `User.Data.Updated` ระหว่างอัปเดตโปรไฟล์

| ฟิลด์            | ชนิด                                         | Optional | หมายเหตุ                                                                             |
| ---------------- | -------------------------------------------- | -------- | ------------------------------------------------------------------------------------ |
| interactionEvent | `'SignIn' \| 'Register' \| 'ForgotPassword'` | ✅       | ประเภทเหตุการณ์ user-flow ที่ทำให้เกิดการเปลี่ยนแปลง ชื่อฟิลด์ยังคงใช้ "interaction" |
| sessionId        | `string`                                     | ✅       | Session ID (ไม่ใช่ Interaction ID) ของเหตุการณ์นี้ ถ้ามี                             |
| applicationId    | `string`                                     | ✅       | Application ID ถ้ามี                                                                 |
| application      | `ApplicationEntity`                          | ✅       | application entity ถ้ามี                                                             |

### ฟิลด์ Management API context \{#management-api-context-fields}

มีเมื่อการเปลี่ยนแปลงถูกทริกเกอร์โดยการเรียก Management API

| ฟิลด์        | ชนิด     | Optional | หมายเหตุ                                                             |
| ------------ | -------- | -------- | -------------------------------------------------------------------- |

| method       | `string` | ✅       | HTTP method ของ API call                                             |
| status       | `number` | ✅       | รหัสสถานะตอบกลับของ API call                                         |
| params       | `object` | ✅       | koa path params ของ API call                                         |
| matchedRoute | `string` | ✅       | koa matched route Logto ใช้ฟิลด์นี้เพื่อจับคู่ webhook event filters |

### Payload ข้อมูลเฉพาะเหตุการณ์ (Event-specific data payloads) \{#event-specific-data-payloads}

ทุกเหตุการณ์ data-mutation จะมีฟิลด์ระดับบนสุดชื่อ `data` ที่บรรจุ entity ที่ได้รับผลกระทบ หรือ `null` เมื่อไม่สามารถสรุปเป็น entity เดียวได้ (เช่น เหตุการณ์ลบและ membership) บางเหตุการณ์จะมีฟิลด์ระดับบนเพิ่มเติมนอกเหนือจาก `data` เช่น `Organization.Membership.Updated` อธิบายไว้ด้านล่าง

##### Payload Organization.Membership.Updated \{#organizationmembershipupdated-payload}

นอกจาก [ฟิลด์ร่วม (common fields)](#common-fields) และฟิลด์ API-context ที่เกี่ยวข้องกับแหล่งที่มาของ trigger ([Management API context](#management-api-context-fields) สำหรับ Management API, [Experience API context](#experience-api-context-fields) สำหรับ just-in-time provisioning) เหตุการณ์ `Organization.Membership.Updated` จะมี `organizationId` และ delta array ระดับบน (อยู่ข้าง ๆ `event`, `createdAt` ฯลฯ **ไม่ใช่** ใน `data` ซึ่งจะเป็น `null` เสมอสำหรับ event นี้)

| ฟิลด์                 | ชนิด       | Optional | หมายเหตุ                                                                                                   |
| --------------------- | ---------- | -------- | ---------------------------------------------------------------------------------------------------------- |
| organizationId        | `string`   |          | องค์กรที่ membership มีการเปลี่ยนแปลง                                                                      |
| addedUserIds          | `string[]` | ✅       | User ID ที่ถูกเพิ่มใหม่โดย trigger นี้ ไม่แสดงเมื่อไม่มีการเพิ่ม หรือ trigger ไม่เกี่ยวกับ user membership |
| removedUserIds        | `string[]` | ✅       | User ID ที่ถูกลบโดย trigger นี้ ไม่แสดงเมื่อไม่มีการลบ                                                     |
| addedApplicationIds   | `string[]` | ✅       | Application ID ที่ถูกเพิ่มใหม่ ไม่แสดงเมื่อไม่มีการเพิ่ม หรือ trigger ไม่เกี่ยวกับ application membership  |
| removedApplicationIds | `string[]` | ✅       | Application ID ที่ถูกลบ ไม่แสดงเมื่อไม่มีการลบ                                                             |

delta array ทั้ง 4 นี้ **เป็น optional และ additive**: ไม่เปลี่ยนรูปแบบ payload เดิมสำหรับ consumer ที่ไม่ได้คาดหวัง และฟิลด์ `data: null` แบบเดิมยังคงถูกส่งเหมือนเดิม

###### Trigger และ delta field ที่อาจเกิดขึ้น \{#membership-triggers}

| Trigger                                                   | delta field ที่อาจเกิดขึ้น                     |
| --------------------------------------------------------- | ---------------------------------------------- |
| `POST /organizations/:id/users`                           | `addedUserIds`                                 |
| `PUT /organizations/:id/users`                            | `addedUserIds`, `removedUserIds`               |
| `DELETE /organizations/:id/users/:userId`                 | `removedUserIds`                               |
| `POST /organizations/:id/applications`                    | `addedApplicationIds`                          |
| `PUT /organizations/:id/applications`                     | `addedApplicationIds`, `removedApplicationIds` |
| `DELETE /organizations/:id/applications/:applicationId`   | `removedApplicationIds`                        |
| `PUT /organization-invitations/:id/status` (`Accepted`)   | `addedUserIds`                                 |
| Just-in-time provisioning เมื่อเพิ่ม user ไปยังองค์กรใหม่ | `addedUserIds`                                 |

###### delta array ว่างจะถูกละเว้น (absent ≠ empty change) \{#empty-deltas-are-omitted}

delta array ที่ว่าง **จะถูกละเว้นโดยสมบูรณ์** เช่น `PUT /organizations/:id/users` ที่แทนที่สมาชิกด้วยชุดเดิม จะไม่มีการเปลี่ยนแปลงจริง payload จะเหลือแค่ `{ organizationId }` โดยไม่มี delta field ทั้ง 4 เช่นเดียวกับการเพิ่มสมาชิกซ้ำหรือรับคำเชิญซ้ำ

**Consumer ต้องถือว่าฟิลด์ที่หายไปคือ "ไม่มีการเปลี่ยนแปลงด้านนั้น" ไม่ใช่ "เปลี่ยนแปลงเป็นค่าว่าง"**

###### จำกัดจำนวนต่อ array (silent truncation) \{#membership-delta-cap}

แต่ละ delta array จำกัดที่ **5000 รายการ** หาก Management API call เพิ่มหรือลบผู้ใช้ (หรือแอป) เกิน 5000 รายการในครั้งเดียว delta array ที่เกี่ยวข้องจะถูกตัดเหลือ 5000 รายการแรก **ไม่มี marker ใน payload** ว่าถูกตัด

หากแอปของคุณมี bulk operation ที่อาจกระทบสมาชิกเกิน 5000 คนในครั้งเดียว ให้ถือว่า array ที่มี 5000 รายการคือสัญญาณให้ sync สมาชิก authoritative ผ่าน Management API:

- `GET /organizations/:id/users`: สมาชิกผู้ใช้ทั้งหมด
- `GET /organizations/:id/applications`: สมาชิกแอปทั้งหมด

รูปแบบนี้เหมือนกับ event `push` ของ GitHub ที่จำกัด `commits` ไว้ 20 รายการและแนะนำให้ consumer ไปดู compare API สำหรับรายการเต็ม

###### ข้าม event ที่ไม่มีการเปลี่ยนแปลง (no-op) \{#skipping-no-op-events}

เพื่อข้าม event ที่ไม่มีการเปลี่ยนแปลง (ไม่มี delta field) ในฝั่ง consumer ให้ filter ด้วยการมีอยู่ของ delta array:

```ts
if (
  payload.addedUserIds?.length ||
  payload.removedUserIds?.length ||
  payload.addedApplicationIds?.length ||
  payload.removedApplicationIds?.length
) {
  // มีการเปลี่ยนแปลง membership จริง ให้จัดการ
}
```

`?.length` จะเป็น falsy ทั้งกรณี `undefined` และ `[]` ดังนั้น predicate นี้ robust ไม่ว่าฟิลด์จะหายไปหรือ (ในอนาคต) ถูกส่งเป็น array ว่าง

###### ตัวอย่าง payload \{#membership-example-payloads}

**เพิ่มผู้ใช้ (`POST /organizations/:id/users`):**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "addedUserIds": ["u_001"]
}
```

**แทนที่ชุดสมาชิกผู้ใช้ (`PUT /organizations/:id/users`):**

```json
{
  "event": "Organization.Membership.Updated",
```

**ลบผู้ใช้ (`DELETE /organizations/:id/users/:userId`):**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "removedUserIds": ["u_001"]
}
```

**เพิ่มแอปพลิเคชัน (`POST /organizations/:id/applications`):**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "addedApplicationIds": ["app_xyz"]
}
```

**เพิ่มสมาชิกซ้ำ, no-op `PUT`, หรือรับคำเชิญซ้ำ (ไม่มีการเปลี่ยนแปลงจริง):**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc"
}
```

**Bulk operation ที่ชน cap 5000 (ถูกตัดแบบเงียบ ๆ):**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "removedUserIds": ["u_0001", "u_0002", "/* … exactly 5000 entries total */"]
}
```

หากเห็น array ที่มี 5000 รายการ ให้ sync สมาชิก authoritative ด้วย `GET /organizations/:id/users` (หรือ `/applications`)

## Payload ของเหตุการณ์ Exception \{#exception-event-payloads}

**เหตุการณ์:** `Identifier.Lockout`

ทริกเกอร์เมื่อเกิดเหตุการณ์ด้านความปลอดภัย เช่น บัญชีถูกล็อกหลังจากพยายามยืนยันตัวตนล้มเหลวหลายครั้ง เหตุการณ์เหล่านี้จะมาจาก user-facing flow เสมอ ดังนั้น body จะมี:

- [ฟิลด์ร่วม (common fields)](#common-fields)
- ฟิลด์ `ip` (รูปแบบเดียวกับ data-mutation events)
- [ฟิลด์ Experience API context](#experience-api-context-fields)
- ฟิลด์เฉพาะ exception ด้านล่าง

```tsx
enum SignInIdentifier {
  Email = 'email',
  Phone = 'phone',
  Username = 'username',
}
```

| ฟิลด์ | ชนิด               | Optional | หมายเหตุ                                                    |
| ----- | ------------------ | -------- | ----------------------------------------------------------- |
| type  | `SignInIdentifier` |          | ประเภท identifier ของผู้ใช้ เช่น email, phone หรือ username |
| value | `string`           |          | ค่า identifier ของผู้ใช้ที่ทริกเกอร์ lockout                |

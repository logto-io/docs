# การตั้งค่าบัญชีผู้ใช้ด้วย Account API

## Logto Account API คืออะไร \{#what-is-logto-account-api}

Logto Account API คือชุด API ที่ครอบคลุมซึ่งเปิดให้ผู้ใช้ปลายทางเข้าถึง API ได้โดยตรงโดยไม่ต้องผ่าน Management API จุดเด่นมีดังนี้:

- เข้าถึงโดยตรง: Account API ให้อำนาจผู้ใช้ปลายทางในการเข้าถึงและจัดการโปรไฟล์บัญชีของตนเองโดยตรง โดยไม่ต้องผ่าน Management API
- การจัดการโปรไฟล์ผู้ใช้และอัตลักษณ์: ผู้ใช้สามารถจัดการโปรไฟล์และการตั้งค่าความปลอดภัย เช่น อีเมล โทรศัพท์ รหัสผ่าน การเชื่อมต่อโซเชียล และปัจจัย MFA รวมถึงดึงโทเค็น federated access ของ enterprise SSO จาก Secret Vault ได้
- การควบคุมการเข้าถึงระดับโกลบอล: ผู้ดูแลระบบมีสิทธิ์ควบคุมการเข้าถึงทั้งหมดและสามารถปรับแต่งแต่ละฟิลด์ได้
- การอนุญาต (Authorization) ที่ไร้รอยต่อ: การอนุญาตง่ายกว่าที่เคย! เพียงใช้ `client.getAccessToken()` เพื่อรับโทเค็นการเข้าถึงทึบ (opaque access token) สำหรับ OP (Logto) และแนบไปกับ Authorization header ในรูปแบบ `Bearer <access_token>`

ด้วย Logto Account API คุณสามารถสร้างระบบจัดการบัญชีผู้ใช้แบบกำหนดเอง เช่น หน้าโปรไฟล์ ที่ผสานรวมกับ Logto ได้อย่างสมบูรณ์

ตัวอย่างกรณีการใช้งานที่พบบ่อย:

- ดึงข้อมูลโปรไฟล์ผู้ใช้
- อัปเดตโปรไฟล์ผู้ใช้
- อัปเดตรหัสผ่านผู้ใช้
- อัปเดตอัตลักษณ์ผู้ใช้ เช่น อีเมล โทรศัพท์ และการเชื่อมต่อโซเชียล
- จัดการปัจจัย MFA (การยืนยันตัวตน)
- จัดการเซสชันผู้ใช้
- จัดการแอปที่ผู้ใช้อนุญาต (grants)

ดูรายละเอียด API ที่มีได้ที่ [Logto Account API Reference](https://openapi.logto.io/group/endpoint-my-account) และ [Logto Verification API Reference](https://openapi.logto.io/group/endpoint-verifications)

:::note

ฟีเจอร์ดูบัญชี SSO และการลบบัญชีมีให้ใช้งานผ่าน Logto Management APIs (การเชื่อมหรือยกเลิกเชื่อมต่ออัตลักษณ์ enterprise SSO ยังไม่รองรับใน Account API; รองรับเฉพาะการดึงโทเค็น Secret Vault สำหรับอัตลักษณ์ SSO ที่เชื่อมต่อแล้ว) ดู [การตั้งค่าบัญชีผู้ใช้ด้วย Management API](/end-user-flows/account-settings/by-management-api) สำหรับรายละเอียดการใช้งาน

:::

## วิธีเปิดใช้งาน Account API \{#how-to-enable-account-api}

ไปที่ <CloudLink to="/sign-in-experience/account-center">Console > Sign-in & account > Account center</CloudLink>

Account API ถูกปิดใช้งานโดยค่าเริ่มต้น ดังนั้นการควบคุมการเข้าถึงจะถูกล็อกไว้ ให้สลับเปิด **Enable Account API** เพื่อเปิดใช้งาน

เมื่อเปิดใช้งานแล้ว ให้กำหนดช่วงเวลา **Recent authentication** (ตั้งแต่ `1` ถึง `120` นาที; ค่าเริ่มต้น `10` นาที) และสิทธิ์แต่ละฟิลด์สำหรับ identifiers, ข้อมูลโปรไฟล์ และการเข้าถึงโทเค็นของบุคคลที่สาม แต่ละฟิลด์รองรับ `Off`, `ReadOnly` หรือ `Edit` (ค่าเริ่มต้นคือ `Off`)

1. **ฟิลด์ความปลอดภัย**:
   - ฟิลด์ประกอบด้วย: อีเมลหลัก, โทรศัพท์หลัก, อัตลักษณ์โซเชียล, รหัสผ่าน, passkeys, MFA และ personal access tokens
   - การดำเนินการที่ละเอียดอ่อนต้องการการยืนยันตัวตนล่าสุดของผู้ใช้จากแอป first-party — โทเค็นการเข้าถึงที่ `acr` ตรงตาม `urn:logto:acr:1fa` ภายในช่วง recent authentication ที่ตั้งไว้ (ดู [OIDC step-up authentication](/end-user-flows/step-up-authentication#account-api-and-account-center))
   - หากต้องการใช้ WebAuthn passkey สำหรับ MFA ให้เพิ่มโดเมนแอป front-end ของคุณใน **WebAuthn Related Origins** เพื่อให้ account center และ sign-in experience ใช้ passkey ร่วมกันได้ ดู [เชื่อมต่อ WebAuthn passkey ใหม่](#link-a-new-webauthn-passkey)
2. **ฟิลด์โปรไฟล์**:
   - ฟิลด์ประกอบด้วย: username, name, avatar, [profile](/user-management/user-data#profile) (แอตทริบิวต์โปรไฟล์มาตรฐานอื่น ๆ) และ [custom data](/user-management/user-data#custom-data)
   - ผู้ใช้ปลายทางสามารถแก้ไขฟิลด์เหล่านี้ได้โดยไม่ต้องยืนยันเพิ่มเติม ยกเว้น `username` ที่ต้องการการยืนยันตัวตนล่าสุดเช่นกัน
3. **Secret vault**:
   - สำหรับ OIDC หรือ OAuth social และ enterprise connectors, Logto [secret vault](/secret-vault/federated-token-set) จะเก็บโทเค็น access และ refresh ของบุคคลที่สามอย่างปลอดภัยหลังการยืนยันตัวตน แอปสามารถเรียก API ภายนอก เช่น ซิงค์กิจกรรม Google Calendar ได้โดยไม่ต้องให้ผู้ใช้ลงชื่อเข้าใช้อีก การดึงโทเค็นจะพร้อมใช้งานโดยอัตโนมัติเมื่อเปิด Account API
4. **การจัดการเซสชัน**:
   - เมื่อเปิดใช้งาน ผู้ใช้สามารถดูและจัดการเซสชันที่ใช้งานอยู่ รวมถึงข้อมูลอุปกรณ์และเวลาลงชื่อเข้าใช้ล่าสุด ผู้ใช้ยังสามารถเพิกถอนเซสชันเพื่อออกจากอุปกรณ์เฉพาะได้
   - สิทธิ์ฟิลด์ `Sessions` นี้ควบคุม API สำหรับแอปที่ผู้ใช้อนุญาต (grants) ด้วย (ดูและเพิกถอน grants)
   - การเข้าถึงการจัดการเซสชันและ grant ต้องการการยืนยันตัวตนล่าสุดเช่นเดียวกับฟิลด์ความปลอดภัย

## วิธีเข้าถึง Account API \{#how-to-access-account-api}

:::note
เพื่อให้แน่ใจว่า access token มีสิทธิ์ที่เหมาะสม โปรดกำหนด scopes ที่เกี่ยวข้องใน Logto config ของคุณให้ถูกต้อง

ตัวอย่างเช่น สำหรับ API `POST /api/my-account/primary-email` คุณต้องกำหนด scope `email`; สำหรับ API `POST /api/my-account/primary-phone` คุณต้องกำหนด scope `phone`

```ts
import { type LogtoConfig, UserScope } from '@logto/js';

const config: LogtoConfig = {
  // ...ตัวเลือกอื่น ๆ
  // เพิ่ม scopes ที่เหมาะสมกับกรณีใช้งานของคุณ
  scopes: [
    UserScope.Email, // สำหรับ `{POST,DELETE} /api/my-account/primary-email`
    UserScope.Phone, // สำหรับ `{POST,DELETE} /api/my-account/primary-phone`
    UserScope.CustomData, // จัดการ custom data
    UserScope.Address, // จัดการ address
    UserScope.Identities, // สำหรับ API ที่เกี่ยวข้องกับอัตลักษณ์และ MFA
    UserScope.Profile, // จัดการโปรไฟล์ผู้ใช้
    UserScope.Sessions, // จัดการเซสชันผู้ใช้และ app grants
  ],
};
```

:::

### ดึง access token \{#fetch-an-access-token}

หลังจากตั้งค่า SDK ในแอปของคุณแล้ว คุณสามารถใช้เมธอด `client.getAccessToken()` เพื่อดึง access token ซึ่งเป็นโทเค็นทึบ (opaque token) ที่ใช้เข้าถึง Account API ได้

หากคุณไม่ได้ใช้ SDK อย่างเป็นทางการ ให้ตั้งค่า `resource` เป็นค่าว่างสำหรับ access token grant request ไปที่ `/oidc/token`

### เข้าถึง Account API ด้วย access token \{#access-account-api-using-access-token}

คุณควรแนบ access token ในฟิลด์ `Authorization` ของ HTTP headers ในรูปแบบ Bearer (`Bearer YOUR_TOKEN`) เมื่อเรียกใช้งาน Account API

ตัวอย่างการดึงข้อมูลบัญชีผู้ใช้:

```bash
curl https://[tenant-id].logto.app/api/my-account \
  -H 'authorization: Bearer <access_token>'
```

## จัดการข้อมูลบัญชีผู้ใช้พื้นฐาน \{#manage-basic-account-information}

### ดึงข้อมูลบัญชีผู้ใช้ \{#retrieve-user-account-information}

เพื่อดึงข้อมูลผู้ใช้ ใช้ endpoint [`GET /api/my-account`](https://openapi.logto.io/operation/operation-getprofile)

```bash
curl https://[tenant-id].logto.app/api/my-account \
  -H 'authorization: Bearer <access_token>'
```

ตัวอย่าง response:

```json
{
  "id": "...",
  "username": "...",
  "name": "...",
  "avatar": "..."
}
```

ฟิลด์ใน response อาจแตกต่างกันไปตามการตั้งค่า account center

### อัปเดตข้อมูลบัญชีผู้ใช้พื้นฐาน \{#update-basic-account-information}

ข้อมูลบัญชีผู้ใช้พื้นฐานประกอบด้วย username, name, avatar, custom data และข้อมูลโปรไฟล์อื่น ๆ

เพื่ออัปเดต **username, name, avatar, และ customData** ใช้ endpoint [`PATCH /api/my-account`](https://openapi.logto.io/operation/operation-updateprofile)

```bash
curl -X PATCH https://[tenant-id].logto.app/api/my-account \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"username":"...","name":"...","avatar":"..."}'
```

เพื่ออัปเดตข้อมูลโปรไฟล์อื่น ๆ เช่น **familyName, givenName, middleName, nickname, profile (profile page URL), website, gender, birthdate, zoneinfo, locale, และ address** ใช้ endpoint [`PATCH /api/my-account/profile`](https://openapi.logto.io/operation/operation-updateotherprofile)

```bash
curl -X PATCH https://[tenant-id].logto.app/api/my-account/profile \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"familyName":"...","givenName":"..."}'
```

## จัดการ identifiers และข้อมูลสำคัญอื่น ๆ \{#manage-identifiers-and-other-sensitive-information}

ด้วยเหตุผลด้านความปลอดภัย การดำเนินการที่ละเอียดอ่อนของ Account API ต้องการการยืนยันตัวตนล่าสุดของผู้ใช้จากแอป first-party: access token ต้องมี `acr` ที่ตรงตาม `urn:logto:acr:1fa` และ `auth_time` อยู่ในช่วง **Recent authentication** ของ tenant (`600` วินาที / `10` นาทีโดยค่าเริ่มต้น กำหนดได้ตั้งแต่ `60` ถึง `7,200` วินาที)

หาก access token ไม่มี `urn:logto:acr:1fa` หรือหมดอายุเกินช่วงเวลาดังกล่าว Account API จะคืนค่า `401 Unauthorized` พร้อม header `WWW-Authenticate` ตาม RFC 9470 (`error="insufficient_user_authentication"`, `acr_values="urn:logto:acr:1fa"`, `max_age="<window>"`) ให้เริ่ม [OIDC step-up authentication](/end-user-flows/step-up-authentication#account-api-and-account-center) ด้วยพารามิเตอร์เหล่านั้นและลองใหม่ด้วย access token ที่ออกใหม่

:::note
การผูก **อีเมลใหม่**, หมายเลขโทรศัพท์ใหม่, อัตลักษณ์โซเชียลใหม่ หรือ WebAuthn passkey ใหม่ ต้องพิสูจน์ความเป็นเจ้าของ identifier หรือ factor ใหม่นั้นผ่าน Verification API และส่ง `newIdentifierVerificationRecordId` ใน request body ตามแต่ละหัวข้อด้านล่าง
:::

### อัปเดตรหัสผ่านผู้ใช้ \{#update-users-password}

เพื่ออัปเดตรหัสผ่านผู้ใช้ ใช้ endpoint [`POST /api/my-account/password`](https://openapi.logto.io/operation/operation-updatepassword)

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/password \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"password":"..."}'
```

:::tip
เช่นเดียวกับรหัสผ่านที่สร้างระหว่างสมัครใช้งาน รหัสผ่านที่ตั้งผ่าน Account API ต้องเป็นไปตาม [นโยบายรหัสผ่าน](/security/password-policy) ที่คุณตั้งค่าไว้ใน <CloudLink to="/security/password-policy">Console > Security > Password policy</CloudLink> หากไม่ผ่าน Logto จะคืนผลการตรวจสอบและข้อความผิดพลาดโดยละเอียด
:::

### อัปเดตหรือเชื่อมต่ออีเมลใหม่ \{#update-or-link-new-email}

:::note
เพื่อใช้วิธีนี้ คุณต้อง [ตั้งค่า email connector](/connectors/email-connectors/) และตรวจสอบให้แน่ใจว่าได้ตั้งค่าเทมเพลต `BindNewIdentifier` แล้ว
:::

เพื่ออัปเดตหรือเชื่อมต่ออีเมลใหม่ คุณต้องพิสูจน์ความเป็นเจ้าของอีเมลนั้นก่อน

เรียก endpoint [`POST /api/verifications/verification-code`](https://openapi.logto.io/operation/operation-createverificationbyverificationcode) เพื่อขอรหัสยืนยัน

```bash
curl -X POST https://[tenant-id].logto.app/api/verifications/verification-code \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"identifier":{"type":"email","value":"..."}}'
```

คุณจะได้รับ `verificationId` ใน response และรับรหัสยืนยันทางอีเมล ให้นำไปยืนยันอีเมล

```bash
curl -X POST https://[tenant-id].logto.app/api/verifications/verification-code/verify \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"identifier":{"type":"email","value":"..."},"verificationId":"...","code":"..."}'
```

หลังจากยืนยันรหัสแล้ว สามารถเรียก [`PATCH /api/my-account/primary-email`](https://openapi.logto.io/operation/operation-updateprimaryemail) เพื่ออัปเดตอีเมลผู้ใช้ โดยใส่ `verificationId` ใน request body เป็น `newIdentifierVerificationRecordId`

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/primary-email \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"email":"...","newIdentifierVerificationRecordId":"<verification_record_id_from_new_email>"}'
```

:::tip
เช่นเดียวกับอีเมลที่เก็บระหว่างสมัครใช้งาน อีเมลใด ๆ ที่เชื่อมต่อผ่าน Account API ต้องผ่านการตรวจสอบ [blocklist](/security/blocklist) ที่คุณตั้งค่าไว้ใน <CloudLink to="/security/blocklist">Console > Security > Blocklist</CloudLink> หากไม่ผ่าน Logto จะปฏิเสธคำขอและคืนข้อผิดพลาดโดยละเอียด
:::

### ลบอีเมลของผู้ใช้ \{#remove-the-users-email}

เพื่อลบอีเมลของผู้ใช้ ใช้ endpoint [`DELETE /api/my-account/primary-email`](https://openapi.logto.io/operation/operation-deleteprimaryemail)

```bash
curl -X DELETE https://[tenant-id].logto.app/api/my-account/primary-email \
  -H 'authorization: Bearer <access_token>'
```

### จัดการโทรศัพท์ \{#manage-phone}

:::note
เพื่อใช้วิธีนี้ คุณต้อง [ตั้งค่า SMS connector](/connectors/sms-connectors/) และตรวจสอบให้แน่ใจว่าได้ตั้งค่าเทมเพลต `BindNewIdentifier` แล้ว
:::

คล้ายกับการอัปเดตอีเมล คุณสามารถใช้ endpoint [`PATCH /api/my-account/primary-phone`](https://openapi.logto.io/operation/operation-updateprimaryphone) เพื่ออัปเดตหรือเชื่อมต่อโทรศัพท์ใหม่ และใช้ endpoint [`DELETE /api/my-account/primary-phone`](https://openapi.logto.io/operation/operation-deleteprimaryphone) เพื่อลบโทรศัพท์ของผู้ใช้

### เชื่อมต่อโซเชียลใหม่ \{#link-a-new-social-connection}

เพื่อเชื่อมต่อโซเชียลใหม่ ให้ขอ authorization URL ก่อนด้วย [`POST /api/verifications/social`](https://openapi.logto.io/operation/operation-createverificationbysocial)

```bash
curl -X POST https://[tenant-id].logto.app/api/verifications/social \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"connectorId":"...","redirectUri":"...","state":"..."}'
```

- `connectorId`: รหัสของ [social connector](/connectors/social-connectors/)
- `redirectUri`: URI ที่จะเปลี่ยนเส้นทางหลังผู้ใช้อนุญาตแอป คุณควรโฮสต์หน้าเว็บที่ URL นี้และจับ callback
- `state`: สถานะที่จะคืนหลังผู้ใช้อนุญาตแอป เป็นสตริงสุ่มเพื่อป้องกัน CSRF

ใน response จะมี `verificationRecordId` ให้เก็บไว้ใช้ในขั้นตอนถัดไป

หลังผู้ใช้อนุญาตแอป คุณจะได้รับ callback ที่ `redirectUri` พร้อมพารามิเตอร์ `state` จากนั้นใช้ endpoint [`POST /api/verifications/social/verify`](https://openapi.logto.io/operation/operation-verifyverificationbysocial) เพื่อตรวจสอบการเชื่อมต่อโซเชียล

```bash
curl -X POST https://[tenant-id].logto.app/api/verifications/social/verify \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"connectorData":"...","verificationRecordId":"..."}'
```

`connectorData` คือข้อมูลที่ social connector ส่งกลับหลังผู้ใช้อนุญาตแอป คุณต้องแยก query parameters จาก `redirectUri` ในหน้า callback ของคุณและห่อเป็น JSON ในฟิลด์ `connectorData`

สุดท้าย ใช้ endpoint [`POST /api/my-account/identities`](https://openapi.logto.io/operation/operation-adduseridentities) เพื่อเชื่อมต่อโซเชียล

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/identities \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"newIdentifierVerificationRecordId":"<verification_record_id_from_social>"}'
```

### ลบการเชื่อมต่อโซเชียล \{#remove-a-social-connection}

เพื่อลบการเชื่อมต่อโซเชียล ใช้ endpoint [`DELETE /api/my-account/identities`](https://openapi.logto.io/operation/operation-deleteidentity)

```bash
curl -X DELETE https://[tenant-id].logto.app/api/my-account/identities/[connector_target_id] \
  -H 'authorization: Bearer <access_token>'
```

### เชื่อมต่อ WebAuthn passkey ใหม่ \{#link-a-new-webauthn-passkey}

:::note
อย่าลืม [เปิดใช้งาน MFA และ WebAuthn](/end-user-flows/mfa) ก่อน
:::

:::note
endpoint สำหรับเขียน WebAuthn passkey (`POST /api/my-account/mfa-verifications` พร้อม `type: "WebAuthn"`, `PATCH /api/my-account/mfa-verifications/{verificationId}/name`, และ `DELETE /api/my-account/mfa-verifications/{verificationId}` สำหรับ WebAuthn) ถูกควบคุมโดยฟิลด์ `passkey` ใน [account center settings](#how-to-enable-account-api) หากไม่ได้ตั้งค่า `passkey` จะใช้ `mfa` แทน การอ่าน `GET /api/my-account/mfa-verifications` ต้องตั้งค่า `mfa` เป็น `ReadOnly` หรือ `Edit`
:::

**ขั้นตอนที่ 1: เพิ่ม origin ของแอป front-end ของคุณใน related origins**

WebAuthn passkey ผูกกับ hostname เฉพาะที่เรียกว่า **Relying Party ID (RP ID)** เฉพาะแอปที่โฮสต์บน origin ของ RP ID เท่านั้นที่สามารถลงทะเบียนหรือยืนยันตัวตนด้วย passkey เหล่านั้นได้

เนื่องจากแอป front-end ของคุณเรียก Account API จากโดเมนที่ต่างจากหน้าการยืนยันตัวตนของ Logto คุณต้องตั้งค่า **Related Origins** เพื่ออนุญาตการดำเนินการ passkey ข้าม origin

**Logto กำหนด RP ID อย่างไร:**

- **ค่าเริ่มต้น**: หากใช้โดเมน Logto เริ่มต้น `https://[tenant-id].logto.app` RP ID คือ `[tenant-id].logto.app`
- **Custom domain**: หากตั้งค่า [custom domain](/logto-cloud/custom-domain) เช่น `https://auth.example.com` RP ID จะเป็น `auth.example.com`

**ตั้งค่า Related Origins:**

ใช้ endpoint [`PATCH /api/account-center`](https://openapi.logto.io/operation/operation-updateaccountcentersettings) เพื่อเพิ่ม origin ของแอป front-end ของคุณ เช่น หาก account center ของแอปรันที่ `https://account.example.com`:

```bash
curl -X PATCH https://[tenant-id].logto.app/api/account-center \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"webauthnRelatedOrigins":["https://account.example.com"]}'
```

:::note

WebAuthn รองรับได้สูงสุด 5 label eTLD+1 ที่ไม่ซ้ำสำหรับ Related Origins โดย eTLD+1 (effective top-level domain plus one label) คือส่วนโดเมนที่ลงทะเบียนได้ เช่น:

- `https://example.com`, `https://app.example.com`, และ `https://auth.example.com` นับเป็น **หนึ่ง** label (`example.com`)
- `https://shopping.com`, `https://shopping.co.uk`, และ `https://shopping.co.jp` ก็นับเป็น **หนึ่ง** label (`shopping`)
- `https://example.com` และ `https://another.com` นับเป็น **สอง** label

หากต้องการรองรับมากกว่า 5 โดเมนที่แตกต่างกันสำหรับ Related Origins ดูรายละเอียดที่ [Related Origin Requests](https://passkeys.dev/docs/advanced/related-origins/)

:::

**ขั้นตอนที่ 2: ขอ registration options ใหม่**

ใช้ endpoint [`POST /api/verifications/web-authn/registration`](https://openapi.logto.io/operation/operation-generatewebauthnregistrationoptions) เพื่อขอ registration สำหรับ passkey ใหม่ Logto อนุญาตให้แต่ละบัญชีผู้ใช้ลงทะเบียน passkey ได้หลายอัน

```bash
curl -X POST https://[tenant-id].logto.app/api/verifications/web-authn/registration \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

คุณจะได้รับ response เช่น:

```json
{
  "registrationOptions": "...",
  "verificationRecordId": "...",
  "expiresAt": "..."
}
```

**ขั้นตอนที่ 3: ลงทะเบียน passkey ในเบราว์เซอร์**

ตัวอย่างใช้ [`@simplewebauthn/browser`](https://simplewebauthn.dev/) สามารถใช้ฟังก์ชัน `startRegistration` เพื่อลงทะเบียน passkey ในเบราว์เซอร์

```ts
import { startRegistration } from '@simplewebauthn/browser';

// ...
const response = await startRegistration({
  optionsJSON: registrationOptions, // ข้อมูลที่เซิร์ฟเวอร์ส่งกลับในขั้นตอนที่ 1
});
// บันทึก response ไว้ใช้ในขั้นตอนถัดไป
```

**ขั้นตอนที่ 4: ตรวจสอบการลงทะเบียน passkey**

ใช้ endpoint [`POST /api/verifications/web-authn/registration/verify`](https://openapi.logto.io/operation/operation-verifywebauthnregistration) เพื่อตรวจสอบการลงทะเบียน passkey

ขั้นตอนนี้จะตรวจสอบลายเซ็นดิจิทัลที่สร้างโดย authenticator เพื่อให้แน่ใจว่า passkey ถูกสร้างขึ้นอย่างถูกต้องและไม่ถูกแก้ไขระหว่างส่งข้อมูล

```bash
curl -X POST https://[tenant-id].logto.app/api/verifications/web-authn/registration/verify \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"payload":"...","verificationRecordId":"..."}'
```

- `payload`: response จากเบราว์เซอร์ในขั้นตอนที่ 2
- `verificationRecordId`: verification record ID ที่เซิร์ฟเวอร์ส่งกลับในขั้นตอนที่ 1

**ขั้นตอนที่ 5: เชื่อมต่อ passkey**

สุดท้าย เชื่อมต่อ passkey กับบัญชีผู้ใช้โดยใช้ endpoint [`POST /api/my-account/mfa-verifications`](https://openapi.logto.io/operation/operation-addmfaverification)

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/mfa-verifications \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"type":"WebAuthn","newIdentifierVerificationRecordId":"..."}'
```

- `type`: ประเภทของปัจจัย MFA (`WebAuthn`, `Totp`, หรือ `BackupCode`; ใช้ `WebAuthn` ที่นี่)
- `newIdentifierVerificationRecordId`: verification record ID ที่เซิร์ฟเวอร์ส่งกลับในขั้นตอนที่ 2

### จัดการ WebAuthn passkey ที่มีอยู่ \{#manage-existing-webauthn-passkeys}

เพื่อจัดการ WebAuthn passkey ที่มีอยู่ ใช้ endpoint [`GET /api/my-account/mfa-verifications`](https://openapi.logto.io/operation/operation-getmfaverifications) เพื่อดึง passkey ปัจจุบันและปัจจัย MFA อื่น ๆ

```bash
curl https://[tenant-id].logto.app/api/my-account/mfa-verifications \
  -H 'authorization: Bearer <access_token>'
```

ตัวอย่าง response:

```json
[
  {
    "id": "...",
    "type": "WebAuthn",
    "name": "...",
    "agent": "...",
    "createdAt": "...",
    "lastUsedAt": "..."
  }
]
```

- `id`: รหัสของการยืนยันตัวตน
- `type`: ประเภทของการยืนยัน (`WebAuthn`, `Totp`, `BackupCode`, `EmailVerificationCode`, หรือ `PhoneVerificationCode`) `EmailVerificationCode` และ `PhoneVerificationCode` จะแสดงเฉพาะเมื่อผู้ใช้ [ตั้งค่า email หรือ SMS MFA](#manage-email-and-sms-mfa)
- `name`: ชื่อของ passkey (สำหรับ `WebAuthn`)
- `agent`: user agent ของ passkey (สำหรับ `WebAuthn`)
- `createdAt`: เวลาที่สร้างการยืนยัน
- `lastUsedAt`: เวลาที่ใช้การยืนยันล่าสุด (สำหรับ `WebAuthn`)
- `remainCodes`: จำนวน backup code ที่ยังไม่ได้ใช้ (สำหรับ `BackupCode`)

อัปเดตชื่อ passkey ด้วย endpoint [`PATCH /api/my-account/mfa-verifications/{verificationId}/name`](https://openapi.logto.io/operation/operation-updatemfaverificationname):

```bash
curl -X PATCH https://[tenant-id].logto.app/api/my-account/mfa-verifications/{verificationId}/name \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"name":"..."}'
```

ลบ passkey ด้วย endpoint [`DELETE /api/my-account/mfa-verifications/{verificationId}`](https://openapi.logto.io/operation/operation-deletemfaverification):

```bash
curl -X DELETE https://[tenant-id].logto.app/api/my-account/mfa-verifications/{verificationId} \
  -H 'authorization: Bearer <access_token>'
```

### เชื่อมต่อ TOTP ใหม่ \{#link-a-new-totp}

:::note
อย่าลืม [เปิดใช้งาน MFA และ TOTP](/end-user-flows/mfa) ก่อน
:::

:::note
เพื่อใช้วิธีนี้ คุณต้องเปิดฟิลด์ `mfa` ใน [account center settings](#how-to-enable-account-api)
:::

**ขั้นตอนที่ 1: สร้าง TOTP secret**

ใช้ endpoint [`POST /api/my-account/mfa-verifications/totp-secret/generate`](https://openapi.logto.io/operation/operation-generatetotpsecret) เพื่อสร้าง TOTP secret

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/mfa-verifications/totp-secret/generate \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

ตัวอย่าง response:

```json
{
  "secret": "..."
}
```

**ขั้นตอนที่ 2: แสดง TOTP secret ให้ผู้ใช้**

นำ secret ไปสร้าง QR code หรือแสดงให้ผู้ใช้โดยตรง ผู้ใช้ควรเพิ่ม secret นี้ในแอป authenticator (เช่น Google Authenticator, Microsoft Authenticator, หรือ Authy)

รูปแบบ URI สำหรับ QR code:

```
otpauth://totp/[Issuer]:[Account]?secret=[Secret]&issuer=[Issuer]
```

ตัวอย่าง:

```
otpauth://totp/YourApp:user@example.com?secret=JBSWY3DPEHPK3PXP&issuer=YourApp
```

**ขั้นตอนที่ 3: ผูกปัจจัย TOTP**

หลังผู้ใช้เพิ่ม secret ในแอป authenticator แล้ว ต้องยืนยันและผูกกับบัญชีผู้ใช้ ใช้ endpoint [`POST /api/my-account/mfa-verifications`](https://openapi.logto.io/operation/operation-addmfaverification) เพื่อผูกปัจจัย TOTP

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/mfa-verifications \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"type":"Totp","secret":"..."}'
```

- `type`: ต้องเป็น `Totp`
- `secret`: TOTP secret ที่สร้างในขั้นตอนที่ 1

:::note
ผู้ใช้แต่ละคนมี TOTP factor ได้เพียงหนึ่งรายการ หากมีอยู่แล้ว การเพิ่มใหม่จะได้ error 422
:::

### แทนที่ TOTP ที่มีอยู่ \{#replace-an-existing-totp}

หากผู้ใช้มี TOTP factor อยู่แล้ว สามารถแทนที่ด้วยอันใหม่ได้โดยใช้ endpoint [`PUT /api/my-account/mfa-verifications/totp`](https://openapi.logto.io/operation/operation-createorreplacetotpmfaverification) การดำเนินการนี้เป็น idempotent คือจะลบ TOTP เดิมและผูกอันใหม่

:::note
เพื่อใช้วิธีนี้ คุณต้องเปิดฟิลด์ `mfa` ใน [account center settings](#how-to-enable-account-api)
:::

**ขั้นตอนที่ 1: สร้าง TOTP secret ใหม่**

ใช้ endpoint [`POST /api/my-account/mfa-verifications/totp-secret/generate`](https://openapi.logto.io/operation/operation-generatetotpsecret) เพื่อสร้าง TOTP secret ใหม่ แล้วแสดงให้ผู้ใช้ตาม [เชื่อมต่อ TOTP ใหม่](#link-a-new-totp)

**ขั้นตอนที่ 2: แทนที่ปัจจัย TOTP**

```bash
curl -X PUT https://[tenant-id].logto.app/api/my-account/mfa-verifications/totp \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"secret":"...","code":"..."}'
```

- `secret`: TOTP secret ใหม่ที่สร้างในขั้นตอนที่ 1
- `code`: รหัส TOTP ที่สร้างจาก secret ใหม่เพื่อยืนยันการผูก

### จัดการ email และ SMS MFA \{#manage-email-and-sms-mfa}

:::note
อย่าลืม [เปิดใช้งาน MFA และปัจจัย email หรือ SMS verification code](/end-user-flows/mfa) ก่อน
:::

:::note
เพื่อใช้วิธีนี้ คุณต้องเปิดฟิลด์ `mfa` ใน [account center settings](#how-to-enable-account-api)
:::

รหัส MFA สำหรับ email และ SMS จะถูกส่งไปยังอีเมลหลักและหมายเลขโทรศัพท์หลักของผู้ใช้ การตั้งค่าปัจจัยจะบันทึกว่าผู้ใช้เลือกใช้; ที่อยู่เองจัดการด้วย [อัปเดตหรือเชื่อมต่ออีเมลใหม่](#update-or-link-new-email) และ [จัดการโทรศัพท์](#manage-phone)

ผู้ใช้จำเป็นต้องตั้งค่าปัจจัยเหล่านี้หรือไม่ขึ้นอยู่กับ [การลงทะเบียน MFA สำหรับ email และ SMS](/end-user-flows/mfa/configure-mfa#email-and-sms-mfa-enrollment) หากเลือก **Only users who set it up** เฉพาะผู้ใช้ที่ตั้งค่าเท่านั้นจึงจะใช้ MFA ได้ หากเลือก **Every user with a verified email or phone number** ระบบจะบันทึกการตั้งค่าไว้ ผู้ใช้จะยังคงมีปัจจัยนี้หากคุณเปลี่ยนโหมดในภายหลัง

**ตั้งค่า email หรือ SMS MFA**

ใช้ endpoint [`POST /api/my-account/mfa-verifications`](https://openapi.logto.io/operation/operation-addmfaverification):

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/mfa-verifications \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"type":"EmailVerificationCode"}'
```

- `type`: `EmailVerificationCode` สำหรับ email MFA หรือ `PhoneVerificationCode` สำหรับ SMS MFA

:::note

- ผู้ใช้ต้องมีอีเมลหลักสำหรับ email MFA หรือหมายเลขโทรศัพท์หลักสำหรับ SMS MFA มิฉะนั้นจะได้ error 422
- ผู้ใช้แต่ละคนตั้งค่าปัจจัยแต่ละประเภทได้เพียงครั้งเดียว การตั้งค่าใหม่จะได้ error 422

:::

**ลบ email หรือ SMS MFA**

ใช้ endpoint [`GET /api/my-account/mfa-verifications`](https://openapi.logto.io/operation/operation-getmfaverifications) เพื่อค้นหา verification ที่ `type` เป็น `EmailVerificationCode` หรือ `PhoneVerificationCode` แล้วลบด้วย endpoint [`DELETE /api/my-account/mfa-verifications/{verificationId}`](https://openapi.logto.io/operation/operation-deletemfaverification):

```bash
curl -X DELETE https://[tenant-id].logto.app/api/my-account/mfa-verifications/{verificationId} \
  -H 'authorization: Bearer <access_token>'
```

การลบปัจจัยนี้จะไม่เปลี่ยนอีเมลหลักหรือหมายเลขโทรศัพท์หลักของผู้ใช้

### จัดการ backup codes \{#manage-backup-codes}

:::note
อย่าลืม [เปิดใช้งาน MFA และ backup codes](/end-user-flows/mfa) ก่อน
:::

:::note
เพื่อใช้วิธีนี้ คุณต้องเปิดฟิลด์ `mfa` ใน [account center settings](#how-to-enable-account-api)
:::

**ขั้นตอนที่ 1: สร้าง backup codes ใหม่**

ใช้ endpoint [`POST /api/my-account/mfa-verifications/backup-codes/generate`](https://openapi.logto.io/operation/operation-generatemyaccountbackupcodes) เพื่อสร้าง backup codes ชุดใหม่ 10 รหัส

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/mfa-verifications/backup-codes/generate \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

ตัวอย่าง response:

```json
{
  "codes": ["...", "...", "..."]
}
```

**ขั้นตอนที่ 2: แสดง backup codes ให้ผู้ใช้**

ก่อนผูก backup codes กับบัญชีผู้ใช้ คุณต้องแสดงรหัสเหล่านี้ให้ผู้ใช้และแนะนำให้:

- ดาวน์โหลดหรือจดรหัสเหล่านี้ทันที
- เก็บไว้ในที่ปลอดภัย
- เข้าใจว่ารหัสแต่ละอันใช้ได้ครั้งเดียว
- ทราบว่ารหัสเหล่านี้เป็นทางเลือกสุดท้ายหากสูญเสียวิธี MFA หลัก

ควรแสดงรหัสในรูปแบบที่ชัดเจนและง่ายต่อการคัดลอก และอาจมีตัวเลือกให้ดาวน์โหลด (เช่น ไฟล์ข้อความหรือ PDF)

**ขั้นตอนที่ 3: ผูก backup codes กับบัญชีผู้ใช้**

ใช้ endpoint [`POST /api/my-account/mfa-verifications`](https://openapi.logto.io/operation/operation-addmfaverification) เพื่อผูก backup codes กับบัญชีผู้ใช้

```bash
curl -X POST https://[tenant-id].logto.app/api/my-account/mfa-verifications \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"type":"BackupCode","codes":["...","...","..."]}'
```

- `type`: ต้องเป็น `BackupCode`
- `codes`: อาร์เรย์ของ backup codes ที่สร้างในขั้นตอนก่อนหน้า

:::note

- ผู้ใช้แต่ละคนมี backup codes ได้เพียงชุดเดียว หากใช้หมดแล้วต้องสร้างและผูกใหม่
- backup codes ไม่สามารถเป็นปัจจัย MFA เดียวได้ ผู้ใช้ต้องมี authenticator app (`Totp`) หรือ passkey (`WebAuthn`) ด้วย; รหัสยืนยัน email หรือ SMS เพียงอย่างเดียวไม่เพียงพอ
- backup code แต่ละอันใช้ได้ครั้งเดียว

:::

**ดู backup codes ที่มีอยู่**

เพื่อดู backup codes ที่มีอยู่และสถานะการใช้งาน ใช้ endpoint [`GET /api/my-account/mfa-verifications/backup-codes`](https://openapi.logto.io/operation/operation-getbackupcodes):

```bash
curl https://[tenant-id].logto.app/api/my-account/mfa-verifications/backup-codes \
  -H 'authorization: Bearer <access_token>'
```

ตัวอย่าง response:

```json
{
  "codes": [
    {
      "code": "...",
      "usedAt": null
    },
    {
      "code": "...",
      "usedAt": "2024-01-15T10:30:00.000Z"
    }
  ]
}
```

- `code`: backup code
- `usedAt`: เวลาที่ใช้รหัสนั้น (`null` หากยังไม่ถูกใช้)

### จัดการการตั้งค่าการยืนยันตัวตน 2 ขั้นตอน \{#manage-2-step-verification-settings}

:::note
เพื่อใช้วิธีเหล่านี้ คุณต้องเปิดฟิลด์ `mfa` ใน [account center settings](#how-to-enable-account-api)
:::

ผู้ใช้ปลายทางสามารถเปิดหรือปิดการยืนยันตัวตน 2 ขั้นตอนสำหรับบัญชีของตนเอง กรณีที่พบบ่อยคือผู้ใช้ตั้งค่าปัจจัย MFA (เช่น passkey) แล้วแต่ต้องการใช้เฉพาะสำหรับลงชื่อเข้าใช้ ไม่ต้องการให้เป็นขั้นตอนยืนยันเพิ่มเติม — การปิด 2-step verification จะช่วยให้ข้าม MFA prompt ระหว่างลงชื่อเข้าใช้ได้โดยยังคงมีปัจจัย MFA อยู่ การตั้งค่านี้ควบคุมโดย `skipMfaOnSignIn` ต่อผู้ใช้

**ดูการตั้งค่า MFA ปัจจุบัน**

ใช้ endpoint [`GET /api/my-account/mfa-settings`](https://openapi.logto.io/operation/operation-getmfasettings) เพื่อดึงการตั้งค่าการยืนยันตัวตน 2 ขั้นตอนของผู้ใช้

```bash
curl https://[tenant-id].logto.app/api/my-account/mfa-settings \
  -H 'authorization: Bearer <access_token>'
```

ตัวอย่าง response:

```json
{
  "skipMfaOnSignIn": false,
  "enabled": true,
  "required": false
}
```

- `skipMfaOnSignIn`: ผู้ใช้เลือกข้าม MFA prompt ระหว่างลงชื่อเข้าใช้หรือไม่
- `enabled` (optional): เปิดใช้งาน MFA สำหรับผู้ใช้หรือไม่ (`undefined` สำหรับบัญชีเก่าก่อนมีฟิลด์นี้ Logto จะถือว่าเปิดใช้งานหากมีปัจจัยที่ใช้ได้)
- `required` (read-only): MFA ถูกบังคับโดยนโยบาย tenant (รวมถึง **Mandatory** และ **Adaptive MFA** ที่ไม่สามารถข้ามได้), ข้อกำหนดต่อผู้ใช้ หรือองค์กร ทำให้ `skipMfaOnSignIn` และ `enabled: false` ไม่มีผล

**อัปเดตการตั้งค่า MFA**

เพื่อเปิดหรือปิด 2-step verification ใช้ endpoint [`PATCH /api/my-account/mfa-settings`](https://openapi.logto.io/operation/operation-updatemfasettings)

```bash
curl -X PATCH https://[tenant-id].logto.app/api/my-account/mfa-settings \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json' \
  --data-raw '{"skipMfaOnSignIn":true}'
```

- `skipMfaOnSignIn`: ตั้งค่า `true` เพื่อปิด prompt 2-step verification ระหว่างลงชื่อเข้าใช้ หรือ `false` เพื่อเปิดใช้งาน
- `enabled` (optional): ตั้งค่า `true` หรือ `false` เพื่ออัปเดตการเปิดใช้งาน MFA สำหรับผู้ใช้ Response จะมี `skipMfaOnSignIn`, `enabled`, และ `required` (read-only) ที่อัปเดตแล้ว

:::note
`skipMfaOnSignIn` และ `enabled: false` มีผลเฉพาะเมื่อ MFA policy เป็น **Optional** และ MFA ไม่ถูกบังคับสำหรับผู้ใช้หรือองค์กร (ผ่าน `organizationRequiredMfaPolicy`) หาก MFA เป็น **Mandatory** หรือถูกบังคับสำหรับผู้ใช้หรือองค์กร ทั้งสองค่าจะถูกละเลยและ MFA จะถูกบังคับ (`required` เป็น `true`) ภายใต้ **Adaptive MFA** `required` ก็เป็น `true` และทั้งสองค่าจะถูกละเลย แม้จะ prompt MFA เฉพาะเมื่อกฎความเสี่ยงถูกทริกเกอร์
:::

### จัดการเซสชันผู้ใช้ \{#manage-user-sessions}

**แสดงรายการเซสชันที่ใช้งานอยู่**

เพื่อแสดงรายการเซสชันที่ใช้งานของผู้ใช้ ใช้ endpoint [`GET /api/my-account/sessions`](https://openapi.logto.io/operation/operation-getsessions)

:::note

- ต้องใช้ scope `UserScope.Sessions` เพื่อเข้าถึง endpoint นี้
- ฟิลด์ `Sessions` ใน account center settings ต้องตั้งค่าเป็น `ReadOnly` หรือ `Edit`

:::

```bash
curl https://[tenant-id].logto.app/api/my-account/sessions \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

**เพิกถอนเซสชันตาม session ID**

เพื่อเพิกถอนเซสชันเฉพาะ ใช้ endpoint [`DELETE /api/my-account/sessions/{sessionId}`](https://openapi.logto.io/operation/operation-deletesessionbyid)

:::note

- ต้องใช้ scope `UserScope.Sessions` เพื่อเข้าถึง endpoint นี้
- ฟิลด์ `Sessions` ใน account center settings ต้องตั้งค่าเป็น `Edit`
  :::

```bash
curl -X DELETE https://[tenant-id].logto.app/api/my-account/sessions/{sessionId} \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

พารามิเตอร์ query เสริม:

- `revokeGrantsTarget`: ระบุเป้าหมายของ grants ที่จะเพิกถอนพร้อมกับเซสชัน ค่าได้แก่:
  - `all`: เพิกถอน grants ทั้งหมดที่เกี่ยวข้องกับเซสชัน
  - `firstParty`: เพิกถอนเฉพาะ grants ของแอป first-party ที่เกี่ยวข้องกับเซสชัน (แนะนำสำหรับกรณีส่วนใหญ่ เพราะจะเพิกถอนการเข้าถึงเฉพาะแอปของคุณเองโดยยังคง grants ของแอป third-party ไว้ เพื่อประสบการณ์ผู้ใช้ที่ดีกว่า)
  - ไม่ระบุ: พฤติกรรมเริ่มต้นจะเพิกถอน grants ที่ไม่มี scope `offline_access` ซึ่งโดยทั่วไปหมายถึงเพิกถอน grants ที่ไม่ใช่ refresh token สำหรับเซสชันนั้น

### จัดการแอปที่ผู้ใช้อนุญาต (grants) \{#manage-user-authorized-apps-grants}

ใช้ API สำหรับแอปที่ผู้ใช้อนุญาต (grants) เมื่อผู้ใช้ต้องการตรวจสอบและเพิกถอนแอปที่อนุญาตจากหน้าตั้งค่าบัญชี

:::note

- API สำหรับ app grant ใช้โมเดลสิทธิ์เดียวกับ session API
- ต้องใช้ scope `UserScope.Sessions`
- ฟิลด์ `Sessions` ใน account center settings ต้องเปิดใช้งาน:
  - `ReadOnly` หรือ `Edit` เพื่อแสดงรายการ grants
  - `Edit` เพื่อเพิกถอน grants

:::

**แสดงรายการ app grants ที่ใช้งานอยู่**

เพื่อแสดงรายการ app grants ที่ใช้งานของผู้ใช้ปัจจุบัน ใช้ endpoint [`GET /api/my-account/grants`](https://openapi.logto.io/operation/operation-getgrants)

```bash
curl https://[tenant-id].logto.app/api/my-account/grants \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

พารามิเตอร์ query เสริม:

- `appType=firstParty`: คืนเฉพาะ app grants ของแอป first-party
- `appType=thirdParty`: คืนเฉพาะ app grants ของแอป third-party
- ไม่ระบุ `appType`: คืน grants ที่ใช้งานทั้งหมด

```bash
curl "https://[tenant-id].logto.app/api/my-account/grants?appType=thirdParty" \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

**เพิกถอน app grant ตาม grant ID**

เพื่อเพิกถอน app grant เฉพาะ ใช้ endpoint [`DELETE /api/my-account/grants/{grantId}`](https://openapi.logto.io/operation/operation-deletegrantbyid)

```bash
curl -X DELETE https://[tenant-id].logto.app/api/my-account/grants/{grantId} \
  -H 'authorization: Bearer <access_token>' \
  -H 'content-type: application/json'
```

เมื่อ grant ถูกเพิกถอน โทเค็นทึบ (opaque access tokens) และ refresh tokens ที่ออกให้กับ grant นั้นจะถูกทำให้ใช้ไม่ได้

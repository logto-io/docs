# ตั้งค่า MFA

## ตั้งค่าการยืนยันตัวตนหลายปัจจัย (MFA) ใน Logto \{#configure-mfa-settings-in-logto}

Logto มีตัวเลือกการตั้งค่า MFA ที่ยืดหยุ่นเพื่อตอบสนองความต้องการด้านความปลอดภัยที่แตกต่างกัน คุณสามารถตั้งค่า MFA ในระดับโกลบอลสำหรับผู้ใช้ทุกคน หรือเปิดใช้งานในแต่ละองค์กรสำหรับแอปพลิเคชันแบบหลายผู้เช่า

### การตั้งค่า MFA ระดับโกลบอล \{#global-mfa-configuration}

ทำตามขั้นตอนเหล่านี้เพื่อเปิดใช้งาน MFA ในขั้นตอนลงชื่อเข้าใช้ของผู้ใช้ Logto:

1. ไปที่: <CloudLink to="/mfa">Console > Multi-factor auth</CloudLink>
2. เปิดใช้งานปัจจัยการยืนยันตัวตนที่รองรับสำหรับผู้ใช้ของคุณ
   1. ปัจจัยหลัก:
      - [Passkeys (WebAuthn)](/end-user-flows/mfa/webauthn): ตัวเลือกความปลอดภัยสูง เหมาะสำหรับผลิตภัณฑ์เว็บที่รองรับไบโอเมตริกซ์ของอุปกรณ์หรือกุญแจความปลอดภัย ฯลฯ เพื่อการปกป้องที่แข็งแกร่ง
      - [Authenticator App OTP](/end-user-flows/mfa/authenticator-app-otp): วิธีที่พบได้บ่อยและได้รับการยอมรับอย่างกว้างขวาง ใช้รหัสผ่านแบบใช้ครั้งเดียวตามเวลา (TOTP) ที่สร้างโดยแอปยืนยันตัวตน เช่น Google Authenticator หรือ Authy
      - [SMS verification](/end-user-flows/mfa/sms-mfa): วิธีที่สะดวก ส่งรหัสยืนยันแบบใช้ครั้งเดียวผ่าน SMS ไปยังหมายเลขโทรศัพท์ที่ลงทะเบียน เหมาะสำหรับผู้ใช้ที่ต้องการยืนยันตัวตนผ่านมือถือโดยไม่ต้องใช้แอปเพิ่มเติม
      - [Email verification](/end-user-flows/mfa/email-mfa): วิธีที่เข้าถึงได้ง่าย ส่งรหัสยืนยันแบบใช้ครั้งเดียวไปยังอีเมลที่ลงทะเบียน เหมาะสำหรับผู้ใช้ทุกแพลตฟอร์มและอุปกรณ์
   2. ปัจจัยสำรอง:
      - [Backup codes](/end-user-flows/mfa/backup-codes): ใช้เป็นตัวเลือกสำรองเมื่อผู้ใช้ไม่สามารถยืนยันตัวตนด้วยปัจจัยหลักที่กล่าวถึงข้างต้น การเปิดใช้งานนี้ช่วยลดอุปสรรคในการเข้าถึงของผู้ใช้
   3. หากเปิดใช้งาน SMS หรืออีเมล ให้เลือกว่าผู้ใช้ใดจะมีสิทธิ์ใน **Email/SMS 2-step verification** ดู [การลงทะเบียน MFA ด้วยอีเมลและ SMS](#email-and-sms-mfa-enrollment)
3. เลือกนโยบาย **Require MFA** จากดรอปดาวน์ นโยบายนี้ควบคุมว่าผู้ใช้ต้องทำ MFA เมื่อใดระหว่างการลงชื่อเข้าใช้:
   - **Optional MFA** (_Optional MFA: ให้ผู้ใช้เลือกเปิด MFA เพื่อความปลอดภัยของบัญชีตนเอง_): ให้ผู้ใช้ตัดสินใจเองว่าจะเปิด MFA หรือไม่ ผู้ใช้สามารถข้ามการตั้งค่า MFA ระหว่างลงชื่อเข้าใช้และตั้งค่าได้ภายหลังผ่านหน้าตั้งค่าบัญชีด้วยตนเอง [เรียนรู้เพิ่มเติม](/end-user-flows/account-settings/) เกี่ยวกับการสร้างหน้าตั้งค่าบัญชีผู้ใช้
   - **Adaptive MFA** (_Adaptive MFA: ขอ MFA เฉพาะเมื่อการลงชื่อเข้าใช้ดูเสี่ยง เช่น ประเทศใหม่ / ไม่ได้ใช้งานนาน_): ใช้ MFA เฉพาะเมื่อการลงชื่อเข้าใช้ดูผิดปกติ เพื่อให้การลงชื่อเข้าใช้ที่มีความเสี่ยงต่ำเป็นไปอย่างราบรื่น ในขณะที่การลงชื่อเข้าใช้ที่น่าสงสัยจะได้รับการยืนยันเพิ่มเติม Logto จะประเมินตามกฎความเสี่ยงในตัว (ประเทศใหม่, geo velocity, ไม่ได้ใช้งานนาน, สัญญาณ IP ที่ไม่น่าเชื่อถือ) โหมดนี้ขึ้นอยู่กับการตั้งค่า MFA ที่มีอยู่ (ต้องเปิดใช้งานอย่างน้อย 1 ปัจจัย) ใช้กับขั้นตอนลงชื่อเข้าใช้ของผู้ใช้ปลายทาง และไม่พึ่งพาการตรวจลายนิ้วมืออุปกรณ์ ดู [Adaptive MFA](/end-user-flows/mfa/adaptive-mfa) สำหรับเกณฑ์กฎ, ข้อกำหนด edge header และรายละเอียด webhook
   - **Mandatory MFA** (_Mandatory MFA: บังคับให้ผู้ใช้ทุกคนทำ MFA ทุกครั้งที่ลงชื่อเข้าใช้_): บังคับให้ผู้ใช้ทุกคนทำ MFA ทุกครั้งที่ลงชื่อเข้าใช้ ผู้ใช้ที่ยังไม่ได้ตั้งค่า MFA ต้องตั้งค่าก่อนจึงจะดำเนินการต่อได้
   - เมื่อเลือก **Optional MFA** ให้ตั้งค่านโยบาย **MFA set-up prompt**:
     - **Do not ask users to set up MFA**: จะไม่แจ้งให้ผู้ใช้ตั้งค่า MFA ระหว่างลงชื่อเข้าใช้หรือสมัครสมาชิก
     - **Ask users to set up MFA during registration (skippable, one-time prompt)**: ผู้ใช้ใหม่จะถูกแจ้งให้ตั้งค่า MFA ระหว่างสมัครสมาชิก และผู้ใช้เดิมจะเห็นแจ้งเตือนนี้ในการลงชื่อเข้าใช้ครั้งถัดไป ผู้ใช้สามารถข้ามขั้นตอนนี้และจะไม่เห็นอีก
     - **Ask users to set up MFA on their next sign-in attempt after registration (skippable, one-time prompt)**: ผู้ใช้ใหม่จะถูกแจ้งให้ตั้งค่า MFA ในการลงชื่อเข้าใช้ครั้งถัดไปหลังสมัครสมาชิก และผู้ใช้เดิมจะเห็นแจ้งเตือนนี้ในการลงชื่อเข้าใช้ครั้งถัดไป ผู้ใช้สามารถข้ามขั้นตอนนี้และจะไม่เห็นอีก
   - เมื่อเลือก **Adaptive MFA** จะรองรับเฉพาะนโยบาย **MFA set-up prompt** แบบบังคับสองแบบเท่านั้น (**Do not ask users to set up MFA** จะไม่สามารถเลือกได้):
     - **Ask users to set up MFA during registration (non-skippable)**: ผู้ใช้ใหม่ต้องตั้งค่า MFA ระหว่างสมัครสมาชิก และผู้ใช้เดิมที่ยังไม่มี MFA ต้องตั้งค่าในการลงชื่อเข้าใช้ครั้งถัดไป
     - **Ask users to set up MFA on their next sign-in attempt after registration (non-skippable)**: ผู้ใช้ใหม่ต้องตั้งค่า MFA ในการลงชื่อเข้าใช้ครั้งถัดไปหลังสมัครสมาชิก และผู้ใช้เดิมที่ยังไม่มี MFA ต้องตั้งค่าในการลงชื่อเข้าใช้ครั้งถัดไป

เมื่อเลือก **Optional MFA** พร้อมเปิดใช้งานการแจ้งเตือน (`Ask users to set up MFA during registration (skippable, one-time prompt)` หรือ `Ask users to set up MFA on their next sign-in attempt after registration (skippable, one-time prompt)`), Logto จะแสดงหน้าคอนเฟิร์มเปิดใช้งาน MFA ชื่อ `Turn on 2-step verification` ก่อน ผู้ใช้สามารถเลือก `Enable 2-step verification` เพื่อดำเนินการตั้งค่า MFA หรือข้ามและจบขั้นตอนลงชื่อเข้าใช้/สมัครสมาชิกโดยไม่เปิด MFA ภายใต้ **Adaptive MFA** หรือ **Mandatory MFA** ผู้ใช้จะเข้าสู่ขั้นตอนผูก MFA โดยตรงโดยไม่เห็นหน้าคอนเฟิร์ม `Turn on 2-step verification`

:::tip
หากคุณต้องการแจ้งเตือนผู้ใช้อีกครั้งหลังจากที่ข้ามการลงทะเบียน MFA ให้รีเซ็ตสถานะ skip ของพวกเขาเพื่อให้หน้าตั้งค่าปรากฏในการลงชื่อเข้าใช้ครั้งถัดไป ผู้ดูแลระบบสามารถใช้ Management API (`PATCH /api/users/{userId}/logto-configs`) และนักพัฒนาที่สร้าง flow แบบ self-service สามารถเรียก Account API (`PATCH /api/my-account/logto-configs`) [Management API reference](https://openapi.logto.io/operation/operation-updateuserlogtoconfigs) · [Account API reference](https://openapi.logto.io/operation/operation-updatelogtoconfig)
:::

### การลงทะเบียน MFA ด้วยอีเมลและ SMS \{#email-and-sms-mfa-enrollment}

รหัสยืนยันอีเมลและ SMS จะถูกส่งไปยังอีเมลหลักและหมายเลขโทรศัพท์หลักของผู้ใช้ การตั้งค่า **Email/SMS 2-step verification** จะกำหนดว่าผู้ใช้ใดจะมีปัจจัยเหล่านี้ ตัวเลือกนี้จะปรากฏเมื่อเปิดใช้งานปัจจัยรหัสยืนยัน SMS หรืออีเมล และใช้กับทั้งสองปัจจัย

- **ผู้ใช้ทุกคนที่มีอีเมลหรือเบอร์โทรศัพท์ที่ยืนยันแล้ว**: ผู้ใช้ที่มีอีเมลหลักจะมี MFA อีเมล และผู้ใช้ที่มีเบอร์โทรหลักจะมี MFA SMS โดยไม่ต้องตั้งค่าเพิ่มเติม ผู้ใช้ที่สมัครด้วยอีเมลหรือเบอร์โทรที่ยืนยันแล้วจะมีปัจจัยนี้ทันที
- **เฉพาะผู้ใช้ที่ตั้งค่าเอง**: ผู้ใช้จะมี MFA อีเมลหรือ SMS ก็ต่อเมื่อได้ตั้งค่าเอง: โดยการยืนยันรหัสใน flow ตั้งค่า MFA, ใน [Account Center](/end-user-flows/account-settings/by-account-center-ui) หรือผ่าน [Account API](/end-user-flows/account-settings/by-account-api#manage-email-and-sms-mfa) หรือเมื่อผู้ดูแลระบบเพิ่มให้ผ่าน [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) การมีอีเมลหรือเบอร์โทรที่ยืนยันแล้วเพียงอย่างเดียวจะไม่เปิด MFA ดังนั้นคุณสามารถเสนออีเมลหรือ SMS เป็นตัวเลือก MFA หนึ่งถัดจากแอปยืนยันตัวตนและ passkey โดยไม่ต้องลงทะเบียนผู้ใช้ทุกคน

ผู้เช่าใหม่จะใช้ **เฉพาะผู้ใช้ที่ตั้งค่าเอง** เป็นค่าเริ่มต้น ผู้เช่าที่สร้างก่อนหน้านี้จะใช้ **ผู้ใช้ทุกคนที่มีอีเมลหรือเบอร์โทรศัพท์ที่ยืนยันแล้ว** จนกว่าคุณจะเปลี่ยน ใน Management API การตั้งค่านี้คือ `mfa.verificationCodeEnrollment` ของ [sign-in experience](https://openapi.logto.io/operation/operation-updatesigninexp) โดยมีค่า `Implicit` และ `Explicit` การอัปเดต `mfa` จะเขียนทับทั้งอ็อบเจกต์ หากไม่ระบุ `verificationCodeEnrollment` ขณะอัปเดต `mfa` จะรีเซ็ตเป็น `Implicit`

Logto จะบันทึกการตั้งค่า MFA อีเมลหรือ SMS ของแต่ละผู้ใช้ในทั้งสองโหมด โดยบันทึกเฉพาะตัวเลือก ไม่ใช่ที่อยู่: ข้อมูลนี้จะยังคงอยู่เมื่อผู้ใช้เปลี่ยนหรือเอาอีเมล/เบอร์โทรหลักออก และจะถูกละเว้นขณะที่ผู้ใช้ไม่มีอีเมล/เบอร์โทร หากผู้ใช้เพิ่มที่อยู่ใหม่ในภายหลัง จะนับใหม่อีกครั้ง

**การเปลี่ยนโหมด**

การเปลี่ยนโหมดมีผลทันทีและไม่เปลี่ยนข้อมูลผู้ใช้ใด ๆ Console จะขอให้คุณยืนยัน

- **ไปยัง เฉพาะผู้ใช้ที่ตั้งค่าเอง**: MFA อีเมลและ SMS จะหยุดนับสำหรับผู้ใช้ที่ยังไม่ได้ตั้งค่าเอง ผู้ใช้ที่มีปัจจัยเดียวคืออีเมลหรือเบอร์โทรจะถือว่าไม่มี MFA: จะไม่ถูกขอให้ยืนยันระหว่างลงชื่อเข้าใช้ และจะถูกขอให้ตั้งค่าปัจจัยเมื่อมีนโยบาย MFA กำหนดหรือแจ้งเตือน Logto จะไม่ลงทะเบียนใครโดยอัตโนมัติ หากต้องการให้ผู้ใช้บางคนยังมี MFA อีเมลหรือ SMS ให้เพิ่มให้พวกเขาผ่าน [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) ก่อนเปลี่ยน
- **ไปยัง ผู้ใช้ทุกคนที่มีอีเมลหรือเบอร์โทรศัพท์ที่ยืนยันแล้ว**: ผู้ใช้ที่มีอีเมลหรือเบอร์โทรหลักจะมี MFA อีเมลหรือ SMS อีกครั้ง รวมถึงผู้ใช้ที่ยังไม่ได้ตั้งค่าเอง

### การตั้งค่า MFA ระดับองค์กร \{#organization-level-mfa-configuration}

สำหรับผลิตภัณฑ์ที่มีสถาปัตยกรรมหลายผู้เช่าและรองรับ [องค์กร](/organizations) โดยส่วนใหญ่คุณไม่จำเป็นต้องบังคับ MFA กับผู้ใช้ทุกคน แต่สามารถเปิด MFA ในแต่ละองค์กรได้ เพื่อปรับตามความต้องการของลูกค้าแต่ละราย ดูวิธีเริ่มต้นที่ [บังคับ MFA สำหรับสมาชิกองค์กร](/organizations/organization-management#require-mfa-for-organization-members)

เมื่อเลือก **Optional MFA** ในดรอปดาวน์ **Require MFA** Console จะแสดงการตั้งค่า **MFA setup prompt for users after organization enables MFA** ให้ตั้งค่าเป็น **Ask users to set up MFA on next sign-in (non-skippable)** เพื่อให้สมาชิกองค์กรที่บังคับ MFA ต้องตั้งค่า MFA ในการลงชื่อเข้าใช้ครั้งถัดไปและไม่สามารถข้ามได้ (การตั้งค่านี้จะซ่อนใน Console และไม่ถูกบันทึกเมื่อเลือก **Adaptive MFA** หรือ **Mandatory MFA**)

ภายใต้ **Adaptive MFA** การลงชื่อเข้าใช้ที่มีความเสี่ยงต่ำและไม่เข้าเกณฑ์กฎความเสี่ยงจะไม่ถูกขอ MFA verification แม้ผู้ใช้จะเปิด **Require MFA setup** รายบุคคลหรืออยู่ในองค์กรที่เปิด `isMfaRequired`

### แนะนำให้เพิ่มปัจจัย MFA อื่น \{#suggest-adding-another-mfa-factor}

ใน <CloudLink to="/mfa">Console > Multi-factor authentication</CloudLink> สวิตช์ **Suggest adding another MFA factor** (เปิดใช้งานโดยค่าเริ่มต้น; ควบคุมโดย `mfa.skipAdditionalBindingSuggestion` ใน Sign-in Experience API) จะกระตุ้นให้ผู้ใช้เพิ่มปัจจัย MFA อื่นระหว่างสมัครสมาชิกหรือเข้าสู่ระบบเมื่อ:

- ปัจจัย MFA เดียวของผู้ใช้คืออีเมล เบอร์โทร หรือ passkey ที่ใช้ลงชื่อเข้าใช้ และ
- มีปัจจัย MFA อื่นอย่างน้อยหนึ่งรายการเปิดใช้งานใน tenant

ผู้ใช้สามารถข้ามการแจ้งเตือนนี้ได้ เมื่อข้าม Logto จะบันทึก `mfa.additionalBindingSuggestionSkipped: true` ใน `logtoConfig` ของผู้ใช้เพื่อไม่ให้แจ้งเตือนนี้อีกในการลงชื่อเข้าใช้ครั้งถัดไป คุณสามารถอัปเดตหรือรีเซ็ต flag นี้ผ่าน [Account API](/end-user-flows/account-settings/by-account-api) (`PATCH /api/my-account/logto-configs` พร้อม `{ "mfa": { "additionalBindingSuggestionSkipped": false } }`; หมายเหตุว่า `GET /api/my-account/logto-configs` และ `GET /api/users/{userId}/logto-configs` จะไม่คืนค่าฟิลด์นี้)

### ข้อกำหนด MFA รายผู้ใช้ \{#per-user-mfa-requirement}

ผู้ดูแลระบบสามารถบังคับให้ผู้ใช้แต่ละรายต้องตั้งค่า MFA โดยไม่ขึ้นกับการตั้งค่า **Optional MFA** ของ tenant:

- **ใน Console**: เปิด <CloudLink to="/users">Console > User management</CloudLink> เลือกผู้ใช้ และเปิด **Require MFA setup** ในส่วน **Multi-factor authentication**
- **ผ่าน Management API**: เรียก `PATCH /api/users/{userId}/logto-configs` พร้อม `{ "mfa": { "required": true } }` (และอ่านค่าด้วย `GET /api/users/{userId}/logto-configs`) ดู [การตั้งค่าบัญชีผ่าน Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management)

ผู้ใช้ปลายทางไม่สามารถแก้ไข `mfa.required` ผ่าน Account API (`PATCH /api/my-account/logto-configs`); สำหรับลูกค้า self-service จะอ่านได้อย่างเดียวที่ `required` ใน `GET /api/my-account/mfa-settings`

เมื่อ `mfa.required` รายผู้ใช้เป็น `true` ผู้ใช้ต้องตั้งค่า MFA อย่างน้อยหนึ่งปัจจัยก่อนจบการลงชื่อเข้าใช้และไม่สามารถข้ามได้ ภายใต้ **Optional MFA** จะบังคับ MFA verification ระหว่างลงชื่อเข้าใช้แม้ผู้ใช้จะเปิด `skipMfaOnSignIn` หรือตั้งค่า `enabled: false` ภายใต้ **Adaptive MFA** การลงชื่อเข้าใช้ที่มีความเสี่ยงต่ำและไม่เข้าเกณฑ์กฎความเสี่ยงจะไม่ถูกขอ MFA verification

## กระบวนการ MFA ของผู้ใช้ \{#mfa-user-flow}

### กระบวนการตั้งค่า MFA \{#mfa-set-up-flow}

เมื่อเปิดใช้งาน MFA ผู้ใช้อาจถูกแจ้งให้ตั้งค่า MFA ระหว่างลงชื่อเข้าใช้หรือสมัครสมาชิก ผู้ใช้สามารถข้ามขั้นตอนนี้ได้เฉพาะเมื่อเลือก **Optional MFA** ใน **Require MFA** policy

1. **เข้าสู่หน้าลงชื่อเข้าใช้หรือสมัครสมาชิก**: ผู้ใช้ไปยังหน้าลงชื่อเข้าใช้หรือสมัครสมาชิก
2. **ดำเนินการลงชื่อเข้าใช้หรือสมัครสมาชิก**: ผู้ใช้ดำเนินการยืนยันตัวตนใน flow ลงชื่อเข้าใช้หรือสมัครสมาชิก
   - หากเลือก **Optional MFA** พร้อมเปิดแจ้งเตือน Logto จะแสดงหน้าคอนเฟิร์ม `Turn on 2-step verification` ให้ผู้ใช้ข้ามหรือคลิก `Enable 2-step verification` เพื่อดำเนินการ
   - ภายใต้ **Adaptive MFA** หรือ **Mandatory MFA** ผู้ใช้จะเข้าสู่ขั้นตอนผูก MFA โดยตรงโดยไม่เห็นหน้าคอนเฟิร์ม `Turn on 2-step verification` และไม่สามารถข้ามได้
3. **ตั้งค่าปัจจัย MFA หลัก**: ผู้ใช้จะถูกแจ้งให้ตั้งค่าปัจจัย MFA หลัก (passkey, Authenticator app OTP, SMS code หรือ email code)
   - หากเปิดใช้งานหลายปัจจัยหลัก ผู้ใช้สามารถเลือกตัวเลือกที่ต้องการ
   - หากปัจจัยหลักตรงกับ identifier ที่ใช้สมัคร (เช่น SMS หรืออีเมล) จะถือว่ายืนยันแล้ว ผู้ใช้ไม่ต้องยืนยันซ้ำ:
     - ด้วย **ผู้ใช้ทุกคนที่มีอีเมลหรือเบอร์โทรศัพท์ที่ยืนยันแล้ว** จะถือว่าเป็นปัจจัยของผู้ใช้แล้ว และไปขั้นตอนถัดไปได้ทันที (เช่น "เพิ่ม 2-step verification อื่น" หรือ "บันทึกรหัสสำรอง")
     - ด้วย **เฉพาะผู้ใช้ที่ตั้งค่าเอง** จะเสนอเหมือนปัจจัยอื่น และจะไม่ส่งรหัสซ้ำเมื่อผู้ใช้ตั้งค่า ดู [การลงทะเบียน MFA ด้วยอีเมลและ SMS](#email-and-sms-mfa-enrollment)
   - หากเลือก **Optional MFA** ใน **Require MFA** policy ผู้ใช้สามารถข้ามขั้นตอนนี้โดยกดปุ่ม "Skip"
4. **ตั้งค่าปัจจัย MFA สำรอง**: หากเปิดใช้งาน **Backup codes** ผู้ใช้จะถูกแจ้งให้บันทึกรหัสสำรองหลังตั้งค่าปัจจัยหลักเสร็จ รหัสสำรองจะถูกสร้างอัตโนมัติและแสดงให้ผู้ใช้ดาวน์โหลดและเก็บไว้อย่างปลอดภัย ผู้ใช้ต้องยืนยันรหัสสำรองด้วยตนเองเพื่อจบกระบวนการตั้งค่า MFA

### กระบวนการยืนยัน MFA \{#mfa-verification-flow}

ผู้ใช้ที่ตั้งค่า MFA แล้วจะถูกแจ้งให้ยืนยันตัวตนด้วยปัจจัย MFA ที่ตั้งค่าไว้ระหว่างลงชื่อเข้าใช้ ปัจจัยที่ใช้ขึ้นอยู่กับการตั้งค่า MFA ใน Logto และการตั้งค่าของผู้ใช้

หากผู้ใช้ลงชื่อเข้าใช้ด้วย [passkey sign-in](/end-user-flows/sign-up-and-sign-in/passkey-sign-in) Logto จะข้ามขั้นตอน MFA verification แยกต่างหาก เพราะ passkey ที่ใช้ลงชื่อเข้าใช้ถือเป็นปัจจัย MFA แบบ WebAuthn อยู่แล้ว

- หากผู้ใช้มีปัจจัย MFA เพียงหนึ่งรายการ จะถูกขอให้ยืนยันปัจจัยนั้นโดยตรง
- หากผู้ใช้มีปัจจัย MFA หลายรายการ Logto จะเรียงลำดับตามลำดับความสำคัญและเปิดปัจจัยแรกที่มีให้โดยตรง:
  1. **Passkey (WebAuthn)**
  2. **Authenticator app OTP (TOTP)**
  3. **SMS verification code**
  4. **Email verification code**
  5. **Backup codes**
- เมื่อมีปัจจัย MFA สองรายการขึ้นไป หน้ายืนยันจะแสดงลิงก์ **Try another method to verify** เพื่อให้ผู้ใช้เลือกวิธีอื่นที่มี (รวมถึงรหัสสำรองหากเปิดใช้งาน)

<img src="/img/assets/verify-mfa.png" alt="MFA verification flow" />

### กฎการผูก MFA ระหว่างลงชื่อเข้าใช้และข้อยกเว้น \{#sign-in-binding-rules-and-exemptions}

โปรดคำนึงถึงพฤติกรรมต่อไปนี้เมื่อออกแบบ journey MFA:

- **แจ้งเตือนรหัสสำรองใหม่**: เมื่อเปิดใช้งาน **Backup codes** และผู้ใช้มีปัจจัย MFA อื่นอยู่แล้ว Logto จะเตือนให้สร้างและบันทึกรหัสสำรองชุดใหม่ระหว่างลงชื่อเข้าใช้ หากรหัสเดิมถูกใช้หมดหรือเปิดใช้งาน **Backup codes** หลังจากลงทะเบียน MFA ครั้งแรก
- **ต้องยืนยันปัจจัยก่อนผูกระหว่างลงชื่อเข้าใช้**: ระหว่าง interaction `SignIn` ที่ผู้ใช้มีปัจจัย MFA อยู่แล้ว การผูกปัจจัยใหม่ (รวมถึงการบันทึกรหัสสำรองใหม่หรือการแจ้งเตือน "Suggest adding another MFA factor") ต้องผ่านการยืนยัน MFA ก่อน (หรือเข้าสู่ระบบด้วย passkey sign-in หรือ enterprise SSO) การลงชื่อเข้าใช้ที่ข้าม MFA verification เช่น [trusted device](/end-user-flows/mfa/trusted-devices), [Adaptive MFA](/end-user-flows/mfa/adaptive-mfa) ที่ไม่เข้าเกณฑ์กฎ หรือผู้ใช้ข้าม **Optional MFA** (`skipMfaOnSignIn` / `enabled: false`) จะไม่สามารถผูกปัจจัย MFA ใหม่ใน flow นั้นได้ ผู้ใช้ใน session เหล่านี้สามารถเพิ่มปัจจัยภายหลังผ่าน Account Center หรือ [Account API](/end-user-flows/account-settings/by-account-api)
- **ข้อยกเว้น Enterprise SSO**: การลงชื่อเข้าใช้หรือสมัครสมาชิกผ่าน [Enterprise SSO](/end-user-flows/enterprise-sso) จะข้ามการยืนยัน MFA และการแจ้งเตือนตั้งค่า MFA ของ tenant ใน interaction นั้น (เว้นแต่ client ขอ MFA โดยตรงผ่าน `acr_values` เช่น `urn:logto:acr:mfa`)
- **ข้อยกเว้นลืมรหัสผ่าน**: flow [ลืมรหัสผ่าน](/end-user-flows/sign-up-and-sign-in/reset-password) จะข้ามการยืนยัน MFA และการแจ้งเตือนตั้งค่า MFA

## การจัดการ MFA \{#mfa-management}

นอกเหนือจากการตั้งค่าเบื้องต้นระหว่างลงชื่อเข้าใช้/สมัครสมาชิก ผู้ใช้สามารถจัดการการตั้งค่า MFA ได้ด้วยตนเองผ่านศูนย์บัญชี (account center) เพื่อความยืดหยุ่นในการผูกหรือยกเลิกปัจจัย MFA ตามต้องการ

### การสร้างศูนย์บัญชี \{#building-an-account-center}

คุณสามารถสร้างศูนย์บัญชีที่ครบถ้วนโดยใช้ [Account API](/end-user-flows/account-settings/by-account-api) ของ Logto ซึ่งช่วยให้ผู้ใช้:

- **ผูกปัจจัย MFA ใหม่**: เพิ่มแอปยืนยันตัวตน, passkey หรือสร้างรหัสสำรองใหม่
- **ยกเลิกปัจจัย MFA ที่มีอยู่**: ลบวิธี MFA ที่ไม่ต้องการใช้
- **ดูสถานะ MFA ปัจจุบัน**: ตรวจสอบว่าตั้งค่า MFA อะไรไว้บ้าง

### แจ้งเตือนตั้งค่า MFA หลังเข้าสู่ระบบ \{#post-login-mfa-setup-prompts}

สำหรับแอปที่ไม่บังคับ MFA ระหว่างสมัครสมาชิก คุณสามารถสร้างการแจ้งเตือนอัจฉริยะเพื่อกระตุ้นให้ผู้ใช้ตั้งค่า MFA:

- **แจ้งเตือนตามเงื่อนไข**: แนะนำการตั้งค่า MFA ตามพฤติกรรมผู้ใช้หรือมูลค่าบัญชี
- **แดชบอร์ดความปลอดภัย**: แสดงคะแนนความปลอดภัยที่ดีขึ้นเมื่อเปิด MFA
- **การ onboarding แบบค่อยเป็นค่อยไป**: นำเสนอการตั้งค่า MFA เป็นส่วนหนึ่งของ flow เพิ่มความปลอดภัยทีละขั้น

เรียนรู้เพิ่มเติมเกี่ยวกับการนำรูปแบบเหล่านี้ไปใช้กับ [Account API](/end-user-flows/account-settings/by-account-api)

### จัดการ MFA ของผู้ใช้ใน Console \{#manage-users-mfa-in-console}

ใน <CloudLink to="/user"> Console > User management</CloudLink> ผู้ดูแลระบบสามารถจัดการการตั้งค่า MFA ของผู้ใช้ได้อย่างมีประสิทธิภาพ:

- **ดูสถานะ MFA ของผู้ใช้**: ตรวจสอบว่าผู้ใช้แต่ละรายเปิดใช้งาน MFA อะไรบ้าง มี tip แสดงปัจจัยอีเมลหรือ SMS ที่นับเพราะผู้ใช้มีอีเมล/เบอร์โทรที่ยืนยันแล้ว และปัจจัยที่ผู้ใช้ตั้งค่าเองแต่ไม่ถูกนับ เช่น ปัจจัยถูกปิดใช้งาน
- **ลบ MFA ของผู้ใช้**: ลบปัจจัย MFA ที่บันทึกไว้ทีละรายการ แถวรหัสยืนยันอีเมลหรือ SMS แบบ implicit ไม่สามารถลบได้โดยตรง และเมื่อเปิด passkey sign-in แถว passkey (WebAuthn) จะไม่มีปุ่มลบที่นี่และจัดการในส่วน **Passkeys** ของหน้ารายละเอียดผู้ใช้เดียวกัน

หากต้องการเพิ่ม MFA อีเมลหรือ SMS ให้ผู้ใช้ ให้ใช้ [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management)

### จะเกิดอะไรขึ้นเมื่อผู้ดูแลระบบลบปัจจัย MFA ของผู้ใช้ทั้งหมด? \{#what-happens-when-administrators-remove-users-existing-mfa-factors}

เมื่อผู้ดูแลระบบลบปัจจัย MFA หลักทั้งหมดของผู้ใช้ (passkey, authenticator app OTP, SMS หรืออีเมล) จะเกิดสถานการณ์ต่อไปนี้ในการลงชื่อเข้าใช้ครั้งถัดไปของผู้ใช้:

**สถานการณ์ที่ 1: ไม่มีปัจจัย MFA เหลืออยู่**

- หากไม่มีปัจจัย MFA ใด ๆ (รวมถึงไม่มีรหัสสำรอง) และ [นโยบาย MFA](#global-mfa-configuration) กำหนดให้ต้องใช้ MFA ผู้ใช้จะสามารถลงชื่อเข้าใช้โดยไม่ต้องยืนยัน MFA และจะถูกแจ้งให้ตั้งค่า MFA ใหม่ทันที

**สถานการณ์ที่ 2: ยังมีรหัสสำรองเหลืออยู่**

- หากยังมีรหัสสำรอง ผู้ใช้ต้องยืนยันด้วยรหัสสำรองก่อนระหว่างลงชื่อเข้าใช้
- หลังยืนยันรหัสสำรองสำเร็จ ผู้ใช้จะถูกแจ้งให้ตั้งค่าปัจจัย MFA หลักใหม่
- ผู้ใช้จะสามารถข้ามขั้นตอนนี้ได้หรือไม่ขึ้นอยู่กับนโยบาย MFA ที่ตั้งไว้
- วิธีนี้ช่วยป้องกันไม่ให้ผู้ใช้ถูกล็อกบัญชีเมื่อไม่มีปัจจัยหลักเหลืออยู่

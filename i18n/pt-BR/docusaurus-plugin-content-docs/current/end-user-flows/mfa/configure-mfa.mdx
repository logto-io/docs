# Configurar MFA

## Configurar as definições de MFA no Logto \{#configure-mfa-settings-in-logto}

O Logto oferece opções flexíveis de configuração de MFA para atender a diferentes requisitos de segurança. Você pode configurar o MFA em nível global para todos os usuários ou habilitá-lo por organização para aplicações multi-tenant.

### Configuração global de MFA \{#global-mfa-configuration}

Siga estes passos para habilitar MFAs no fluxo de login dos usuários do Logto:

1. Navegue até: <CloudLink to="/mfa">Console > Autenticação multifatorial (MFA)</CloudLink>.
2. Habilite os fatores de verificação suportados para seus usuários.
   1. Fatores primários:
      - [Chaves de acesso (WebAuthn)](/end-user-flows/mfa/webauthn): Uma opção de alta segurança adequada para produtos web que suportam biometria de dispositivo ou chaves de segurança, garantindo proteção robusta.
      - [OTP de aplicativo autenticador](/end-user-flows/mfa/authenticator-app-otp): O método mais comum e amplamente aceito. Use uma senha única baseada em tempo (TOTP) gerada por um aplicativo autenticador como Google Authenticator ou Authy.
      - [Verificação por SMS](/end-user-flows/mfa/sms-mfa): Um método conveniente que envia códigos de verificação únicos via SMS para o número de telefone registrado do usuário, ideal para quem prefere autenticação baseada em celular sem aplicativos adicionais.
      - [Verificação por e-mail](/end-user-flows/mfa/email-mfa): Um método amplamente acessível que entrega códigos de verificação únicos ao endereço de e-mail registrado do usuário, adequado para usuários em todas as plataformas e dispositivos.
   2. Fatores de backup:
      - [Códigos de backup](/end-user-flows/mfa/backup-codes): Serve como opção de backup quando os usuários não conseguem verificar nenhum dos fatores primários mencionados acima. Habilitar esta opção reduz o atrito para o acesso bem-sucedido dos usuários.
   3. Se a verificação por SMS ou e-mail estiver habilitada, escolha quais usuários terão acesso em **Verificação em 2 etapas por e-mail/SMS**. Veja [Inscrição em MFA por e-mail e SMS](#email-and-sms-mfa-enrollment).
3. Escolha a política **Exigir MFA** no menu suspenso. Esta política controla quando os usuários devem concluir o MFA durante o login:
   - **MFA opcional** (_Optional MFA: Permite que os usuários escolham habilitar MFA para a segurança de sua própria conta_): Permite que os usuários decidam se desejam habilitar MFA para a segurança de sua conta. Eles podem pular a configuração do MFA durante o login e configurá-lo depois na página de configurações de conta de autoatendimento. [Saiba mais](/end-user-flows/account-settings/) sobre como implementar uma página de configurações de conta do usuário.
   - **MFA adaptativo** (_Adaptive MFA: Solicita MFA apenas quando um login parece arriscado (por exemplo, novo país / longa inatividade)_): Aplica MFA apenas quando um login parece incomum, permitindo que logins de baixo risco sejam mais suaves enquanto logins suspeitos recebem verificação extra. Para tomar essa decisão, o Logto avalia regras de risco contextuais internas (novo país, velocidade geográfica, longa inatividade e sinais de IP não confiável). Este modo depende da configuração existente de MFA (pelo menos um fator de MFA deve estar habilitado), aplica-se aos fluxos de login do usuário final e não depende de impressão digital do dispositivo. Veja [MFA adaptativo](/end-user-flows/mfa/adaptive-mfa) para limites de regras, pré-requisitos de cabeçalho de borda e detalhes de webhook.
   - **MFA obrigatório** (_Mandatory MFA: Exige que todos os usuários concluam MFA toda vez que fizerem login_): Exige que todos os usuários concluam MFA em cada login. Usuários que não configuraram MFA devem concluir a configuração antes de continuar.
   - Quando **MFA opcional** estiver selecionado, configure a política **Prompt de configuração de MFA**:
     - **Não solicitar aos usuários que configurem MFA**: Os usuários não serão solicitados a configurar MFA durante o login ou registro.
     - **Solicitar aos usuários que configurem MFA durante o registro (pode ser ignorado, prompt único)**: Novos usuários serão solicitados a configurar MFA durante o registro, e usuários existentes verão o prompt no próximo login. Os usuários podem pular esta etapa e ela não aparecerá novamente.
     - **Solicitar aos usuários que configurem MFA na próxima tentativa de login após o registro (pode ser ignorado, prompt único)**: Novos usuários serão solicitados a configurar MFA no próximo login após o registro, e usuários existentes verão o prompt no próximo login. Os usuários podem pular esta etapa e ela não aparecerá novamente.
   - Quando **MFA adaptativo** estiver selecionado, apenas as duas políticas de **Prompt de configuração de MFA** não ignoráveis são suportadas (**Não solicitar aos usuários que configurem MFA** não está disponível):
     - **Solicitar aos usuários que configurem MFA durante o registro (não pode ser ignorado)**: Novos usuários devem concluir a configuração de MFA durante o registro, e usuários existentes sem MFA devem concluí-la no próximo login.
     - **Solicitar aos usuários que configurem MFA na próxima tentativa de login após o registro (não pode ser ignorado)**: Novos usuários devem concluir a configuração de MFA no próximo login após o registro, e usuários existentes sem MFA devem concluí-la no próximo login.

Quando **MFA opcional** está selecionado com um prompt de configuração habilitado (`Solicitar aos usuários que configurem MFA durante o registro (pode ser ignorado, prompt único)` ou `Solicitar aos usuários que configurem MFA na próxima tentativa de login após o registro (pode ser ignorado, prompt único)`), o Logto exibe primeiro uma página de confirmação para ativar o MFA intitulada `Ativar verificação em 2 etapas`. Os usuários podem escolher `Ativar verificação em 2 etapas` para continuar com a vinculação do MFA ou pular o prompt e concluir o fluxo de login ou cadastro atual sem ativar o MFA. Sob **MFA adaptativo** ou **MFA obrigatório**, os usuários vão direto para a vinculação do fator de MFA sem ver a página de confirmação `Ativar verificação em 2 etapas`.

:::tip
Se você precisar solicitar novamente a inscrição em MFA para um usuário que pulou o processo, redefina o estado de pulo dele para que a tela de configuração apareça na próxima vez que ele fizer login. Os administradores podem usar a Management API (`PATCH /api/users/{userId}/logto-configs`), e desenvolvedores que constroem fluxos de autoatendimento podem chamar a Account API (`PATCH /api/my-account/logto-configs`). [Referência da Management API](https://openapi.logto.io/operation/operation-updateuserlogtoconfigs) · [Referência da Account API](https://openapi.logto.io/operation/operation-updatelogtoconfig)
:::

### Inscrição em MFA por e-mail e SMS \{#email-and-sms-mfa-enrollment}

Códigos de verificação por e-mail e SMS são enviados para o endereço de e-mail principal e número de telefone principal do usuário. A configuração **Verificação em 2 etapas por e-mail/SMS** decide quais usuários terão esses fatores. Ela aparece quando o fator de código de verificação por SMS ou e-mail está habilitado e se aplica a ambos os fatores.

- **Todo usuário com e-mail ou telefone verificado**: Todo usuário com endereço de e-mail principal tem MFA por e-mail, e todo usuário com número de telefone principal tem MFA por SMS, sem precisar configurar. Um usuário que se cadastra com e-mail ou telefone verificado já possui esse fator.
- **Apenas usuários que configurarem**: Um usuário só terá MFA por e-mail ou SMS após configurar: verificando um código no fluxo de configuração de MFA, no [Account Center](/end-user-flows/account-settings/by-account-center-ui) ou através da [Account API](/end-user-flows/account-settings/by-account-api#manage-email-and-sms-mfa), ou quando um administrador adiciona via [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management). Ter um e-mail ou telefone verificado por si só não habilita o MFA, então você pode oferecer e-mail ou SMS como uma opção de MFA ao lado de aplicativos autenticadores e chaves de acesso, sem inscrever todos os usuários.

Novos tenants usam **Apenas usuários que configurarem** por padrão. Tenants criados anteriormente mantêm **Todo usuário com e-mail ou telefone verificado** até que você altere. Na Management API, essa configuração é `mfa.verificationCodeEnrollment` da [experiência de login](https://openapi.logto.io/operation/operation-updatesigninexp), com os valores `Implicit` e `Explicit`. Como atualizar `mfa` substitui todo o objeto, omitir `verificationCodeEnrollment` ao atualizar `mfa` redefine para `Implicit`.

O Logto registra cada configuração de MFA por e-mail ou SMS, em ambos os modos. O registro armazena a escolha, não o endereço: permanece quando o usuário altera ou remove o e-mail ou telefone principal, e é ignorado enquanto o usuário não tiver nenhum. Se o usuário adicionar um novo endereço depois, conta novamente.

**Mudando de modo**

A mudança tem efeito imediato e não altera nenhum dado do usuário. O Console pede confirmação.

- **Para Apenas usuários que configurarem**: MFA por e-mail e SMS deixa de contar para todo usuário que não configurou. Um usuário cujo único fator era e-mail ou telefone passa a ser tratado como usuário sem MFA: não será solicitado a verificar no login, e só será solicitado a configurar um fator quando sua política de MFA exigir ou sugerir. O Logto não inscreve ninguém automaticamente. Para manter MFA por e-mail ou SMS para usuários específicos, adicione para eles via [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) antes de mudar.
- **Para Todo usuário com e-mail ou telefone verificado**: Todo usuário com e-mail ou telefone principal volta a ter MFA por e-mail ou SMS, incluindo quem não configurou.

### Configuração de MFA por organização \{#organization-level-mfa-configuration}

Para produtos com arquitetura multi-tenant que suportam [Organizações](/organizations), na maioria dos casos não é necessário exigir MFA para todos os usuários. Em vez disso, o MFA pode ser habilitado por organização, permitindo adaptar os requisitos conforme a necessidade de cada cliente. Para começar, consulte [Exigir MFA para membros da organização](/organizations/organization-management#require-mfa-for-organization-members).

Quando **MFA opcional** está selecionado no menu **Exigir MFA**, o Console exibe a configuração **Prompt de configuração de MFA para usuários após a organização habilitar MFA**. Defina como **Solicitar aos usuários que configurem MFA no próximo login (não pode ser ignorado)** para que membros de qualquer organização que exija MFA sejam solicitados a concluir a configuração de MFA no próximo login e não possam pular. (Esta configuração fica oculta no Console e não é salva quando **MFA adaptativo** ou **MFA obrigatório** está selecionado.)

Sob **MFA adaptativo**, logins de baixo risco que não acionam nenhuma regra de risco não são desafiados para verificação de MFA, mesmo para usuários com **Exigir configuração de MFA** habilitado por usuário ou pertencentes a uma organização com `isMfaRequired` habilitado.

### Sugerir adicionar outro fator de MFA \{#suggest-adding-another-mfa-factor}

Em <CloudLink to="/mfa">Console > Autenticação multifatorial (MFA)</CloudLink>, o botão **Sugerir adicionar outro fator de MFA** (habilitado por padrão; controlado por `mfa.skipAdditionalBindingSuggestion` na Sign-in Experience API) sugere ao usuário adicionar outro fator de MFA durante o cadastro ou login quando:

- O único fator de MFA do usuário é o endereço de e-mail, número de telefone ou chave de acesso com o qual ele faz login, e
- Pelo menos outro fator de MFA está habilitado para o tenant.

Os usuários podem pular esse prompt. Quando um usuário ignora a sugestão, o Logto salva `mfa.additionalBindingSuggestionSkipped: true` no `logtoConfig` do usuário para que a sugestão não apareça novamente em futuros logins. Você pode atualizar ou redefinir esse flag via [Account API](/end-user-flows/account-settings/by-account-api) (`PATCH /api/my-account/logto-configs` com `{ "mfa": { "additionalBindingSuggestionSkipped": false } }`; observe que `GET /api/my-account/logto-configs` e `GET /api/users/{userId}/logto-configs` não retornam esse campo).

### Exigência de MFA por usuário \{#per-user-mfa-requirement}

Administradores podem exigir a configuração de MFA para um usuário individual independentemente da configuração de prompt de **MFA opcional** do tenant:

- **No Console**: Abra <CloudLink to="/users">Console > Gerenciamento de usuários</CloudLink>, selecione o usuário e habilite **Exigir configuração de MFA** na seção **Autenticação multifatorial (MFA)**.
- **Via Management API**: Chame `PATCH /api/users/{userId}/logto-configs` com `{ "mfa": { "required": true } }` (e leia com `GET /api/users/{userId}/logto-configs`). Veja [Configurações de conta via Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management).

Usuários finais não podem modificar `mfa.required` pela Account API (`PATCH /api/my-account/logto-configs`); para clientes de autoatendimento, é exposto apenas leitura como `required` em `GET /api/my-account/mfa-settings`.

Quando `mfa.required` por usuário é `true`, o usuário deve configurar pelo menos um fator de MFA antes de concluir o login e não pode pular a configuração. Sob **MFA opcional**, também exige verificação de MFA no login mesmo que o usuário tenha habilitado `skipMfaOnSignIn` ou definido `enabled: false`. Sob **MFA adaptativo**, logins de baixo risco que não acionam nenhuma regra de risco ainda não são desafiados para verificação de MFA.

## Fluxo do usuário MFA \{#mfa-user-flow}

### Fluxo de configuração de MFA \{#mfa-set-up-flow}

Uma vez que o MFA está habilitado, os usuários podem ser solicitados a configurar MFA durante o login e cadastro. Os usuários só podem pular esse processo de configuração quando **MFA opcional** está selecionado na política **Exigir MFA**.

1. **Visite a página de login ou cadastro**: O usuário navega até a página de login ou cadastro.
2. **Conclui o login ou cadastro**: O usuário conclui o processo de verificação de identidade dentro do fluxo de login ou cadastro.
   - Se **MFA opcional** estiver selecionado com um prompt de configuração habilitado, o Logto exibe primeiro a página de confirmação `Ativar verificação em 2 etapas`, onde os usuários podem pular a configuração de MFA ou clicar em `Ativar verificação em 2 etapas` para continuar.
   - Sob **MFA adaptativo** ou **MFA obrigatório**, os usuários vão direto para a vinculação do fator de MFA sem ver a página `Ativar verificação em 2 etapas` e não podem pular a configuração.
3. **Configurar fator primário de MFA**: O usuário é solicitado a configurar seu fator primário de MFA (chave de acesso, OTP de aplicativo autenticador, código SMS ou código de e-mail).
   - Se vários fatores primários estiverem habilitados, o usuário pode escolher a opção preferida.
   - Se o fator primário for o mesmo que o identificador de cadastro (por exemplo, SMS ou e-mail), ele já está pré-verificado, então o usuário não precisa verificar novamente:
     - Com **Todo usuário com e-mail ou telefone verificado**, já é o fator do usuário, e ele segue direto para o próximo passo (por exemplo, "Adicionar outro verificação em 2 etapas" ou "Salve seus fatores de backup").
     - Com **Apenas usuários que configurarem**, é oferecido como qualquer outro fator, e nenhum segundo código é enviado ao configurar. Veja [Inscrição em MFA por e-mail e SMS](#email-and-sms-mfa-enrollment).
   - Se **MFA opcional** estiver selecionado na política **Exigir MFA**, o usuário pode pular esta etapa selecionando o botão "Pular".
4. **Configurar fator de backup de MFA**: Se **Códigos de backup** estiverem habilitados, o usuário será solicitado a salvar os códigos de backup após configurar com sucesso o fator de autenticação primário. Códigos de backup gerados automaticamente serão exibidos para o usuário, que poderá baixá-los e armazená-los com segurança. O usuário deve confirmar manualmente os códigos de backup para concluir o processo de configuração de MFA.

### Fluxo de verificação de MFA \{#mfa-verification-flow}

Usuários que configuraram MFA serão solicitados a verificar sua identidade usando os fatores de MFA configurados durante o login. O fator de verificação dependerá da configuração de MFA no Logto e das configurações do usuário.

Se o usuário fizer login com [login por chave de acesso](/end-user-flows/sign-up-and-sign-in/passkey-sign-in), o Logto pula a etapa separada de verificação de MFA. Isso se aplica porque a chave de acesso usada no login já é um fator de MFA WebAuthn.

- Se o usuário tiver apenas um fator de MFA disponível, ele o verificará diretamente.
- Se o usuário tiver vários fatores de MFA disponíveis, o Logto os ordena em uma ordem de prioridade fixa e abre diretamente o primeiro fator disponível:
  1. **Chave de acesso (WebAuthn)**
  2. **OTP de aplicativo autenticador (TOTP)**
  3. **Código de verificação por SMS**
  4. **Código de verificação por e-mail**
  5. **Códigos de backup**
- Quando dois ou mais fatores de MFA estão disponíveis, a página de verificação exibe um link **Tentar outro método de verificação** para que o usuário possa abrir a lista de seleção de métodos e alternar para qualquer outro fator disponível (incluindo um código de backup único, se habilitado).

### Regras de vinculação e isenções no login \{#sign-in-binding-rules-and-exemptions}

Mantenha o seguinte comportamento em mente ao projetar jornadas de MFA:

- **Solicitação de novo código de backup**: Quando **Códigos de backup** estão habilitados e o usuário já possui outro fator de MFA ativo, o Logto solicita durante o login que o usuário gere e salve um novo conjunto de códigos de backup se todos os códigos anteriores tiverem sido usados ou se **Códigos de backup** foram habilitados após a inscrição inicial do usuário.
- **Fator verificado necessário para vincular durante o login**: Durante uma interação `SignIn` em que o usuário já possui fatores de MFA disponíveis, vincular um novo fator (incluindo salvar códigos de backup regenerados ou seguir o prompt "Sugerir adicionar outro fator de MFA") exige concluir um desafio de verificação de MFA primeiro (ou fazer login via chave de acesso ou SSO corporativo). Logins que ignoram a verificação de MFA—como um [dispositivo confiável](/end-user-flows/mfa/trusted-devices), um login de [MFA adaptativo](/end-user-flows/mfa/adaptive-mfa) de baixo risco que não acionou regra, ou usuário que pulou **MFA opcional** (`skipMfaOnSignIn` / `enabled: false`)—não podem vincular novos fatores de MFA durante esse fluxo de login. Usuários nessas sessões podem adicionar fatores depois via Account Center ou [Account API](/end-user-flows/account-settings/by-account-api).
- **Isenção de SSO corporativo**: Fazer login ou registrar-se via [SSO corporativo (Enterprise SSO)](/end-user-flows/enterprise-sso) ignora a verificação de MFA do tenant e prompts de configuração de MFA durante essa interação (a menos que o MFA seja explicitamente solicitado pelo cliente via `acr_values`, como `urn:logto:acr:mfa`).
- **Isenção de esqueci minha senha**: O fluxo de [Esqueci minha senha](/end-user-flows/sign-up-and-sign-in/reset-password) ignora a verificação de MFA e prompts de configuração de MFA.

## Gerenciamento de MFA \{#mfa-management}

Além da configuração inicial durante o login/cadastro, os usuários podem gerenciar suas configurações de MFA através de um centro de contas de autoatendimento. Isso oferece flexibilidade para os usuários vincularem ou desvincularem fatores de MFA conforme suas necessidades.

### Construindo um centro de contas \{#building-an-account-center}

Você pode construir um centro de contas completo usando a [Account API](/end-user-flows/account-settings/by-account-api) do Logto, que permite aos usuários:

- **Vincular novos fatores de MFA**: Adicionar aplicativos autenticadores adicionais, chaves de acesso ou regenerar códigos de backup
- **Desvincular fatores de MFA existentes**: Remover métodos de MFA que não desejam mais usar
- **Visualizar o status atual do MFA**: Ver quais fatores de MFA estão atualmente configurados

### Prompts de configuração de MFA pós-login \{#post-login-mfa-setup-prompts}

Para aplicações que não exigem MFA durante o registro inicial, você pode implementar prompts inteligentes para incentivar a configuração de MFA:

- **Prompts condicionais**: Exibir recomendações de configuração de MFA com base no comportamento do usuário ou valor da conta
- **Painéis de segurança**: Exibir pontuações de segurança que melhoram quando o MFA está habilitado
- **Onboarding gradual**: Apresentar a configuração de MFA como parte de um fluxo progressivo de aprimoramento de segurança

Saiba mais sobre como implementar esses padrões com a [Account API](/end-user-flows/account-settings/by-account-api).

### Gerenciar MFA do usuário no Console \{#manage-users-mfa-in-console}

No <CloudLink to="/user">Console > Gerenciamento de usuários</CloudLink>, administradores podem gerenciar as configurações de MFA dos usuários de forma eficaz:

- **Visualizar status de MFA do usuário**: Ver quais fatores de MFA estão habilitados para cada usuário. Uma dica marca um fator de e-mail ou SMS que conta apenas porque o usuário tem e-mail ou telefone verificado, e um que o usuário configurou mas não conta, por exemplo, porque o fator está desabilitado.
- **Remover MFA do usuário**: Remover fatores de MFA armazenados um a um. Linhas de código de verificação implícito por e-mail ou SMS não podem ser removidas diretamente desta tabela, e quando o login por chave de acesso está habilitado, linhas de chave de acesso (WebAuthn) não têm botão de remoção aqui e são gerenciadas na seção **Chaves de acesso** na mesma página de detalhes do usuário.

Para adicionar MFA por e-mail ou SMS para um usuário, use a [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management).

### Perguntas frequentes \{#faqs}

<details>
<summary>
### O que acontece quando administradores removem os fatores de MFA existentes do usuário? \{#what-happens-when-administrators-remove-users-existing-mfa-factors}
</summary>
Quando administradores removem todos os fatores primários de MFA de um usuário (chave de acesso, OTP de aplicativo autenticador, SMS ou e-mail), os seguintes cenários ocorrerão no próximo login do usuário:

**Cenário 1: Nenhum fator de MFA restante**

- Se não existirem fatores de MFA (incluindo nenhum código de backup) e a [política de MFA](#global-mfa-configuration) exigir MFA, o usuário poderá fazer login sem verificação de MFA e será imediatamente solicitado a configurar MFA novamente.

**Cenário 2: Códigos de backup ainda existem**

- Se ainda houver códigos de backup disponíveis, o usuário deve primeiro verificar usando um código de backup durante o login.
- Após a verificação bem-sucedida do código de backup, o usuário será solicitado a configurar um novo fator primário de MFA.
- Se o usuário pode pular essa configuração depende da política de MFA configurada.
- Essa abordagem evita que os usuários fiquem bloqueados em suas contas quando não houver fatores primários disponíveis.

 </details>

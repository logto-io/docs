# Service principal

## Introduction \{#introduction}

_Le service principal_ est un service monolithique pour les tâches critiques de Logto. Le code source se trouve dans [`@logto/core`](https://github.com/logto-io/logto/tree/master/packages/core).

:::note
_Le service principal_ et _SDK core_ sont deux concepts distincts. Voir [Convention SDK](/developers/sdk-conventions) pour les différences.
:::

Pour simplifier, nous divisons le service principal en quatre modules majeurs :

<table>
  <thead>
    <tr>
      <td>Nom</td>
      <td>Description</td>
      <td>Chemin de montage</td>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>Fournisseur OIDC</td>
      <td>Un [fournisseur OpenID](https://openid.net/specs/openid-connect-core-1_0.html).</td>
      <td>
        <code>/oidc</code>
      </td>
    </tr>
    <tr>

      <td>Management API, Experience API et Account API.</td>
      <td>
        <code>/api</code>
      </td>
    </tr>
    <tr>
      <td>Proxys frontend</td>
      <td>Proxys HTTP ou service de fichiers statiques pour les projets frontend.</td>

      </td>
    </tr>
  </tbody>
</table>

Les API backend, y compris OIDC, sont construites dans le package `core`, tandis que les proxys frontend dépendent des packages frères correspondants dans le monorepo Logto.

## Fournisseur OIDC \{#oidc-provider}

Logto utilise l’excellente implémentation certifiée [OpenID Connect](https://openid.net/connect/) [node-oidc-provider](https://github.com/panva/node-oidc-provider) en interne. Le fournisseur est monté sur `/oidc`, et vous pouvez consulter les configurations et fichiers relatifs dans [packages/core/src/oidc](https://github.com/logto-io/logto/tree/master/packages/core/src/oidc).

Le [Userinfo Endpoint](https://openid.net/specs/openid-connect-core-1_0.html#UserInfo) OIDC est disponible et monté sur `/oidc/me`.

:::info
Si vous souhaitez appeler directement les API OIDC, n'oubliez pas de définir l'en-tête `Content-Type: application/x-www-form-urlencoded`.
:::

## Logto API \{#logto-api}

### Management API \{#management-api}

_Management API_ est un ensemble d’API qui gèrent et mettent à jour les données Logto. Seuls les utilisateurs ayant le rôle `admin` y ont accès.

Rendez-vous sur [Références API](https://openapi.logto.io) pour voir les détails.

Pour accéder à l’API de manière programmatique, voir [Interagir avec Management API](/integrate-logto/interact-with-management-api).

### Experience API \{#experience-api}

Experience API est un ensemble de points de terminaison dédiés qui prennent en charge les interactions personnalisées de l’interface de connexion.

Ces API permettent aux développeurs d’implémenter les fonctionnalités principales d’authentification (Authentification), y compris la connexion, l’inscription, la réinitialisation du mot de passe, la liaison de comptes sociaux et l’authentification multi-facteurs (MFA). Pour implémenter ces fonctionnalités, votre interface personnalisée doit interagir avec Experience API.

Pour mieux comprendre les flux utilisateurs et les détails d’implémentation :

- Consultez le guide [Développez votre interface personnalisée](/customization/bring-your-ui/#develop-your-custom-ui) pour apprendre à utiliser Experience API afin de construire votre propre interface d’expérience utilisateur
- Référez-vous à la [documentation Experience API](https://openapi.logto.io/group/endpoint-experience) pour la documentation détaillée de l’API
- Lisez le [RFC de conception Experience API](https://github.com/logto-io/rfcs/blob/master/draft/0004-experience-api.md) pour des spécifications techniques approfondies et des exemples

### Account API \{#account-api}

Account API est un ensemble complet d’API qui donne aux utilisateurs finaux un accès direct à l’API sans avoir besoin de passer par Management API, voici les points clés :

- Accès direct : Account API permet aux utilisateurs finaux d’accéder et de gérer directement leur propre profil de compte sans nécessiter le relais de Management API.
- Gestion du profil utilisateur et des identités : Les utilisateurs peuvent gérer leur profil et leurs paramètres de sécurité, y compris l’e-mail, le téléphone, le mot de passe, les connexions sociales et les facteurs MFA, ainsi que récupérer les jetons Secret Vault pour les connexions sociales et SSO d’entreprise liées.
- Contrôle d’accès global : L’administrateur a un contrôle total et global sur les paramètres d’accès, et peut personnaliser chaque champ.
- Autorisation transparente : Autoriser n’a jamais été aussi simple ! Utilisez simplement `client.getAccessToken()` pour obtenir un jeton d’accès opaque pour OP (Logto), et attachez-le à l’en-tête Authorization comme `Bearer <access_token>`.

Avec Logto Account API, vous pouvez construire un système de gestion de compte personnalisé comme une page de profil entièrement intégrée à Logto.

Consultez [Paramètres du compte via Account API](/end-user-flows/account-settings/by-account-api) pour apprendre à exploiter Account API afin de construire votre propre page de paramètres de compte.

Référez-vous à la [documentation Account API](https://openapi.logto.io/group/endpoint-my-account) pour la documentation détaillée de l’API.

## Proxys frontend \{#frontend-proxies}

Un _proxy frontend_ est une fonction middleware qui sert un projet frontend de manière adaptée à l’environnement :

- En développement, il proxy les requêtes HTTP vers le serveur de développement frontend.
- En production, il sert directement les fichiers frontend statiques.

Logto dispose de trois proxys frontend :

      <td>

Vous remarquerez peut-être que le proxy UI utilise le chemin racine. Contrairement aux autres proxys, le proxy UI est un proxy de secours, ce qui signifie qu’il ne prend effet que lorsqu’aucun autre proxy n’est trouvé.
:::

# Webhook 請求 (Webhooks request)

當 webhook 事件觸發時，Logto 會向每個已訂閱該事件的端點發送 `POST` 請求。完整事件目錄請參閱 [Webhook 事件](/developers/webhooks/webhooks-events)；本頁說明 Logto 傳送的 **請求結構**。

## 請求標頭 \{#request-headers}

| Key                     | 可自訂 | 說明                                                                            |
| ----------------------- | ------ | ------------------------------------------------------------------------------- |
| user-agent              | ✅     | 預設為 `Logto (https://logto.io/)`。                                            |
| content-type            | ✅     | 預設為 `application/json`。                                                     |
| logto-signature-sha-256 |        | 請求主體的簽章。詳見 [保護你的 webhook](/developers/webhooks/secure-webhooks)。 |

可自訂標頭可透過 [安全 webhook](/developers/webhooks/configure-webhooks/#secure-webhook) 設定覆寫。

## 請求主體概覽 \{#request-body-overview}

主體為 JSON 物件。其具體結構取決於事件所屬類別：

| 類別           | 事件                                                                                         | 觸發時機                                                                   |
| -------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **使用者流程** | `PostRegister`、`PostSignIn`、`PostResetPassword`                                            | 使用者完成由 Experience API 處理的註冊、登入或重設密碼流程時。             |
| **資料變更**   | `User.*`、`Role.*`、`Scope.*`、`Organization.*`、`OrganizationRole.*`、`OrganizationScope.*` | 由 Management API 呼叫或 Experience API 上的使用者流程變更底層資料模型時。 |
| **例外**       | `Identifier.Lockout`                                                                         | 安全事件，例如連續驗證失敗後帳號被鎖定。                                   |

每個類別都包含一組 [共用欄位](#common-fields)。各類別會再加上自身的請求上下文欄位及事件專屬 payload。

### 共用欄位 \{#common-fields}

無論類別，所有 webhook 傳送都會包含：

| 欄位      | 型別     | 選填 | 說明                              |
| --------- | -------- | ---- | --------------------------------- |
| hookId    | `string` |      | Logto 中的 webhook 設定識別碼。   |
| event     | `string` |      | 觸發此次傳送的事件。              |
| createdAt | `string` |      | Payload 建立時間，ISO 8601 格式。 |
| userAgent | `string` | ✅   | 觸發請求的 user-agent。           |

每個類別也會包含觸發請求的 IP 位址：使用者流程事件欄位名為 `userIp`，資料變更與例外事件則為 `ip`。語意相同，僅為歷史命名差異以維持相容性。

## 使用者流程事件 payload \{#user-flow-event-payloads}

**事件：** `PostRegister`、`PostSignIn`、`PostResetPassword`。

當使用者完成由 Experience API 處理的註冊、登入或重設密碼流程時觸發。除了 [共用欄位](#common-fields) 外，主體還包含：

| 欄位             | 型別                                         | 選填 | 說明                                                                                                               |
| ---------------- | -------------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------ |
| interactionEvent | `'SignIn' \| 'Register' \| 'ForgotPassword'` |      | 使用者流程事件型別。分別對應 `PostSignIn` / `PostRegister` / `PostResetPassword`。欄位名稱保留歷史 "interaction"。 |
| sessionId        | `string`                                     | ✅   | 此事件的 Session ID（非 Interaction ID），如適用。                                                                 |
| userIp           | `string`                                     | ✅   | 觸發請求的 IP 位址。                                                                                               |
| userId           | `string`                                     | ✅   | 與此事件關聯的使用者 ID，如適用。                                                                                  |
| user             | `UserEntity`                                 | ✅   | 與此事件關聯的使用者實體，如適用。                                                                                 |
| applicationId    | `string`                                     | ✅   | 與此事件關聯的應用程式 ID，如適用。                                                                                |
| application      | `ApplicationEntity`                          | ✅   | 與此事件關聯的應用程式實體，如適用。                                                                               |

#### Entity 結構 \{#user-flow-entity-shapes}

```tsx
type UserEntity = {
  id: string;
  username?: string;
  primaryEmail?: string;
  primaryPhone?: string;
  name?: string;
  avatar?: string;
  customData?: object;
  identities?: object;
  lastSignInAt?: string;
  createdAt?: string;
  applicationId?: string;
  isSuspended?: boolean;
};
```

```tsx
enum ApplicationType {
  Native = 'Native',
  SPA = 'SPA',
  Traditional = 'Traditional',
  MachineToMachine = 'MachineToMachine',
  Protected = 'Protected',
  SAML = 'SAML',
}

type ApplicationEntity = {
  id: string;
  type: ApplicationType;
  name: string;
  description?: string;
};
```

完整欄位參考請見 [使用者](/user-management/user-data) 與 [應用程式](/integrate-logto/application-data-structure)。

## 資料變更事件 payload \{#data-mutation-event-payloads}

**事件：** 所有 `User.*`、`Role.*`、`Scope.*`、`Organization.*`、`OrganizationRole.*`、`OrganizationScope.*` 事件。完整目錄請見 [Webhook 事件 → 資料變更 webhook 事件](/developers/webhooks/webhooks-events#data-mutation-hook-events)。

主體內容固定包含：

- [共用欄位](#common-fields)。
- `ip` 欄位，觸發請求的 IP 位址（選填，已知時提供）。
- **API 上下文**，描述變更的觸發來源。根據來源有兩種變體：
  - [Experience API 上下文](#experience-api-context-fields)：來自使用者流程。
  - [Management API 上下文](#management-api-context-fields)：來自直接的 Management API 呼叫。
- **事件專屬 payload**：受影響的實體於 `data` 欄位（部分事件還有額外頂層欄位）。詳見 [事件專屬資料 payload](#event-specific-data-payloads)。

### Experience API 上下文欄位 \{#experience-api-context-fields}

當變更由 Experience API 上的使用者流程觸發時（如註冊時的 `User.Created` 或個人資料更新時的 `User.Data.Updated`），會包含：

| 欄位             | 型別                                         | 選填 | 說明                                                           |
| ---------------- | -------------------------------------------- | ---- | -------------------------------------------------------------- |
| interactionEvent | `'SignIn' \| 'Register' \| 'ForgotPassword'` | ✅   | 產生變更的使用者流程事件型別。欄位名稱保留歷史 "interaction"。 |
| sessionId        | `string`                                     | ✅   | 此事件的 Session ID（非 Interaction ID），如適用。             |
| applicationId    | `string`                                     | ✅   | 應用程式 ID，如適用。                                          |
| application      | `ApplicationEntity`                          | ✅   | 應用程式實體，如適用。                                         |

### Management API 上下文欄位 \{#management-api-context-fields}

當變更由 Management API 呼叫觸發時會包含：

| 欄位         | 型別     | 選填 | 說明                                                    |
| ------------ | -------- | ---- | ------------------------------------------------------- |
| path         | `string` | ✅   | 觸發此 webhook 的 API 呼叫路徑。                        |
| method       | `string` | ✅   | API 呼叫的 HTTP 方法。                                  |
| status       | `number` | ✅   | API 呼叫的回應狀態碼。                                  |
| params       | `object` | ✅   | API 呼叫的 koa 路徑參數。                               |
| matchedRoute | `string` | ✅   | koa 匹配到的路由。Logto 用於 webhook 事件過濾器的比對。 |

### 事件專屬資料 payload \{#event-specific-data-payloads}

所有資料變更事件都包含頂層 `data` 欄位，攜帶受影響的實體；若變更無法以單一實體摘要（如刪除與成員變更事件），則為 `null`。部分事件還有額外頂層欄位，`Organization.Membership.Updated` 為一例，詳見下文。

#### 使用者事件 \{#user-events}

| 事件              | 欄位 | 型別         | 選填 | 說明                 |
| ----------------- | ---- | ------------ | ---- | -------------------- |
| User.Created      | data | `UserEntity` |      | 新建立的使用者實體。 |
| User.Data.Updated | data | `UserEntity` |      | 更新後的使用者實體。 |
| User.Deleted      | data | `null`       | /    |                      |

#### 角色事件 \{#role-events}

```tsx
type Role = {
  id: string;
  name: string;
  description: string;
  type: 'User' | 'MachineToMachine';
  isDefault: boolean;
};
```

```tsx
type Scope = {
  id: string;
  name: string;
  description: string;
  resourceId: string;
  createdAt: number;
};
```

| 事件                | 欄位   | 型別      | 選填 | 說明                                                              |
| ------------------- | ------ | --------- | ---- | ----------------------------------------------------------------- |
| Role.Created        | data   | `Role`    |      | 新建立的角色實體。                                                |
| Role.Data.Updated   | data   | `Role`    |      | 更新後的角色實體。                                                |
| Role.Deleted        | data   | `null`    | /    |                                                                   |
| Role.Scopes.Updated | data   | `Scope[]` |      | 指派給該角色的更新後權限範圍 (scopes)。                           |
| Role.Scopes.Updated | roleId | `string`  | ✅   | 指派權限範圍的角色 ID。（僅在建立角色時預先指派權限範圍時提供。） |

#### 權限（Scope）事件 \{#permission-events}

| 事件               | 欄位 | 型別    | 選填 | 說明                   |
| ------------------ | ---- | ------- | ---- | ---------------------- |
| Scope.Created      | data | `Scope` |      | 新建立的權限範圍實體。 |
| Scope.Data.Updated | data | `Scope` |      | 更新後的權限範圍實體。 |
| Scope.Deleted      | data | `null`  | /    |                        |

#### 組織事件 \{#organization-events}

```tsx
type Organization = {
  id: string;
  name: string;
  description?: string;
  customData: object;
  createdAt: number;
};
```

| 事件                            | 欄位 | 型別           | 選填 | 說明                                                                                                                    |
| ------------------------------- | ---- | -------------- | ---- | ----------------------------------------------------------------------------------------------------------------------- |
| Organization.Created            | data | `Organization` |      | 新建立的組織實體。                                                                                                      |
| Organization.Data.Updated       | data | `Organization` |      | 更新後的組織實體。                                                                                                      |
| Organization.Deleted            | data | `null`         | /    |                                                                                                                         |
| Organization.Membership.Updated | data | `null`         | /    | 變更內容由頂層 delta 陣列描述。詳見 [Organization.Membership.Updated payload](#organizationmembershipupdated-payload)。 |

##### Organization.Membership.Updated payload \{#organizationmembershipupdated-payload}

除了 [共用欄位](#common-fields) 及適用的 API 上下文欄位（Management API 路由用 [Management API 上下文](#management-api-context-fields)，即時佈建用 [Experience API 上下文](#experience-api-context-fields)），`Organization.Membership.Updated` 事件還會在 payload 頂層（與 `event`、`createdAt` 等同層，**不在** `data` 內，該欄位永遠為 `null`）攜帶 `organizationId` 及可選的 delta 陣列。

| 欄位                  | 型別       | 選填 | 說明                                                      |
| --------------------- | ---------- | ---- | --------------------------------------------------------- |
| organizationId        | `string`   |      | 發生成員變更的組織 ID。                                   |
| addedUserIds          | `string[]` | ✅   | 此觸發新增的使用者 ID。若無新增或不影響使用者成員則省略。 |
| removedUserIds        | `string[]` | ✅   | 此觸發移除的使用者 ID。若無移除則省略。                   |
| addedApplicationIds   | `string[]` | ✅   | 新增的應用程式 ID。若無新增或不影響應用程式成員則省略。   |
| removedApplicationIds | `string[]` | ✅   | 移除的應用程式 ID。若無移除則省略。                       |

這四個 delta 陣列為 **可選且具加值性**：對於不預期這些欄位的消費端，既有 payload 結構不變，且舊有 `data: null` 欄位仍會照常傳送。

###### 觸發來源與可能出現的 delta 欄位 \{#membership-triggers}

| 觸發來源                                                | 可能出現的 delta 欄位                          |
| ------------------------------------------------------- | ---------------------------------------------- |
| `POST /organizations/:id/users`                         | `addedUserIds`                                 |
| `PUT /organizations/:id/users`                          | `addedUserIds`、`removedUserIds`               |
| `DELETE /organizations/:id/users/:userId`               | `removedUserIds`                               |
| `POST /organizations/:id/applications`                  | `addedApplicationIds`                          |
| `PUT /organizations/:id/applications`                   | `addedApplicationIds`、`removedApplicationIds` |
| `DELETE /organizations/:id/applications/:applicationId` | `removedApplicationIds`                        |
| `PUT /organization-invitations/:id/status`（Accepted）  | `addedUserIds`                                 |
| 即時佈建將使用者加入新組織時                            | `addedUserIds`                                 |

###### 空 delta 會被省略（缺席 ≠ 空變更） \{#empty-deltas-are-omitted}

空的 delta 陣列會 **完全省略**。例如，`PUT /organizations/:id/users` 若將成員集合替換為原集合，實際無變更，payload 僅剩 `{ organizationId }`，四個 delta 欄位皆缺席。重新加入已存在成員、已是成員的邀請再接受亦同。

**消費端必須將缺席欄位視為「該側無變更」，而非「空變更」。**

###### 單一陣列上限（靜默截斷） \{#membership-delta-cap}

每個 delta 陣列上限為 **5000 筆**。若單次 Management API 呼叫新增或移除超過 5000 位使用者（或應用程式），對應 delta 陣列會靜默截斷為前 5000 筆。**payload 內不會標示已達上限。**

若你的應用程式會進行可能影響超過 5000 成員的大量操作，遇到陣列長度正好 5000 時，請主動透過 Management API 重新同步完整成員：

- `GET /organizations/:id/users`：完整使用者成員。
- `GET /organizations/:id/applications`：完整應用程式成員。

此設計與 GitHub 的 `push` 事件（`commits` 上限 20 筆，需用 compare API 取全量）相同。

###### 跳過無實質變更事件 \{#skipping-no-op-events}

若要在消費端跳過無 delta 欄位的無操作事件，可依 delta 陣列是否存在過濾：

```ts
if (
  payload.addedUserIds?.length ||
  payload.removedUserIds?.length ||
  payload.addedApplicationIds?.length ||
  payload.removedApplicationIds?.length
) {
  // 有實質成員變更，處理之
}
```

`?.length` 對 `undefined` 與 `[]` 皆為 falsy，因此此判斷式無論欄位缺席或（假設未來）為空陣列都適用。

###### 範例 payload \{#membership-example-payloads}

**新增使用者（`POST /organizations/:id/users`）：**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "addedUserIds": ["u_001"]
}
```

**取代使用者成員集合（`PUT /organizations/:id/users`）：**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "addedUserIds": ["u_002"],
  "removedUserIds": ["u_001"]
}
```

**移除使用者（`DELETE /organizations/:id/users/:userId`）：**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "removedUserIds": ["u_001"]
}
```

**新增應用程式（`POST /organizations/:id/applications`）：**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "addedApplicationIds": ["app_xyz"]
}
```

**重新加入已存在成員、無操作 `PUT` 或已是成員的邀請再接受（無實質變更）：**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc"
}
```

**大量操作觸發 5000 筆上限（靜默截斷）：**

```json
{
  "event": "Organization.Membership.Updated",
  "organizationId": "org_abc",
  "removedUserIds": ["u_0001", "u_0002", "/* … 共 5000 筆 */"]
}
```

遇到長度正好 5000 的陣列時，請主動呼叫 `GET /organizations/:id/users`（或 `/applications`）同步全量。

## 例外事件 payload \{#exception-event-payloads}

**事件：** `Identifier.Lockout`。

於安全事件（如連續驗證失敗導致帳號鎖定）時觸發。這類事件皆來自使用者流程，因此主體包含：

- [共用欄位](#common-fields)。
- `ip` 欄位（與資料變更事件相同）。
- [Experience API 上下文欄位](#experience-api-context-fields)。
- 下方例外專屬欄位。

```tsx
enum SignInIdentifier {
  Email = 'email',
  Phone = 'phone',
  Username = 'username',
}
```

| 欄位  | 型別               | 選填 | 說明                                            |
| ----- | ------------------ | ---- | ----------------------------------------------- |
| type  | `SignInIdentifier` |      | 使用者識別型別，例如 email、phone 或 username。 |
| value | `string`           |      | 觸發鎖定的使用者識別值。                        |

# MFA 구성

## Logto에서 MFA 설정 구성하기 \{#configure-mfa-settings-in-logto}

Logto는 다양한 보안 요구 사항을 충족할 수 있도록 유연한 MFA 구성 옵션을 제공합니다. 모든 사용자에게 글로벌 수준에서 MFA를 설정하거나, 다중 테넌트 애플리케이션의 경우 조직별로 활성화할 수 있습니다.

### 글로벌 MFA 구성 \{#global-mfa-configuration}

사용자의 Logto 로그인 플로우에서 MFA를 활성화하려면 다음 단계를 따르세요:

1. 이동: <CloudLink to="/mfa">콘솔 > 다단계 인증 (MFA)</CloudLink>.
2. 사용자에게 지원할 인증 요소를 활성화하세요.
   1. 주요 인증 요소:
      - [패스키 (WebAuthn)](/end-user-flows/mfa/webauthn): 기기 생체 인증 또는 보안 키 등을 지원하는 웹 제품에 적합한 고보안 옵션으로, 강력한 보호를 제공합니다.
      - [인증 앱 OTP](/end-user-flows/mfa/authenticator-app-otp): 가장 일반적이고 널리 사용되는 방법입니다. Google Authenticator 또는 Authy와 같은 인증 앱에서 생성된 시간 기반 일회용 비밀번호(TOTP)를 사용합니다.
      - [SMS 인증](/end-user-flows/mfa/sms-mfa): 사용자의 등록된 휴대폰 번호로 일회용 인증 코드를 SMS로 전송하는 편리한 방법으로, 별도의 앱 없이 모바일 인증을 선호하는 사용자에게 적합합니다.
      - [이메일 인증](/end-user-flows/mfa/email-mfa): 사용자의 등록된 이메일 주소로 일회용 인증 코드를 전송하는 널리 접근 가능한 방법으로, 모든 플랫폼과 기기에서 사용할 수 있습니다.
   2. 백업 인증 요소:
      - [백업 코드](/end-user-flows/mfa/backup-codes): 사용자가 위의 주요 인증 요소를 모두 사용할 수 없을 때를 위한 백업 옵션입니다. 이 옵션을 활성화하면 사용자의 접근 성공률이 높아집니다.
   3. SMS 또는 이메일 인증을 활성화한 경우, **이메일/SMS 2단계 인증**에서 어떤 사용자가 해당 인증을 사용할지 선택하세요. [이메일 및 SMS MFA 등록](#email-and-sms-mfa-enrollment) 참고.
3. 드롭다운에서 **MFA 필수 정책**을 선택하세요. 이 정책은 사용자가 로그인 중 MFA를 완료해야 하는 시점을 제어합니다:
   - **선택적 MFA** (_Optional MFA: 사용자가 자신의 계정 보안을 위해 MFA 활성화 여부를 선택할 수 있음_): 사용자가 자신의 계정 보안을 위해 MFA 활성화 여부를 직접 결정할 수 있습니다. 사용자는 로그인 중 MFA 설정을 건너뛰고, 나중에 셀프 서비스 계정 설정 페이지에서 설정할 수 있습니다. 사용자 계정 설정 페이지 구현에 대해 [자세히 알아보기](/end-user-flows/account-settings/).
   - **적응형 MFA** (_Adaptive MFA: 로그인 시 위험이 감지될 때만 MFA 요청 (예: 새로운 국가 / 장기간 미사용)_): 로그인 시 비정상적인 상황에서만 MFA를 적용하여, 저위험 로그인은 원활하게 진행되고 의심스러운 로그인에는 추가 인증을 요구합니다. Logto는 내장된 컨텍스트 위험 규칙(새로운 국가, 지오 벨로시티, 장기간 미사용, 신뢰할 수 없는 IP 신호 등)을 평가하여 결정합니다. 이 모드는 기존 MFA 설정(최소 1개 이상의 MFA 요소 활성화)이 필요하며, 최종 사용자 로그인 플로우에 적용되고, 디바이스 지문 인식에 의존하지 않습니다. 규칙 임계값, 엣지 헤더 전제 조건, Webhook 세부 정보는 [적응형 MFA](/end-user-flows/mfa/adaptive-mfa) 참고.
   - **필수 MFA** (_Mandatory MFA: 모든 사용자가 로그인할 때마다 MFA를 완료해야 함_): 모든 사용자가 매번 로그인 시 MFA를 완료해야 합니다. MFA를 설정하지 않은 사용자는 계속 진행하기 전에 반드시 설정을 완료해야 합니다.
   - **선택적 MFA**를 선택한 경우, **MFA 설정 프롬프트** 정책을 추가로 구성할 수 있습니다:
     - **사용자에게 MFA 설정을 요청하지 않음**: 로그인 또는 회원가입 중에 MFA 설정 프롬프트가 표시되지 않습니다.
     - **회원가입 중 MFA 설정 요청 (건너뛸 수 있음, 1회 프롬프트)**: 신규 사용자는 회원가입 중 MFA 설정 프롬프트를 받고, 기존 사용자는 다음 로그인 시 프롬프트를 받습니다. 사용자는 이 단계를 건너뛸 수 있으며, 다시 나타나지 않습니다.
     - **회원가입 후 다음 로그인 시 MFA 설정 요청 (건너뛸 수 있음, 1회 프롬프트)**: 신규 사용자는 회원가입 후 다음 로그인 시 MFA 설정 프롬프트를 받고, 기존 사용자는 다음 로그인 시 프롬프트를 받습니다. 사용자는 이 단계를 건너뛸 수 있으며, 다시 나타나지 않습니다.
   - **적응형 MFA**를 선택한 경우, 건너뛸 수 없는 두 가지 **MFA 설정 프롬프트** 정책만 지원됩니다 (**사용자에게 MFA 설정을 요청하지 않음**은 사용할 수 없음):
     - **회원가입 중 MFA 설정 요청 (건너뛸 수 없음)**: 신규 사용자는 회원가입 중 반드시 MFA 설정을 완료해야 하며, 기존 사용자는 다음 로그인 시 반드시 완료해야 합니다.
     - **회원가입 후 다음 로그인 시 MFA 설정 요청 (건너뛸 수 없음)**: 신규 사용자는 회원가입 후 다음 로그인 시 반드시 MFA 설정을 완료해야 하며, 기존 사용자는 다음 로그인 시 반드시 완료해야 합니다.

**선택적 MFA**에서 설정 프롬프트가 활성화된 경우(`회원가입 중 MFA 설정 요청 (건너뛸 수 있음, 1회 프롬프트)` 또는 `회원가입 후 다음 로그인 시 MFA 설정 요청 (건너뛸 수 있음, 1회 프롬프트)`), Logto는 먼저 `2단계 인증 켜기`라는 제목의 MFA 활성화 확인 페이지를 표시합니다. 사용자는 `2단계 인증 활성화`를 선택해 MFA 바인딩을 진행하거나, 프롬프트를 건너뛰고 현재 로그인/회원가입 플로우를 MFA 없이 마칠 수 있습니다. **적응형 MFA** 또는 **필수 MFA**에서는 사용자가 `2단계 인증 켜기` 확인 페이지를 보지 않고 바로 MFA 요소 바인딩 단계로 이동합니다.

:::tip
사용자가 MFA 등록을 건너뛴 후 다시 프롬프트를 표시해야 한다면, 해당 사용자의 건너뛰기 상태를 초기화하세요. 관리자는 Management API (`PATCH /api/users/{userId}/logto-configs`)를 사용할 수 있고, 셀프 서비스 플로우를 구축하는 개발자는 Account API (`PATCH /api/my-account/logto-configs`)를 호출할 수 있습니다. [Management API 참고](https://openapi.logto.io/operation/operation-updateuserlogtoconfigs) · [Account API 참고](https://openapi.logto.io/operation/operation-updatelogtoconfig)
:::

### 이메일 및 SMS MFA 등록 \{#email-and-sms-mfa-enrollment}

이메일 및 SMS 인증 코드는 사용자의 기본 이메일 주소와 기본 휴대폰 번호로 전송됩니다. **이메일/SMS 2단계 인증** 설정은 어떤 사용자가 해당 요소를 사용할 수 있는지 결정합니다. 이 설정은 SMS 또는 이메일 인증 코드 요소가 활성화될 때 나타나며, 두 요소 모두에 적용됩니다.

- **인증된 이메일 또는 휴대폰 번호가 있는 모든 사용자**: 기본 이메일 주소가 있는 모든 사용자는 이메일 MFA를, 기본 휴대폰 번호가 있는 모든 사용자는 SMS MFA를 별도의 설정 없이 사용할 수 있습니다. 인증된 이메일 또는 휴대폰 번호로 회원가입한 사용자는 이미 해당 요소를 보유하게 됩니다.
- **직접 설정한 사용자만**: 사용자가 MFA 설정 플로우, [Account Center](/end-user-flows/account-settings/by-account-center-ui) 또는 [Account API](/end-user-flows/account-settings/by-account-api#manage-email-and-sms-mfa), 혹은 관리자가 [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management)를 통해 직접 설정한 경우에만 이메일 또는 SMS MFA를 사용할 수 있습니다. 인증된 이메일 또는 휴대폰 번호만으로는 MFA가 활성화되지 않으므로, 모든 사용자를 등록시키지 않고도 이메일 또는 SMS를 인증 앱, 패스키와 함께 MFA 옵션으로 제공할 수 있습니다.

신규 테넌트는 기본적으로 **직접 설정한 사용자만**을 사용합니다. 이전에 생성된 테넌트는 변경 전까지 **인증된 이메일 또는 휴대폰 번호가 있는 모든 사용자**를 유지합니다. Management API에서는 이 설정이 [로그인 경험](https://openapi.logto.io/operation/operation-updatesigninexp)의 `mfa.verificationCodeEnrollment`로, 값은 `Implicit`와 `Explicit`입니다. `mfa`를 업데이트할 때 `verificationCodeEnrollment`를 생략하면 전체 객체가 대체되어 기본값인 `Implicit`로 초기화됩니다.

Logto는 두 모드 모두에서 각 이메일 또는 SMS MFA 설정을 기록합니다. 이 기록은 주소가 아니라 선택 자체를 저장하므로, 사용자가 기본 이메일 주소나 휴대폰 번호를 변경하거나 삭제해도 유지되며, 해당 정보가 없을 때는 무시됩니다. 사용자가 나중에 새 주소를 추가하면 다시 적용됩니다.

**모드 전환**

전환은 즉시 적용되며, 사용자 데이터에는 영향을 주지 않습니다. 콘솔에서 전환 시 확인을 요청합니다.

- **직접 설정한 사용자만**으로 전환: 이메일 및 SMS MFA는 직접 설정하지 않은 모든 사용자에게 적용되지 않습니다. 이메일 또는 휴대폰 번호만 보유한 사용자는 MFA가 없는 사용자로 간주되어, 로그인 시 인증을 요구받지 않으며, MFA 정책에 따라 필요할 때만 설정을 요청받습니다. Logto는 사용자를 자동으로 등록시키지 않습니다. 특정 사용자에게 이메일 또는 SMS MFA를 유지하려면 전환 전에 [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management)로 추가하세요.
- **인증된 이메일 또는 휴대폰 번호가 있는 모든 사용자**로 전환: 기본 이메일 주소 또는 휴대폰 번호가 있는 모든 사용자는 다시 이메일 또는 SMS MFA를 갖게 됩니다. 직접 설정하지 않은 사용자도 포함됩니다.

### 조직별 MFA 구성 \{#organization-level-mfa-configuration}

[조직](/organizations)을 지원하는 다중 테넌트 아키텍처 제품의 경우, 대부분의 상황에서 모든 사용자에게 MFA를 필수로 할 필요가 없습니다. 대신, 조직별로 MFA를 활성화하여 각 고객의 요구에 맞게 요구 사항을 맞춤화할 수 있습니다. 시작하려면 [조직 구성원에 대한 MFA 필수화](/organizations/organization-management#require-mfa-for-organization-members)를 참고하세요.

**MFA 필수** 드롭다운에서 **선택적 MFA**를 선택하면, 콘솔에 **조직에서 MFA를 활성화한 후 사용자에게 MFA 설정 프롬프트** 설정이 표시됩니다. 이 설정을 **다음 로그인 시 MFA 설정 요청 (건너뛸 수 없음)**으로 지정하면, MFA가 필수인 조직의 구성원은 다음 로그인 시 반드시 MFA 설정을 완료해야 하며, 건너뛸 수 없습니다. (**적응형 MFA** 또는 **필수 MFA**가 선택된 경우 이 설정은 콘솔에서 숨겨지며 저장되지 않습니다.)

**적응형 MFA**에서는 위험 규칙이 트리거되지 않은 저위험 로그인에 대해, 사용자별 **MFA 필수 설정**이 활성화되어 있거나 `isMfaRequired`가 활성화된 조직에 속해 있어도 MFA 인증이 요구되지 않습니다.

### 추가 MFA 요소 제안 \{#suggest-adding-another-mfa-factor}

<CloudLink to="/mfa">콘솔 > 다단계 인증 (MFA)</CloudLink>에서 **추가 MFA 요소 제안** 스위치(기본
활성화, Sign-in Experience API의 `mfa.skipAdditionalBindingSuggestion`로 제어)는 다음 조건에서
사용자가 회원가입 또는 로그인 시 추가 MFA 요소를 등록하도록 프롬프트합니다:

- 사용자의 유일한 MFA 요소가 로그인에 사용한 이메일 주소, 휴대폰 번호, 또는 패스키일 때
- 테넌트에 최소 하나 이상의 다른 MFA 요소가 활성화되어 있을 때

사용자는 이 프롬프트를 건너뛸 수 있습니다. 사용자가 제안을 건너뛰면, Logto는 해당 사용자의 `logtoConfig`에 `mfa.additionalBindingSuggestionSkipped: true`를 저장하여 이후 로그인 시 제안이 다시 나타나지 않도록 합니다. 이 플래그는 [Account API](/end-user-flows/account-settings/by-account-api) (`PATCH /api/my-account/logto-configs`에서 `{ "mfa": { "additionalBindingSuggestionSkipped": false } }`로 업데이트/초기화; `GET /api/my-account/logto-configs` 및 `GET /api/users/{userId}/logto-configs`에서는 반환되지 않음)로 업데이트하거나 초기화할 수 있습니다.

### 사용자별 MFA 필수화 \{#per-user-mfa-requirement}

관리자는 테넌트의 **선택적 MFA** 프롬프트 설정과 관계없이 개별 사용자에 대해 MFA 설정을 필수로 지정할 수 있습니다:

- **콘솔에서**: <CloudLink to="/users">콘솔 > 사용자 관리</CloudLink>에서 사용자를 선택한 후, **다단계 인증 (MFA)** 섹션에서 **MFA 설정 필수**를 활성화하세요.
- **Management API로**: `PATCH /api/users/{userId}/logto-configs`에 `{ "mfa": { "required": true } }`를 전달하여 설정(조회는 `GET /api/users/{userId}/logto-configs`). [Management API로 계정 설정 관리](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) 참고.

최종 사용자는 Account API (`PATCH /api/my-account/logto-configs`)를 통해 `mfa.required`를 수정할 수 없습니다. 셀프 서비스 클라이언트에서는 `GET /api/my-account/mfa-settings`에서 읽기 전용 `required`로 노출됩니다.

사용자별 `mfa.required`가 `true`이면, 사용자는 로그인 완료 전에 최소 하나의 MFA 요소를 반드시 설정해야 하며, 설정을 건너뛸 수 없습니다. **선택적 MFA**에서는 사용자가 `skipMfaOnSignIn`을 활성화했거나 `enabled: false`로 설정해도 로그인 시 MFA 인증이 요구됩니다. **적응형 MFA**에서는 위험 규칙이 트리거되지 않은 저위험 로그인에 대해 여전히 MFA 인증이 요구되지 않습니다.

## MFA 사용자 플로우 \{#mfa-user-flow}

### MFA 설정 플로우 \{#mfa-set-up-flow}

MFA가 활성화되면, 사용자는 로그인 및 회원가입 중 MFA 설정을 요청받을 수 있습니다. **MFA 필수 정책**에서 **선택적 MFA**가 선택된 경우에만 사용자가 이 설정 과정을 건너뛸 수 있습니다.

1. **로그인 또는 회원가입 페이지 방문**: 사용자가 로그인 또는 회원가입 페이지로 이동합니다.
2. **로그인 또는 회원가입 완료**: 사용자가 로그인 또는 회원가입 플로우 내에서 아이덴티티 인증 과정을 완료합니다.
   - **선택적 MFA**에서 설정 프롬프트가 활성화된 경우, Logto는 먼저 `2단계 인증 켜기` 확인 페이지를 표시하며, 사용자는 MFA 설정을 건너뛰거나 `2단계 인증 활성화`를 클릭해 계속 진행할 수 있습니다.
   - **적응형 MFA** 또는 **필수 MFA**에서는 사용자가 `2단계 인증 켜기` 페이지를 보지 않고 바로 MFA 요소 바인딩 단계로 이동하며, 설정을 건너뛸 수 없습니다.
3. **MFA 주요 인증 요소 설정**: 사용자는 주요 MFA 요소(패스키, 인증 앱 OTP, SMS 코드, 이메일 코드 중 하나)를 설정하도록 안내받습니다.
   - 여러 주요 요소가 활성화된 경우, 사용자가 원하는 옵션을 선택할 수 있습니다.
   - 주요 요소가 회원가입 식별자(SMS 또는 이메일)와 동일한 경우, 이미 인증된 상태이므로 사용자가 다시 인증할 필요가 없습니다:
     - **인증된 이메일 또는 휴대폰 번호가 있는 모든 사용자**에서는 이미 해당 요소가 사용자에게 적용되어 있으므로, 바로 다음 단계(예: "다른 2단계 인증 추가" 또는 "백업 요소 저장")로 진행합니다.
     - **직접 설정한 사용자만**에서는 다른 요소와 동일하게 제공되며, 설정 시 두 번째 코드가 전송되지 않습니다. [이메일 및 SMS MFA 등록](#email-and-sms-mfa-enrollment) 참고.
   - **MFA 필수 정책**에서 **선택적 MFA**가 선택된 경우, "건너뛰기" 버튼을 눌러 이 단계를 건너뛸 수 있습니다.
4. **MFA 백업 요소 설정**: **백업 코드**가 활성화된 경우, 사용자는 주요 인증 요소 설정 후 백업 코드를 저장하라는 안내를 받습니다. 자동 생성된 백업 코드는 사용자가 다운로드 및 안전하게 보관할 수 있도록 표시됩니다. 사용자는 MFA 설정 완료를 위해 백업 코드를 직접 확인해야 합니다.

<img src="/img/assets/link-mfa.png" alt="MFA 설정 플로우" />

### MFA 인증 플로우 \{#mfa-verification-flow}

MFA를 설정한 사용자는 로그인 시 등록된 MFA 요소로 아이덴티티 인증을 요청받습니다. 인증 요소는 Logto의 MFA 구성 및 사용자 설정에 따라 달라집니다.

사용자가 [패스키 로그인](/end-user-flows/sign-up-and-sign-in/passkey-sign-in)으로 로그인하는 경우, Logto는 별도의 MFA 인증 단계를 건너뜁니다. 이는 로그인에 사용된 패스키 자체가 WebAuthn MFA 요소이기 때문입니다.

- 사용 가능한 MFA 요소가 하나뿐인 경우, 해당 요소로 바로 인증합니다.
- 여러 MFA 요소가 있는 경우, Logto는 고정 우선순위로 정렬하여 첫 번째 사용 가능한 요소로 바로 인증을 시작합니다:
  1. **패스키 (WebAuthn)**
  2. **인증 앱 OTP (TOTP)**
  3. **SMS 인증 코드**
  4. **이메일 인증 코드**
  5. **백업 코드**
- 두 개 이상의 MFA 요소가 있을 때, 인증 페이지에 **다른 인증 방법 시도** 링크가 표시되어 사용자가 다른 사용 가능한 요소(백업 코드 포함)로 전환할 수 있습니다.

<img src="/img/assets/verify-mfa.png" alt="MFA 인증 플로우" />

### 로그인 바인딩 규칙 및 예외 \{#sign-in-binding-rules-and-exemptions}

MFA 플로우를 설계할 때 다음 동작을 참고하세요:

- **백업 코드 재생성 프롬프트**: **백업 코드**가 활성화되어 있고 사용자가 이미 다른 활성 MFA 요소를 보유한 경우, 이전에 생성된 모든 백업 코드를 사용했거나 백업 코드가 최초 등록 이후 활성화된 경우, Logto는 로그인 중 새 백업 코드 생성을 안내합니다.
- **로그인 중 바인딩 시 인증 요소 필요**: 사용자가 이미 MFA 요소를 보유한 상태에서 `SignIn` 상호작용 중 새 요소를 바인딩(백업 코드 재생성 포함 또는 "추가 MFA 요소 제안" 프롬프트 응답)하려면, 먼저 MFA 인증을 완료해야 합니다(또는 패스키 로그인/엔터프라이즈 SSO로 로그인). MFA 인증을 우회한 로그인(예: [신뢰 기기](/end-user-flows/mfa/trusted-devices), 위험 규칙이 트리거되지 않은 저위험 [적응형 MFA](/end-user-flows/mfa/adaptive-mfa) 로그인, 사용자가 **선택적 MFA**를 건너뛴 경우(`skipMfaOnSignIn` / `enabled: false`))에서는 해당 로그인 플로우 중 새 MFA 요소를 바인딩할 수 없습니다. 이 세션의 사용자는 이후 Account Center 또는 [Account API](/end-user-flows/account-settings/by-account-api)로 요소를 추가할 수 있습니다.
- **엔터프라이즈 SSO 예외**: [엔터프라이즈 SSO](/end-user-flows/enterprise-sso)로 로그인 또는 회원가입 시, 해당 상호작용 중 테넌트 MFA 인증 및 MFA 설정 프롬프트가 건너뛰어집니다(클라이언트가 `acr_values`로 MFA를 명시적으로 요청한 경우(`urn:logto:acr:mfa`)는 예외).
- **비밀번호 재설정 예외**: [비밀번호 재설정](/end-user-flows/sign-up-and-sign-in/reset-password) 플로우에서는 MFA 인증 및 MFA 설정 프롬프트가 건너뛰어집니다.

## MFA 관리 \{#mfa-management}

로그인/회원가입 시 최초 설정 이후에도, 사용자는 셀프 서비스 계정 센터를 통해 MFA 설정을 관리할 수 있습니다. 이를 통해 사용자는 필요에 따라 MFA 요소를 바인딩하거나 해제할 수 있습니다.

### 계정 센터 구축하기 \{#building-an-account-center}

Logto의 [Account API](/end-user-flows/account-settings/by-account-api)를 활용해 종합적인 계정 센터를 구축할 수 있습니다. 사용자는 다음을 할 수 있습니다:

- **새 MFA 요소 바인딩**: 추가 인증 앱, 패스키 등록 또는 백업 코드 재생성
- **기존 MFA 요소 해제**: 더 이상 사용하지 않는 MFA 방법 제거
- **현재 MFA 상태 확인**: 현재 설정된 MFA 요소 확인

### 로그인 후 MFA 설정 프롬프트 \{#post-login-mfa-setup-prompts}

초기 회원가입 시 MFA가 필수가 아닌 애플리케이션의 경우, MFA 설정을 유도하는 지능형 프롬프트를 구현할 수 있습니다:

- **조건부 프롬프트**: 사용자 행동이나 계정 가치에 따라 MFA 설정 권장
- **보안 대시보드**: MFA 활성화 시 보안 점수가 향상되는 대시보드 제공
- **점진적 온보딩**: MFA 설정을 점진적 보안 강화 플로우의 일부로 제시

이러한 패턴 구현에 대해 [Account API](/end-user-flows/account-settings/by-account-api)에서 자세히 알아보세요.

### 콘솔에서 사용자 MFA 관리 \{#manage-users-mfa-in-console}

<CloudLink to="/user">콘솔 > 사용자 관리</CloudLink>에서 관리자는 사용자 MFA 설정을 효과적으로
관리할 수 있습니다:

- **사용자 MFA 상태 확인**: 각 사용자별로 활성화된 MFA 요소를 확인할 수 있습니다. 이메일 또는 SMS 요소가 인증된 이메일/휴대폰 번호로만 적용된 경우, 또는 사용자가 직접 설정했으나 요소가 비활성화된 경우 등은 안내 메시지로 표시됩니다.
- **사용자 MFA 제거**: 저장된 MFA 요소를 하나씩 제거할 수 있습니다. 암시적 이메일/SMS 인증 코드 행은 이 테이블에서 직접 제거할 수 없으며, 패스키 로그인 활성화 시 패스키(WebAuthn) 행은 여기서 제거 버튼이 없고, 동일한 사용자 상세 페이지의 **패스키** 섹션에서 관리됩니다.

사용자에게 이메일 또는 SMS MFA를 추가하려면 [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management)를 사용하세요.

### 자주 묻는 질문 \{#faqs}

<details>
<summary>
### 관리자가 사용자의 기존 MFA 요소를 제거하면 어떻게 되나요? \{#what-happens-when-administrators-remove-users-existing-mfa-factors}
</summary>
관리자가 사용자의 주요 MFA 요소(패스키, 인증 앱 OTP, SMS, 이메일)를 모두 제거하면, 다음 로그인 시 다음과 같은 상황이 발생합니다:

**상황 1: MFA 요소가 전혀 남지 않은 경우**

- MFA 요소(백업 코드 포함)가 전혀 없고, [MFA 정책](#global-mfa-configuration)이 MFA를 요구하는 경우, 사용자는 MFA 인증 없이 로그인할 수 있으며, 즉시 MFA 설정을 다시 요청받게 됩니다.

**상황 2: 백업 코드가 남아 있는 경우**

- 백업 코드가 남아 있다면, 사용자는 로그인 시 먼저 백업 코드로 인증해야 합니다.
- 백업 코드 인증에 성공하면, 새로운 주요 MFA 요소를 설정하라는 안내를 받습니다.
- 사용자가 이 설정을 건너뛸 수 있는지는 MFA 정책에 따라 다릅니다.
- 이 방식은 주요 요소가 없을 때 사용자가 계정에 접근하지 못하는 상황을 방지합니다.

 </details>

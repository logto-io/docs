# Erweiterte Benutzersuche

Direkte Nutzung der Management API, um erweiterte Suchbedingungen für Benutzer zu nutzen.

## Eine Suchanfrage durchführen \{#perform-a-search-request}

Verwende [`GET /api/users`](https://openapi.logto.io/operation/operation-getuser), um Benutzer zu suchen. Beachte, dass es sich um eine Management API handelt, die wie andere eine Authentifizierung benötigt. Siehe [Interaktion mit Management API](/integrate-logto/interact-with-management-api) für das Vorgehen.

### Beispiel \{#sample}

**Anfrage**

```bash
curl \
  --location \
  --request GET \
  'http://<your-logto-endpoint>/api/users?search=%25alice%25'

```

**Antwort**

Ein Array von `User`-Entitäten.

```json
[
  {
    "id": "MgUzzDsyX0iB",
    "username": "alice_123",
    "primaryEmail": "alice@some.email.domain",
    "primaryPhone": null,
    "name": null,
    "avatar": null
    // ...
  }
]
```

### Parameter \{#parameters}

Eine Suchanfrage besteht aus den folgenden Parameter-Schlüsseln:

- Suchbegriffe: `search`, `search.*`
- Suchmodus für Felder: `mode`, `mode.*` (Standardwert `'like'`, verfügbar: `['exact', 'like', 'similar_to', 'posix']`)
- Verknüpfungsmodus: `joint` oder `jointMode` (Standardwert `'or'`, verfügbar: `['or', 'and']`)
- Groß- / Kleinschreibung beachten: `isCaseSensitive` (Standardwert `false`)

Diese API unterstützt [Paginierung](/integrate-logto/interact-with-management-api/#managing-paginated-api-responses).

Gehen wir sie anhand einiger Beispiele durch. Alle Suchparameter werden als Konstruktor von `URLSearchParams` formatiert.

:::warning

Der Suchmodus ist standardmäßig auf `like` gesetzt, was [ungefähres String-Matching](https://de.wikipedia.org/wiki/Ungefähre_Stringsuche) („Fuzzy Search“) verwendet.

:::

:::note

Alle Fuzzy-Suchmodi unterstützen nur das Matching eines Wertes pro Feld. Wenn du mehrere Werte für ein einzelnes Feld abgleichen möchtest, solltest du den Modus "exact" verwenden. Siehe [Exakte Übereinstimmung und Groß- / Kleinschreibung](/user-management/advanced-user-search#exact-match-and-case-sensitivity) für Details.

:::

### Einfache Fuzzy-Suche \{#basic-fuzzy-search}

Wenn du eine Fuzzy-Suche über alle verfügbaren Felder durchführen möchtest, gib einfach einen Wert für den Schlüssel `search` an. Es wird [der `like`-Operator](https://www.postgresql.org/docs/current/functions-matching.html#FUNCTIONS-LIKE) im Hintergrund verwendet:

```javascript
new URLSearchParams([['search', '%foo%']]);
```

Diese Suche prüft alle verfügbaren Felder in einer Benutzersuche, also `id`, `primaryEmail`, `primaryPhone`, `username`, `name`.

### Felder angeben \{#specify-fields}

Was, wenn du die Suche nur auf `name` beschränken möchtest? Um jemanden zu suchen, dessen Name `foo` enthält, verwende einfach das `.`-Symbol, um das Feld anzugeben:

```javascript
new URLSearchParams([['search.name', '%foo%']]);
```

Beachte, dass verschachtelte Felder nicht unterstützt werden, z. B. führt `search.name.first` zu einem Fehler.

Du kannst auch mehrere Felder gleichzeitig angeben:

```javascript
new URLSearchParams([
  ['search.name', '%foo%'],
  ['search.primaryEmail', '%@gmail.com'],
]);
```

Das bedeutet, Benutzer zu suchen, die `foo` im Namen haben **ODER** deren E-Mail-Adresse mit `@gmail.com` endet.

### Verknüpfungsmodus ändern \{#changing-the-joint-mode}

Wenn du möchtest, dass die API nur Ergebnisse zurückgibt, die ALLE Bedingungen erfüllen, setze den Verknüpfungsmodus auf `and`:

```javascript
new URLSearchParams([
  ['search.name', '%foo%'],
  ['search.primaryEmail', '%@gmail.com'],
  ['joint', 'and'],
]);
```

Das bedeutet, Benutzer zu suchen, die `foo` im Namen haben **UND** deren E-Mail-Adresse mit `@gmail.com` endet.

### Exakte Übereinstimmung und Groß- / Kleinschreibung \{#exact-match-and-case-sensitivity}

Angenommen, du möchtest nach Benutzern suchen, deren Name genau "Alice" ist. Du kannst `mode.name` auf exakte Übereinstimmung setzen.

```javascript
new URLSearchParams([
  ['search.name', 'Alice'],
  ['mode.name', 'exact'],
]);
```

Du wirst feststellen, dass es denselben Effekt hat, wenn du den Modus `like` (Standard) verwendest oder `exact` angibst. Ein Unterschied ist, dass der Modus `exact` `=` zum Vergleichen verwendet, während `like` `like` oder `ilike` nutzt. Theoretisch sollte `=` eine bessere Performance haben.

Außerdem kannst du im Modus `exact` mehrere Werte zum Abgleich übergeben, die mit `or` verbunden werden:

```javascript
new URLSearchParams([
  ['search.name', 'Alice'],
  ['search.name', 'Bob'],
  ['mode.name', 'exact'],
]);
```

Es werden Benutzer mit dem Namen "Alice" **ODER** "Bob" gefunden.

Standardmäßig ist die Suche nicht groß- / kleinschreibungssensitiv. Um präziser zu sein, setze die Suche auf groß- / kleinschreibungssensitiv:

```javascript
new URLSearchParams([
  ['search.name', 'Alice'],
  ['search.name', 'Bob'],
  ['mode.name', 'exact'],
  ['isCaseSensitive', 'true'],
]);
```

Beachte, dass `isCaseSensitive` eine globale Einstellung ist. Daher gilt sie für JEDES Feld.

### Regulärer Ausdruck (RegEx) \{#regular-expression-regex}

PostgreSQL unterstützt zwei Arten von regulären Ausdrücken, [similar to](https://www.postgresql.org/docs/current/functions-matching.html#FUNCTIONS-SIMILARTO-REGEXP) und [posix](https://www.postgresql.org/docs/current/functions-matching.html#FUNCTIONS-POSIX-REGEXP). Setze `mode` auf `similar_to` oder `posix`, um nach regulären Ausdrücken zu suchen:

```javascript
new URLSearchParams([
  ['search', '^T.?m Scot+$'],
  ['mode', 'posix'],
]);
```

> Hinweis: Der Modus similar_to funktioniert nur bei groß- / kleinschreibungssensitiven Suchen.

### Match-Modus überschreiben \{#match-mode-override}

Standardmäßig übernehmen alle Schlüsselwörter den Match-Modus aus der allgemeinen Suche:

```javascript
new URLSearchParams([
  ['search', '^T.?m Scot+$'],
  ['mode', 'posix'],
  ['search.primaryEmail', 'tom%'], // Posix-Modus
  ['joint', 'and'],
]);
```

Um ihn für ein bestimmtes Feld zu überschreiben:

```javascript
new URLSearchParams([
  ['search', '^T.?m Scot+$'],
  ['mode', 'posix'],
  ['search.primaryEmail', 'tom%'], // Like-Modus
  ['mode.primaryEmail', 'like'],
  ['search.phone', '0{3,}'], // Posix-Modus
  ['joint', 'and'],
]);
```

## Nach externer Identität suchen \{#look-up-by-external-identity}

Um den Benutzer zu finden, der mit einer Social- oder Enterprise-SSO-Identität verknüpft ist, übergib die folgenden drei Abfrageparameter gemeinsam für eine exakte Suche:

- `identityType`: `social` für eine Social Connector-Identität oder `sso` für eine Enterprise SSO-Identität.
- `identityProvider`: das Connector-Ziel für eine Social-Identität (z. B. `dingtalk`) oder der Aussteller für eine Enterprise SSO-Identität.
- `identityId`: die vom externen Identitätsanbieter ausgegebene Benutzerkennung.

```javascript
// Finde den Benutzer, der mit einer DingTalk Social-Identität verknüpft ist
new URLSearchParams([
  ['identityType', 'social'],
  ['identityProvider', 'dingtalk'],
  ['identityId', 'dingtalk-open-id'],
]);
```

```javascript
// Finde den Benutzer, der mit einer Enterprise SSO-Identität verknüpft ist
new URLSearchParams([
  ['identityType', 'sso'],
  ['identityProvider', 'https://example.com/issuer'],
  ['identityId', 'enterprise-user-id'],
]);
```

Der Identitätsfilter wird mit anderen Suchfiltern per UND-Logik kombiniert. Um die Identitätssuche beispielsweise mit einer Stichwortsuche weiter einzuschränken:

```javascript
new URLSearchParams([
  ['identityType', 'social'],
  ['identityProvider', 'dingtalk'],
  ['identityId', 'dingtalk-open-id'],
  ['search', '%foo%'],
]);
```

## Nach benutzerdefinierten Daten suchen \{#look-up-by-custom-data}

Um Benutzer anhand der exakten Werte zu finden, die in ihren [benutzerdefinierten Daten](/user-management/user-data#custom-data) gespeichert sind, übergib einen oder mehrere `customData`-Abfrageparameter an `GET /api/users`. Jeder Wert muss ein URL-codiertes JSON-Objekt sein:

```bash
curl \
  --get \
  --data-urlencode 'customData={"qq":114514}' \
  'http://<your-logto-endpoint>/api/users'
```

`--data-urlencode` kodiert das JSON-Objekt für dich. Die äquivalente Anfrage-URL ist `GET /api/users?customData=%7B%22qq%22%3A114514%7D`.

:::note
Benutzerdefinierte Datensuchen können langsamer sein, wenn ein Mandant eine große Anzahl von Benutzern hat. Kombiniere `customData` mit einem weiteren selektiven Filter wie `search` oder einer Identitätssuche, um die Abfrage einzugrenzen.
:::

Logto vergleicht den Wert mit den `custom_data` des Benutzers mittels [JSONB-Containment](https://www.postgresql.org/docs/current/datatype-json.html#JSON-CONTAINMENT). Nur die im Wert enthaltenen Schlüssel müssen übereinstimmen; andere Schlüssel in den benutzerdefinierten Daten des Benutzers werden ignoriert.

- Typen sind strikt: Die Zahl `114514` entspricht nicht dem String `"114514"`.
- Strings sind groß- / kleinschreibungssensitiv.
- `null` entspricht nur einem expliziten JSON-`null`, nicht einem fehlenden Schlüssel.
- Verschachtelte Objekte werden rekursiv abgeglichen.
- Arrays werden elementweise abgeglichen, unabhängig von Reihenfolge oder Duplikaten.

Alle Schlüssel innerhalb eines JSON-Objekts müssen übereinstimmen (UND). Wenn du `customData` mehrmals übergibst, wird ein Benutzer gefunden, wenn eines der Objekte übereinstimmt (ODER):

```bash
curl \
  --get \
  --data-urlencode 'customData={"qq":114514}' \
  --data-urlencode 'customData={"wechat":"logto"}' \
  'http://<your-logto-endpoint>/api/users'
```

Der Filter für benutzerdefinierte Daten wird immer mit anderen Filtern per UND kombiniert, einschließlich `search`, Identitätssuche (`identityType`, `identityProvider` und `identityId`), `excludeRoleId` und `excludeOrganizationId`. Zum Beispiel gibt die folgende Anfrage Benutzer zurück, deren `qq` `114514` ist und deren Benutzername `alice` enthält:

```bash
curl \
  --get \
  --data-urlencode 'customData={"qq":114514}' \
  --data-urlencode 'search.username=%alice%' \
  'http://<your-logto-endpoint>/api/users'
```

Die Parameter `mode`, `joint` und `isCaseSensitive` wirken sich nur auf Stichwortsuchen aus und haben keinen Einfluss auf `customData`.

Die API gibt `400 Bad Request` zurück, wenn ein `customData`-Wert kein gültiges JSON-Objekt ist (z. B. `[]` oder `114514`), ein leeres Objekt `{}` ist oder ein leeres Objekt oder Array auf irgendeiner Ebene enthält (z. B. `{"profile":{}}` oder `{"tags":[]}`). Verschachtelte Parameternamen wie `customData.qq`, `customData[qq]` und `mode.customData` werden ebenfalls mit `400` abgelehnt.

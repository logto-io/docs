# パスキー (Passkeys)（WebAuthn）

[パスキー (Passkey)](https://auth.wiki/passkey) は、従来のパスワードに代わる、より安全でユーザーフレンドリーな認証手段です。公開鍵暗号方式を利用することで、ユーザーのデバイス、サービスドメイン、ユーザー ID を結び付け、フィッシングやパスワード攻撃を効果的に防ぎます。さまざまなデバイスやブラウザに対応し、バイオメトリクスやハードウェアセキュリティ機能を活用した便利な認証 (Authentication) が可能です。[WebAuthn](https://auth.wiki/webauthn) は、Web サイトがパスキーを実装するための API を提供します。

Logto は、[多要素認証 (MFA)](/end-user-flows/mfa/configure-mfa) および [パスキーサインイン](/end-user-flows/sign-up-and-sign-in/passkey-sign-in) の両方でパスキー (WebAuthn) をサポートしています。基盤となる同じ WebAuthn 資格情報は、テナント設定に応じて両方で再利用できます。

## 概念 \{#concepts}

一般的に顧客は WebAuthn よりもパスキー (Passkeys) を知っていますが、両者の関係や使い方はどうなっているのでしょうか？これらの概念を整理します：

- **パスキー (Passkeys)**：パスキーは、FIDO ベースのフィッシング耐性を持つ資格情報で、パスワードの代替となります。非対称公開鍵暗号方式を利用し、セキュリティを強化します。ハードウェアトークンやセキュリティキー（USB や Bluetooth デバイスなど）も含まれます。「パスキー (Passkeys)」はユーザーに表示される認証 (Authentication) 方法であり、プロダクトクライアント内で使用すべきです。
- **WebAuthn**：W3C と FIDO Alliance によって開発された JavaScript API で、Web アプリケーションに FIDO2 標準の認証 (Authentication) を提供します。パスキー (Passkeys) は WebAuthn がサポートする認証 (Authentication) 方法の一つです。Logto コンソールでは、この要素は **「パスキー (Passkeys)」** と表示されます（API や SDK では引き続き識別子 `WebAuthn` を使用）。

WebAuthn は、ユーザーが選択できる多様な認証器を提供しており、ローカル利用とクラウド利用の 2 種類があります：

- **プラットフォーム認証器（内部認証器）**：特定のデバイス OS（パソコン、ノートパソコン、スマートフォン、タブレットなど）に紐付いており、そのデバイスでのみ動作します。バイオメトリクスやデバイスパスコードなどで認証 (Authentication) でき、迅速な認証 (Authentication) が可能です。例：macOS や iOS の Touch ID、Face ID、デバイスパスコードで認証 (Authentication) される iCloud キーチェーン、Windows Hello の顔認証、指紋認証、PIN など。
- **ローミング認証器（外部認証器、クロスプラットフォーム認証器）**：ハードウェアセキュリティキーやスマートフォンなど、別の携帯可能なデバイスやソフトウェアアプリケーションです。USB 接続や NFC、Bluetooth を有効にしてデバイスと連携します。ローミング認証器は特定のデバイスやブラウザに限定されず、柔軟に利用できます。

WebAuthn の原理やプロセスについてさらに詳しく知りたい場合は、ブログ記事 [WebAuthn とパスキー 101](https://blog.logto.io/web-authn-and-passkey-101/) および [WebAuthn 統合前に知っておくべきこと](https://blog.logto.io/webauthn-base-knowledge/) をご覧ください。

## MFA 用パスキー認証 (Authentication) の設定 \{#configure-passkeys-verification-for-mfa}

1. <CloudLink to="/mfa">コンソール > 多要素認証 (MFA)</CloudLink> に移動します
2. **パスキー (Passkeys)** 要素を有効にします。パスキーは他の MFA 要素（TOTP、SMS、バックアップコード）と組み合わせて利用することを推奨します。これにより単一要素への依存を減らせます。
3. 希望する MFA ポリシー（任意、適応型、必須）を設定します
4. 設定変更を保存します

:::tip
同じユーザーが [パスキーサインイン](/end-user-flows/sign-up-and-sign-in/passkey-sign-in) でサインインした場合、Logto は別途 MFA 認証 (Authentication) ステップをスキップします。パスキーサインイン自体が WebAuthn ベースの認証 (Authentication) 要件を満たしているためです。
:::

:::note 制限事項に注意

WebAuthn を実装する際は、いくつかの制限事項に注意が必要です：

1. **プラットフォームとブラウザの制限**：Logto は現在、ネイティブアプリケーション向けの WebAuthn サポートを提供していません。また、WebAuthn 認証器の利用可否はブラウザやデバイスの機能に依存します（[対応状況を確認](https://caniuse.com/?search=webauthn)）。したがって、WebAuthn だけで多要素認証 (MFA) を実装することはできません。必要に応じて、どのブラウザやデバイスが製品にアクセスできるかを制御してください。
2. **ドメインの制限**：ドメインを変更すると、既存の WebAuthn アカウントによるユーザー認証 (Authentication) ができなくなる場合があります。パスキーは現在の Web ページの特定ドメインに紐付いており、異なるドメイン間で利用できません。
3. **デバイスの制限**：「このデバイス」プラットフォーム認証器に依存している場合、デバイスを紛失するとアカウントへのアクセスも失われます。認証 (Authentication) アクセスを強化するため、複数の認証 (Authentication) 要素をユーザーに提供することを推奨します。

:::

## パスキー管理の設定 \{#configure-passkeys-management}

Account API を利用して、ユーザーがパスキーを追加・表示・名前変更・削除できるカスタムアカウント管理画面を構築できます。これにより、個別のアカウントセンターやクロスデバイスバックアップシナリオの実現が可能です。

実装手順や API エンドポイントの詳細は、[Account API によるアカウント設定](/end-user-flows/account-settings/by-account-api#link-a-new-webauthn-passkey) をご覧ください。

## パスキーのエクスポート \{#export-passkeys}

[Management API](/integrate-logto/interact-with-management-api) を利用して、Logto がユーザーごとに保存している WebAuthn 資格情報をエクスポートできます。エクスポートした情報を、同じドメインで WebAuthn を提供する他のシステムへ移行することで、ユーザーは既存のパスキーで引き続きサインインできます。

`includeWebAuthnCredentials` クエリパラメーターを `true` に設定して [`GET /api/users/{userId}/mfa-verifications`](https://openapi.logto.io/operation/operation-listusermfaverifications) を呼び出します：

```bash
curl "https://[tenant-id].logto.app/api/users/{userId}/mfa-verifications?includeWebAuthnCredentials=true" \
  -H 'authorization: Bearer <management-api-access-token>'
```

レスポンス内の各 WebAuthn エントリーには、保存された資格情報が含まれます：

```json
[
  {
    "id": "wv9m3k2x7p1q",
    "createdAt": "2026-10-12T08:31:24.000Z",
    "lastUsedAt": "2026-11-02T06:15:09.000Z",
    "type": "WebAuthn",
    "agent": "Mozilla/5.0 (Macintosh) ...",
    "name": "MacBook",
    "rpId": "auth.example.com",
    "credentialId": "Ab3dY0n9Kq2LwX8mR4sT1uV6zE",
    "publicKey": "pQECAyYgASFYIOrE5x...",
    "counter": 0,
    "transports": ["internal", "hybrid"]
  }
]
```

| フィールド     | 説明                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| `credentialId` | WebAuthn 資格情報 ID（base64url エンコード）。                                                           |
| `publicKey`    | 資格情報の公開鍵（COSE 形式、base64url エンコード）。                                                    |
| `counter`      | Logto がこの資格情報で最後に確認した署名カウンター（`signCount`）。多くのパスキーは常に `0` を返します。 |
| `transports`   | 登録時に認証器が報告したトランスポート（`internal`、`hybrid`、`usb` など）。                             |
| `rpId`         | 資格情報が登録されたリライングパーティ ID（ドメイン）。                                                  |
| `createdAt`    | 資格情報が登録された日時。                                                                               |
| `lastUsedAt`   | 資格情報が最後にユーザー認証 (Authentication) に使用された日時。                                         |

`includeWebAuthnCredentials` を指定しない場合、レスポンスには `credentialId`、`publicKey`、`counter`、`transports`、`rpId` は含まれません。他の MFA 要素は変更されません。このパラメーターは読み取り専用の Management API アクセスでも利用できます。なぜなら、資格情報 ID や公開鍵だけではサインインできないためです。

資格情報を他のシステムにインポートする際は：

- **同じドメインを維持してください。** パスキーは登録時のリライングパーティ ID でのみ動作します。他のシステムもエクスポートした `rpId` を WebAuthn のリライングパーティ ID として使用し、そのドメイン（例：[カスタムドメイン](/logto-cloud/custom-domain)）でサインインを提供する必要があります。
- **`rpId` のない資格情報に対応してください。** Logto がリライングパーティ ID の記録を開始する前に登録され、以降使用されていない資格情報には `rpId` がありません。これらは登録時にサインインページを提供していたドメインに紐付いており、現在のカスタムドメインとは異なる場合があります。
- **ユーザーハンドルをマッピングしてください。** Logto は Logto ユーザー ID の UTF-8 バイト列を WebAuthn の `userHandle` として登録します。パスキーサインイン時、認証器はこの値を返すため、他のシステムでも移行ユーザーにマッピングする必要があります。
- **カウンターを維持してください。** `counter` を資格情報の現在の署名カウンターとして保存し、他のシステムでもクローン認証器の検出を継続できるようにします。

## パスキー設定フロー \{#passkey-setup-flows}

パスキー仕様では、ユーザーが現在のページでボタンをクリックして認証 (Authentication) コンポーネントを起動する必要があります。つまり、セットアップフロー・認証 (Authentication) フローのいずれでも、ユーザーはランディングページにリダイレクトされて WebAuthn を開始する必要があります。

## パスキー認証 (Authentication) フロー \{#passkey-verification-flows}

ユーザーがパスキーを含む複数の MFA 方法を設定している場合、パスキーはその高いセキュリティと利便性から、最初の画面で推奨される MFA 認証 (Authentication) 方法として表示されます。ユーザーは「他の方法で認証 (Authentication) する」をクリックして、他の認証 (Authentication) 方法に切り替えることもできます。詳細は [MFA の設定](/end-user-flows/mfa/configure-mfa#mfa-verification-flow) をご覧ください。

ユーザーが [パスキーサインイン](/end-user-flows/sign-up-and-sign-in/passkey-sign-in) でサインインを完了した場合、他の第一要素を入力せずに済み、Logto は追加の MFA ステップを求めません。これは、パスキー自体が WebAuthn MFA 要素として扱われるためです。

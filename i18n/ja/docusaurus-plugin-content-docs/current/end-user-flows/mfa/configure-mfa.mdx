# 多要素認証 (MFA) の設定

## Logto で MFA 設定を構成する \{#configure-mfa-settings-in-logto}

Logto は、さまざまなセキュリティ要件に対応する柔軟な MFA 設定オプションを提供しています。すべてのユーザーに対してグローバルレベルで MFA を構成したり、マルチテナントアプリケーション向けに組織ごとに有効化することもできます。

### グローバル MFA 設定 \{#global-mfa-configuration}

ユーザーの Logto サインインフローで MFA を有効にするには、以下の手順に従ってください：

1. <CloudLink to="/mfa">コンソール > 多要素認証</CloudLink> に移動します。
2. ユーザー向けにサポートされている認証要素を有効にします。
   1. プライマリ要素:
      - [パスキー (WebAuthn)](/end-user-flows/mfa/webauthn)：デバイスの生体認証やセキュリティキーなどをサポートする Web 製品に適した高セキュリティオプションで、強力な保護を実現します。
      - [認証アプリ OTP](/end-user-flows/mfa/authenticator-app-otp)：最も一般的で広く受け入れられている方法です。Google Authenticator や Authy などの認証アプリによって生成される時限ワンタイムパスワード (TOTP) を使用します。
      - [SMS 認証](/end-user-flows/mfa/sms-mfa)：ユーザーの登録済み電話番号に SMS でワンタイム認証コードを送信する便利な方法で、追加アプリなしでモバイル認証を好むユーザーに最適です。
      - [メール認証](/end-user-flows/mfa/email-mfa)：ユーザーの登録済みメールアドレスにワンタイム認証コードを送信する広く利用可能な方法で、すべてのプラットフォームやデバイスのユーザーに適しています。
   2. バックアップ要素:
      - [バックアップコード](/end-user-flows/mfa/backup-codes)：上記のプライマリ要素で認証できない場合のバックアップオプションです。このオプションを有効にすると、ユーザーのアクセス成功率が向上します。
   3. SMS またはメール認証を有効にした場合は、**メール/SMS 2段階認証** で対象ユーザーを選択します。詳細は [メールと SMS MFA 登録](#email-and-sms-mfa-enrollment) を参照してください。
3. ドロップダウンから **MFA 必須ポリシー** を選択します。このポリシーは、サインイン時にユーザーが MFA を完了する必要があるタイミングを制御します：
   - **オプション MFA** (_Optional MFA: Let users choose to enable MFA for their own account security_)：ユーザー自身がアカウントのセキュリティ向上のために MFA を有効にするかどうかを選択できます。サインイン時に MFA 設定をスキップでき、後からセルフサービスのアカウント設定ページで設定できます。[ユーザーアカウント設定ページの実装方法](/end-user-flows/account-settings/) もご覧ください。
   - **アダプティブ MFA** (_Adaptive MFA: Only ask for MFA when a sign-in seems risky (e.g., new country / long inactivity)_)：サインインが異常と判断された場合のみ MFA を要求し、低リスクのサインインはスムーズに進めます。Logto は組み込みのコンテキストリスクルール（新しい国、地理的移動速度、長期間の非アクティブ、不審な IP シグナル）を評価します。このモードは既存の MFA 設定（少なくとも 1 つの MFA 要素が有効である必要あり）に依存し、エンドユーザーのサインインフローに適用され、デバイスフィンガープリントには依存しません。ルールの閾値や前提条件、Webhook の詳細は [アダプティブ MFA](/end-user-flows/mfa/adaptive-mfa) を参照してください。
   - **必須 MFA** (_Mandatory MFA: Requires all users to complete MFA every time they sign in_)：すべてのユーザーがサインインのたびに MFA を完了する必要があります。MFA を設定していないユーザーは、続行前にセットアップを完了する必要があります。
   - **オプション MFA** を選択した場合は、**MFA セットアッププロンプト** ポリシーを構成します：
     - **ユーザーに MFA セットアップを求めない**：サインインや登録時に MFA セットアップを促しません。
     - **登録時に MFA セットアップを促す（スキップ可能・一度きりのプロンプト）**：新規ユーザーは登録時に、既存ユーザーは次回サインイン時に MFA セットアップを促されます。スキップ可能で、再度表示されません。
     - **登録後の次回サインイン時に MFA セットアップを促す（スキップ可能・一度きりのプロンプト）**：新規ユーザーは登録後の次回サインイン時に、既存ユーザーは次回サインイン時に MFA セットアップを促されます。スキップ可能で、再度表示されません。
   - **アダプティブ MFA** を選択した場合は、スキップ不可の 2 つの **MFA セットアッププロンプト** ポリシーのみがサポートされます（**ユーザーに MFA セットアップを求めない** は利用不可）：
     - **登録時に MFA セットアップを促す（スキップ不可）**：新規ユーザーは登録時に、既存ユーザー（MFA 未設定）は次回サインイン時に MFA セットアップを完了する必要があります。
     - **登録後の次回サインイン時に MFA セットアップを促す（スキップ不可）**：新規ユーザーは登録後の次回サインイン時に、既存ユーザー（MFA 未設定）は次回サインイン時に MFA セットアップを完了する必要があります。

**オプション MFA** でセットアッププロンプトを有効にした場合（`登録時に MFA セットアップを促す（スキップ可能・一度きりのプロンプト）` または `登録後の次回サインイン時に MFA セットアップを促す（スキップ可能・一度きりのプロンプト）`）、Logto はまず `2段階認証を有効にする` というタイトルの確認ページを表示します。ユーザーは `2段階認証を有効にする` を選択して MFA バインディングに進むか、プロンプトをスキップして MFA を有効にせずにサインイン/サインアップフローを完了できます。**アダプティブ MFA** または **必須 MFA** では、`2段階認証を有効にする` 確認ページを表示せず、直接 MFA 要素のバインディング画面に進みます。

:::tip
ユーザーが MFA 登録をスキップした後に再度プロンプトを表示したい場合は、スキップ状態をリセットしてください。管理者は Management API (`PATCH /api/users/{userId}/logto-configs`) を、セルフサービスフローを構築する開発者は Account API (`PATCH /api/my-account/logto-configs`) を利用できます。 [Management API リファレンス](https://openapi.logto.io/operation/operation-updateuserlogtoconfigs) · [Account API リファレンス](https://openapi.logto.io/operation/operation-updatelogtoconfig)
:::

### メールと SMS MFA 登録 \{#email-and-sms-mfa-enrollment}

メールおよび SMS 認証コードは、ユーザーのプライマリメールアドレスおよびプライマリ電話番号に送信されます。**メール/SMS 2段階認証** 設定は、これらの要素を持つユーザーを決定します。SMS またはメール認証コード要素を有効にした場合に表示され、両方の要素に適用されます。

- **認証済みメールまたは電話番号を持つすべてのユーザー**：プライマリメールアドレスを持つすべてのユーザーはメール MFA を、プライマリ電話番号を持つすべてのユーザーは SMS MFA を、セットアップ不要で利用できます。認証済みメールまたは電話番号でサインアップしたユーザーはすでにその要素を持っています。
- **セットアップしたユーザーのみ**：ユーザーは、MFA セットアップフローでコードを認証する、[アカウントセンター](/end-user-flows/account-settings/by-account-center-ui) や [Account API](/end-user-flows/account-settings/by-account-api#manage-email-and-sms-mfa) で設定する、または管理者が [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) で追加することで、メールまたは SMS MFA を持つことができます。認証済みメールや電話番号を持っているだけでは MFA は有効にならないため、すべてのユーザーを登録せずに、認証アプリやパスキーと並んでメールや SMS を MFA オプションとして提供できます。

新規テナントはデフォルトで **セットアップしたユーザーのみ** となります。以前に作成されたテナントは、変更するまで **認証済みメールまたは電話番号を持つすべてのユーザー** のままです。Management API では、この設定は [サインイン体験](https://openapi.logto.io/operation/operation-updatesigninexp) の `mfa.verificationCodeEnrollment` で、値は `Implicit` と `Explicit` です。`mfa` を更新する際に `verificationCodeEnrollment` を省略すると、`Implicit` にリセットされます（`mfa` 全体が置き換えられるため）。

Logto は、両モードで各メールまたは SMS MFA セットアップを記録します。この記録は選択を保存し、アドレス自体は保存しません。ユーザーがプライマリメールアドレスや電話番号を変更または削除しても記録は残り、どちらもない場合は無視されます。後で新しいアドレスを追加した場合は再びカウントされます。

**モード切り替えについて**

切り替えは即時反映され、ユーザーデータは変更されません。コンソールで確認が求められます。

- **セットアップしたユーザーのみへ切り替え**：セットアップしていないユーザーのメール・SMS MFA はカウントされなくなります。唯一の要素がメールや電話番号だったユーザーは MFA 未設定ユーザーとして扱われ、サインイン時に認証を求められず、MFA ポリシーで必要またはプロンプトされた場合のみセットアップを求められます。Logto は自動で誰も登録しません。特定ユーザーにメールや SMS MFA を残したい場合は、切り替え前に [Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) で追加してください。
- **認証済みメールまたは電話番号を持つすべてのユーザーへ切り替え**：プライマリメールアドレスまたは電話番号を持つすべてのユーザーが再びメールまたは SMS MFA を持つことになります。セットアップしていないユーザーも含まれます。

### 組織単位の MFA 設定 \{#organization-level-mfa-configuration}

[組織](/organizations) をサポートするマルチテナントアーキテクチャ製品では、すべてのユーザーに MFA を必須とする必要はありません。代わりに、組織ごとに MFA を有効化でき、各クライアントのニーズに合わせて要件を調整できます。始めるには [組織メンバーに MFA を必須化する](/organizations/organization-management#require-mfa-for-organization-members) を参照してください。

**MFA 必須** ドロップダウンで **オプション MFA** を選択した場合、コンソールに **組織が MFA を有効化した後のユーザーへの MFA セットアッププロンプト** 設定が表示されます。これを **次回サインイン時に MFA セットアップを促す（スキップ不可）** に設定すると、MFA 必須の組織メンバーは次回サインイン時に MFA セットアップを完了するよう促され、スキップできません。（この設定は **アダプティブ MFA** または **必須 MFA** 選択時はコンソールに表示されず保存もされません。）

**アダプティブ MFA** では、リスクルールが発動しない低リスクサインインは、ユーザーが個別に **MFA セットアップ必須** を有効にしている場合や `isMfaRequired` が有効な組織に所属していても、MFA 認証を求められません。

### 追加 MFA 要素の提案 \{#suggest-adding-another-mfa-factor}

<CloudLink to="/mfa">コンソール > 多要素認証</CloudLink> の **追加 MFA 要素の提案**
スイッチ（デフォルト有効、Sign-in Experience API の `mfa.skipAdditionalBindingSuggestion`
で制御）は、以下の場合にサインアップまたはサインイン時にユーザーへ追加 MFA 要素の追加を促します：

- ユーザーの唯一の MFA 要素がサインインに使ったメールアドレス、電話番号、またはパスキーであり、
- テナントで他の MFA 要素が少なくとも 1 つ有効になっている場合。

ユーザーはこのプロンプトをスキップできます。スキップした場合、Logto はユーザーの `logtoConfig` に `mfa.additionalBindingSuggestionSkipped: true` を保存し、今後のサインインで再表示されません。このフラグは [Account API](/end-user-flows/account-settings/by-account-api) で更新またはリセットできます（`PATCH /api/my-account/logto-configs` で `{ "mfa": { "additionalBindingSuggestionSkipped": false } }` を送信。`GET /api/my-account/logto-configs` および `GET /api/users/{userId}/logto-configs` ではこのフィールドは返されません）。

### ユーザー単位の MFA 必須設定 \{#per-user-mfa-requirement}

管理者は、テナントの **オプション MFA** プロンプト設定に関係なく、個別ユーザーに MFA セットアップを必須化できます：

- **コンソールで**：<CloudLink to="/users">コンソール > ユーザー管理</CloudLink> を開き、ユーザーを選択し、**多要素認証** セクションの **MFA セットアップ必須** を有効にします。
- **Management API 経由で**：`PATCH /api/users/{userId}/logto-configs` で `{ "mfa": { "required": true } }` を送信（`GET /api/users/{userId}/logto-configs` で確認）。[Management API によるアカウント設定](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) を参照。

エンドユーザーは Account API (`PATCH /api/my-account/logto-configs`) で `mfa.required` を変更できません。セルフサービスクライアントでは `GET /api/my-account/mfa-settings` の `required` で読み取り専用として公開されます。

ユーザー単位の `mfa.required` が `true` の場合、サインイン完了前に少なくとも 1 つの MFA 要素をセットアップする必要があり、スキップできません。**オプション MFA** では、ユーザーが `skipMfaOnSignIn` や `enabled: false` を設定していてもサインイン時に MFA 認証が必須となります。**アダプティブ MFA** では、リスクルールが発動しない低リスクサインインは引き続き MFA 認証を求められません。

## MFA ユーザーフロー \{#mfa-user-flow}

### MFA セットアップフロー \{#mfa-set-up-flow}

MFA を有効にすると、サインインやサインアップ時にユーザーへ MFA セットアップを促す場合があります。**オプション MFA** が **MFA 必須ポリシー** で選択されている場合のみ、ユーザーはこのセットアッププロセスをスキップできます。

1. **サインインまたはサインアップページにアクセス**：ユーザーがサインインまたはサインアップページに移動します。
2. **サインインまたはサインアップを完了**：ユーザーがサインインまたはサインアップフロー内でアイデンティティ認証を完了します。
   - **オプション MFA** でセットアッププロンプトが有効な場合、Logto はまず `2段階認証を有効にする` 確認ページを表示し、ユーザーは MFA セットアップをスキップするか `2段階認証を有効にする` をクリックして続行できます。
   - **アダプティブ MFA** または **必須 MFA** では、`2段階認証を有効にする` ページを表示せず、直接 MFA 要素のバインディング画面に進み、スキップできません。
3. **MFA プライマリ要素のセットアップ**：ユーザーはパスキー、認証アプリ OTP、SMS コード、メールコードのいずれかのプライマリ MFA 要素のセットアップを促されます。
   - 複数のプライマリ要素が有効な場合、ユーザーは好みのオプションを選択できます。
   - プライマリ要素がサインアップ識別子（例：SMS やメール）と同じ場合は事前認証済みのため、再認証は不要です：
     - **認証済みメールまたは電話番号を持つすべてのユーザー** では、すでにユーザーの要素となっており、次のステップ（例：「別の 2段階認証を追加」や「バックアップ要素を保存」）に直接進みます。
     - **セットアップしたユーザーのみ** では、他の要素と同様に提供され、セットアップ時に 2 回目のコードは送信されません。詳細は [メールと SMS MFA 登録](#email-and-sms-mfa-enrollment) を参照してください。
   - **オプション MFA** が **MFA 必須ポリシー** で選択されている場合、「スキップ」ボタンでこのステップをスキップできます。
4. **MFA バックアップ要素のセットアップ**：**バックアップコード** が有効な場合、ユーザーはプライマリ認証要素の設定完了後にバックアップコードの保存を促されます。自動生成されたバックアップコードが表示され、ダウンロードして安全に保管できます。ユーザーはバックアップコードを手動で確認し、MFA セットアッププロセスを完了します。

### MFA 認証フロー \{#mfa-verification-flow}

MFA を設定したユーザーは、サインイン時に設定済みの MFA 要素で本人確認を求められます。どの認証要素が使われるかは Logto の MFA 設定とユーザー設定によります。

[パスキーサインイン](/end-user-flows/sign-up-and-sign-in/passkey-sign-in) でサインインした場合、Logto は別途 MFA 認証ステップをスキップします。これはサインインに使ったパスキー自体が WebAuthn MFA 要素であるためです。

- 利用可能な MFA 要素が 1 つだけの場合は、その要素で直接認証します。
- 複数の MFA 要素が利用可能な場合、Logto は固定の優先順位で並べ、最初に利用可能な要素を直接開きます：
  1. **パスキー (WebAuthn)**
  2. **認証アプリ OTP (TOTP)**
  3. **SMS 認証コード**
  4. **メール認証コード**
  5. **バックアップコード**
- 2 つ以上の MFA 要素が利用可能な場合、認証ページに **別の方法で認証する** リンクが表示され、ユーザーは選択リストから他の利用可能な要素（有効な場合はワンタイムバックアップコードも含む）に切り替えられます。

### サインイン時のバインディングルールと例外 \{#sign-in-binding-rules-and-exemptions}

MFA ジャーニー設計時は、以下の挙動に注意してください：

- **バックアップコードの再生成プロンプト**：**バックアップコード** が有効で、他の MFA 要素がすでに有効な場合、以前生成したコードをすべて使い切った、またはユーザー登録後に **バックアップコード** を有効にした場合、サインイン時に新しいバックアップコードの生成・保存を促します。
- **サインイン時の要素バインディングには認証済み要素が必要**：ユーザーがすでに MFA 要素を持っている `SignIn` インタラクション中に新しい要素をバインドする場合（バックアップコードの再生成や「追加 MFA 要素の提案」プロンプトに従う場合も含む）、まず MFA 認証チャレンジを完了する必要があります（またはパスキーサインインやエンタープライズ SSO でサインイン）。MFA 認証をバイパスしたサインイン（[信頼済みデバイス](/end-user-flows/mfa/trusted-devices)、リスクルール未発動の [アダプティブ MFA](/end-user-flows/mfa/adaptive-mfa)、ユーザーが **オプション MFA** をスキップした場合（`skipMfaOnSignIn` / `enabled: false`）など）では、そのサインインフロー中に新しい MFA 要素をバインドできません。これらのセッションでは、後からアカウントセンターや [Account API](/end-user-flows/account-settings/by-account-api) で要素を追加できます。
- **エンタープライズ SSO 例外**：[エンタープライズシングルサインオン (SSO)](/end-user-flows/enterprise-sso) でサインインまたは登録した場合、そのインタラクション中はテナントの MFA 認証や MFA セットアッププロンプトをスキップします（ただし、クライアントが `acr_values` で明示的に MFA を要求した場合（例：`urn:logto:acr:mfa`）を除く）。
- **パスワードリセット例外**：[パスワードをお忘れの場合](/end-user-flows/sign-up-and-sign-in/reset-password) フローでは、MFA 認証や MFA セットアッププロンプトをスキップします。

## MFA 管理 \{#mfa-management}

サインイン/サインアップ時の初期セットアップ以外にも、ユーザーはセルフサービスのアカウントセンターで MFA 設定を管理できます。これにより、ユーザーは必要に応じて MFA 要素のバインドや解除が柔軟に行えます。

### アカウントセンターの構築 \{#building-an-account-center}

Logto の [Account API](/end-user-flows/account-settings/by-account-api) を利用して、包括的なアカウントセンターを構築できます。ユーザーは以下の操作が可能です：

- **新しい MFA 要素のバインド**：追加の認証アプリやパスキーの追加、バックアップコードの再生成
- **既存 MFA 要素の解除**：不要になった MFA 方法の削除
- **現在の MFA 状態の確認**：現在設定されている MFA 要素の確認

### ログイン後の MFA セットアッププロンプト \{#post-login-mfa-setup-prompts}

初回登録時に MFA を必須としないアプリケーションでは、MFA セットアップを促すインテリジェントなプロンプトを実装できます：

- **条件付きプロンプト**：ユーザーの行動やアカウント価値に基づいて MFA セットアップを推奨
- **セキュリティダッシュボード**：MFA 有効化で向上するセキュリティスコアを表示
- **段階的オンボーディング**：MFA セットアップを段階的なセキュリティ強化フローの一部として提示

これらのパターンの実装方法は [Account API](/end-user-flows/account-settings/by-account-api) をご覧ください。

### コンソールでユーザーの MFA を管理 \{#manage-users-mfa-in-console}

<CloudLink to="/user">コンソール > ユーザー管理</CloudLink> では、管理者がユーザーの MFA
設定を効果的に管理できます：

- **ユーザーの MFA 状態を確認**：各ユーザーに有効な MFA 要素を確認できます。メールや SMS 要素が「認証済みメールまたは電話番号を持つためにのみカウントされている」場合や、「ユーザーがセットアップしたがカウントされていない」場合（要素が無効な場合など）は、ヒントが表示されます。
- **ユーザーの MFA を削除**：保存されている MFA 要素を 1 つずつ削除できます。暗黙的なメールや SMS 認証コード行はこのテーブルから直接削除できません。また、パスキーサインインが有効な場合、パスキー (WebAuthn) 行には削除ボタンがなく、同じユーザー詳細ページの **パスキー** セクションで管理します。

ユーザーにメールや SMS MFA を追加するには、[Management API](/end-user-flows/account-settings/by-management-api#user-mfa-settings-management) を利用してください。

### よくある質問 \{#faqs}

<details>
<summary>
### 管理者がユーザーの既存 MFA 要素を削除した場合どうなりますか？ \{#what-happens-when-administrators-remove-users-existing-mfa-factors}
</summary>
管理者がユーザーのプライマリ MFA 要素（パスキー、認証アプリ OTP、SMS、メール）をすべて削除した場合、次回サインイン時に以下のシナリオが発生します：

**シナリオ 1：MFA 要素が残っていない場合**

- MFA 要素（バックアップコードも含む）が存在せず、[MFA ポリシー](#global-mfa-configuration) で MFA が必須の場合、ユーザーは MFA 認証なしでサインインでき、直後に再度 MFA セットアップを促されます。

**シナリオ 2：バックアップコードが残っている場合**

- バックアップコードがまだ利用可能な場合、ユーザーはまずサインイン時にバックアップコードで認証する必要があります。
- バックアップコード認証に成功すると、新しいプライマリ MFA 要素のセットアップを促されます。
- このセットアップをスキップできるかどうかは、設定している MFA ポリシーによります。
- この仕組みにより、プライマリ要素がない場合でもユーザーがアカウントにロックアウトされるのを防ぎます。

 </details>

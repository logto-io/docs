# Self-hosted license

A self-hosted license is a signed key that unlocks the paid features of a [Logto self-hosted plan](https://logto.io/self-hosted-plans) on your own Logto OSS instance. Without a license, Logto OSS behaves exactly as before.

:::note
Licenses are for self-hosted Logto OSS only. On Logto Cloud, features are part of your [tenant's plan](/logto-cloud/billing-and-pricing) and license endpoints are not available.
:::

## What a license unlocks \{#what-a-license-unlocks}

A Self-hosted Pro license unlocks the following on your instance:

| Feature                                                                    | Without a license                   | With a license                                                                       |
| -------------------------------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------ |
| [Hide Logto branding](/customization/match-your-brand#hide-logto-branding) | "Powered by Logto" is always shown. | You can hide it.                                                                     |
| [Bring your UI](/customization/bring-your-ui) and custom CSP sources       | Not available.                      | Upload your own sign-in UI to [your own storage](#set-up-storage-for-bring-your-ui). |
| Console members and invitations                                            | Not available.                      | Invite members to Console and manage their roles in **Tenant Settings > Members**.   |
| Mandatory MFA for Console                                                  | Optional MFA only.                  | Require every Console member to set up MFA, in **Tenant Settings > Settings**.       |
| [SAML apps](/integrate-logto/saml-app)                                     | Up to 3 SAML apps.                  | No limit on the number of SAML apps.                                                 |

Features that are not in this list are not affected by a license.

## Get a license \{#get-a-license}

Request a license through the [self-hosted plans page](https://logto.io/self-hosted-plans). Logto will then provide you with two keys for the same license:

- **Production key**: Use this for the production deployment covered by your subscription. Unless your order form states otherwise, each subscription covers one production deployment.
- **Non-production key**: Use this for development, testing, and staging deployments that support the same production deployment. These deployments must not serve production traffic.

Both keys unlock the same features and quotas. Having two keys does not grant permission to run two production deployments. Your permitted use is governed by the [Self-hosted Subscription Terms](https://logto.io/terms/self-hosted) and your order form.

The key you install tells Logto which kind of deployment it is. Logto does not verify this technically, so install the key that matches the deployment.

## Install a license \{#install-a-license}

You can install a license in Console or through the Management API. Either way, Logto verifies the signature on your instance before saving the key, and rejects a key that is invalid, tampered with, or already expired.

### In Console \{#in-console}

1. Go to **Console > Tenant Settings > License**.
2. Paste your license key and click **Install license**.

Once installed, the page shows the details of your license. To switch to another key, for example from a non-production key to a production key, or to a freshly issued key, click **Replace license**.

### Using the Management API \{#using-the-management-api}

Send the key to `PUT /api/systems/license` with an access token for the [Logto Management API](/integrate-logto/interact-with-management-api):

```bash
curl -X PUT 'https://your-logto-endpoint/api/systems/license' \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{ "license": "<your_license_key>" }'
```

A successful request returns `204 No Content`. The request fails with:

- `400` and `license.invalid_key` if the key is not signed by Logto or has been modified.
- `400` and `license.expired_key` if the key is past its expiration. Get a fresh key and install it again.
- `501` if your Logto is running on Logto Cloud.

To check what is installed, send `GET /api/systems/license`. It returns the plan, environment, entitlements, expiration, and refresh status of the license, and the [usage](#usage-limits) of your deployment with any limits it exceeds. It never returns the key itself, and returns `404` when no license is installed. See the [Management API reference](https://openapi.logto.io) for the full request and response schema.

### Multiple instances \{#multiple-instances}

The license is stored in your Logto database, so you only install it once for all Logto instances that share the same database.

## Refresh and grace period \{#refresh-and-grace-period}

Logto verifies the license signature locally, so signing in to your applications never depends on a connection to Logto, and a failed refresh never blocks sign-in traffic.

To pick up renewals and cancellations, your instance checks in with Logto Cloud:

- **Weekly check-in.** When the last successful refresh is more than 7 days old, Logto refreshes the license in the background, as part of handling a request. If an attempt fails, it is retried later, at most once per hour. A license that has just been installed is refreshed right away.
- **30 days of grace.** If refreshes fail, for example because your instance cannot reach the internet, your features keep working for 30 days after the last successful refresh. After that, your instance reverts to the OSS defaults.
- **A refused refresh.** If Logto refuses to refresh the license, for example because the subscription was canceled, the license page shows the reason. The grace period still counts from the last successful refresh.

The refresh is an outbound HTTPS request from your instance to `https://cloud.logto.io`. If your instance runs behind a firewall, allow this destination.

### What your instance sends \{#what-your-instance-sends}

A refresh request contains only:

- Your license key, which identifies the license by its `licenseId`.
- A `deploymentId`: a random identifier generated when you first install a license. It is stored in your database, shared by every instance using that database, and never changes, including when you replace the license.
- The Logto version.
- The usage counts of your deployment, unless you [turn off usage reporting](#turn-off-usage-reporting).

The usage counts are totals across all tenants except the admin tenant, which hosts Console itself. Months are UTC calendar months:

| Field                                                              | Description                                                                                           |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `month`                                                            | The current month, as `YYYY-MM`.                                                                      |
| `mau.lastMonth`, `mau.monthToDate`                                 | [Monthly active users](#how-usage-is-counted) in the last full month and in the current month so far. |
| `monthlyAccessTokens.lastMonth`, `monthlyAccessTokens.monthToDate` | [Access tokens issued](#how-usage-is-counted) in the last full month and in the current month so far. |
| `tenants`                                                          | The number of tenants.                                                                                |

Usage counts contain no personal data or records of individual users. Logto does not collect hostnames, domains, configuration, or any other data from your instance. Logto uses this data to keep your license current, to compare your usage with the [usage limits](#usage-limits) of your plan, to count your active production deployments, and to provide support. See section 10.2 of the [Self-hosted Subscription Terms](https://logto.io/terms/self-hosted).

The behavior is open source, see [`LicenseReader.ts`](https://github.com/logto-io/logto/blob/master/packages/core/src/license/LicenseReader.ts) and [`usage.ts`](https://github.com/logto-io/logto/blob/master/packages/core/src/license/usage.ts).

### Turn off usage reporting \{#turn-off-usage-reporting}

Usage reporting is on by default. To turn it off, set this environment variable on **every** Logto instance that shares your database, then restart them:

```bash
SELF_HOSTED_LICENSE_USAGE_REPORTING_DISABLED=1
```

Any instance can run the weekly refresh, and the instance that runs it decides whether usage counts are sent. If one instance does not have the variable, your usage can still be reported. There is no setting in Console or the Management API for this. To check the current state, look at `usageReportingEnabled` in the response of `GET /api/systems/license`.

When usage reporting is off:

- The refresh still runs and still sends your license key, `deploymentId`, and Logto version, so your deployment is still counted as a [production deployment](#how-usage-is-counted).
- Your instance still compares its usage with the limits of your license, and Console still [warns you](#when-a-limit-is-exceeded) when a limit is exceeded.
- Your obligations under section 4 of the [Self-hosted Subscription Terms](https://logto.io/terms/self-hosted) stay the same.

## Usage limits \{#usage-limits}

Your license key carries the usage limits of your plan. Unlike the features a license unlocks, these limits are never enforced: exceeding one does not block sign-in, turn off features, or stop you from creating anything. Logto shows a warning instead.

The limits depend on which key is installed:

| Metric                 | Production key                                                      | Non-production key |
| ---------------------- | ------------------------------------------------------------------- | ------------------ |
| Monthly active users   | 50,000 for Self-hosted Pro. Self-hosted Enterprise: per order form. | Reported only      |
| Production deployments | 1                                                                   | Not applicable     |
| Monthly access tokens  | Reported only                                                       | 50,000             |
| Tenants                | Reported only                                                       | Reported only      |

If your order form states other limits, your keys carry those limits instead. The non-production limit of 50,000 access tokens is the same as the limit for Logto Cloud development tenants, and tells a non-production deployment apart from one that serves production traffic.

### How usage is counted \{#how-usage-is-counted}

Monthly active users and access tokens are counted from your own database, across all tenants except the admin tenant, in UTC calendar months:

- **Monthly active users (MAU)**: the number of unique users that are issued an access token at least once in the month.
- **Monthly access tokens**: the number of access tokens issued in the month, both for users and for machine-to-machine apps. Exchanging a refresh token for a new access token also counts. See [the connection between token consumption and MAU](/logto-cloud/billing-and-pricing#what-is-the-connection-between-token-consumption-and-mau).
- **Production deployments**: counted by Logto Cloud. It is the number of deployments with a production key, each identified by its `deploymentId`, that refreshed the license in the last 15 days. Instances that share one database are one deployment. Your instance refreshes weekly, so one missed refresh does not drop a deployment from the count. A deployment you have shut down stops counting 15 days after its last refresh.

A metric exceeds its limit when the larger of its last full month and its current month so far is above the limit. The count of the current month only grows, so a warning can appear before the month ends and is never a false alarm.

Your instance checks monthly active users and access tokens itself, so these warnings work offline and with usage reporting turned off. Only Logto Cloud can count production deployments, so that warning arrives with the next refresh.

### When a limit is exceeded \{#when-a-limit-is-exceeded}

Console shows a banner on every page that names each exceeded metric with its value and limit. You can dismiss the banner, and it comes back after 7 days if the limit is still exceeded.

Nothing is blocked. Under section 4.2 of the [Self-hosted Subscription Terms](https://logto.io/terms/self-hosted), contact Logto and, within 30 days, either upgrade to a Self-hosted Enterprise subscription that covers your usage, or reduce your usage to within the limits. Self-hosted Pro does not offer overage pricing. A non-production deployment that exceeds 50,000 access tokens a month may be treated as serving production traffic (section 3.2).

### Get a usage statement \{#get-a-usage-statement}

Logto may ask you for a statement of your usage, at most once per subscription term (section 4.3 of the [Self-hosted Subscription Terms](https://logto.io/terms/self-hosted)). Your instance can prepare the usage part from its own records. Send `GET /api/systems/license/usage-statement` with an access token for the [Logto Management API](/integrate-logto/interact-with-management-api):

```bash
curl 'https://your-logto-endpoint/api/systems/license/usage-statement' \
  -H 'Authorization: Bearer <access_token>'
```

The response lists the monthly active users and access tokens of each of the last 12 full UTC calendar months, oldest first, across all tenants except the admin tenant. A month without usage counts as zero. This example is shortened to two months:

```json
{
  "months": [
    { "month": "2025-11", "mau": 18234, "monthlyAccessTokens": 412907 },
    { "month": "2025-12", "mau": 19012, "monthlyAccessTokens": 430118 }
  ]
}
```

The statement is read from your database, so it also works offline and with usage reporting turned off. The request returns `404` when no license is installed. Add the number of deployments your subscription covers, then send the statement to Logto.

## License expiration \{#license-expiration}

A license covers a yearly period, and the **Expires on** date is the end of that period.

- **When you renew**, nothing needs to be done on your instance. The next refresh after the renewal replaces the installed key with a new one that expires a year later. It is normal for the page to show a date that has just passed for a few days while the renewal is picked up, and features stay available during this time.
- **When you do not renew**, the refresh is refused after the period ends. Features keep working until the end of the 30-day grace period, then your instance reverts to the OSS defaults, as if no license was installed. The license page shows a banner explaining this and the date it will happen.
- **If you reach the end of the grace period**, install a fresh key to unlock the features again. Contact Logto through the channel you used to get your license if you need one.

### What happens when features are turned off \{#what-happens-when-features-are-turned-off}

Reverting to the OSS defaults does not delete anything you created with a license:

- **Hide Logto branding**: the "Powered by Logto" mark is shown again. Your setting is saved, and applies again if a license is installed later.
- **SAML apps**: apps beyond the first 3 stay in place, but you cannot create new ones until you are under the limit.
- **Mandatory MFA**: you can always turn it off. You cannot turn it on again without a license.
- **Bring your UI, custom CSP, and Console invitations**: you cannot make new changes that need the feature, and your existing data is kept.

## Set up storage for Bring your UI \{#set-up-storage-for-bring-your-ui}

On Logto Cloud, Bring your UI assets are hosted by Logto. On your own instance, they are stored in an object storage that you configure. Logto unzips your upload and stores the files there, and serves them from there.

Set the `experienceBlobsProvider` system config with the same JSON structure as the [file storage provider](/logto-oss/file-storage-provider), for example, for an S3-compatible storage:

```bash
pnpm logto db system set experienceBlobsProvider '{"provider":"S3Storage","accessKeyId":"my-access-key-id","accessSecretKey":"my-secret-access-key","bucket":"logto-sie","endpoint":"https://s3.us-east-2.amazonaws.com"}'
```

Restart Logto after changing the config. Then follow [Bring your UI](/customization/bring-your-ui#upload-your-custom-ui-assets) to upload your assets in Console.

## Invitation emails for Console members \{#invitation-emails-for-console-members}

Console invitations are sent by email through the email connector of your default tenant. Make sure you have [set up an email connector](/connectors/email-connectors) before inviting members.
